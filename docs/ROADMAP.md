## 0. Коротко для владельца

**Что есть.** Работающее ядро операционной системы экспедитора: запрос клиента → варианты расчёта → заявка с обязательными этапами → назначение перевозчиков → брокер и оценка таможенных платежей → документооборот с версиями → печатная форма заявки. Четыре отдельных кабинета: сотрудники, клиенты, брокеры, перевозчики. Стек современный (Next.js 16, Prisma, PostgreSQL), код типизирован, сборка чистая.

**Проверка логики.** Я собрал проект, поднял PostgreSQL, засеял базу и прогнал 56 сквозных проверок API по всем четырём кабинетам, плюс снял скриншоты экранов на десктопе и на мобильном (375 px). **51 из 56 проверок прошли.** Основная бизнес-логика работает корректно: конвертация лида защищена от гонок (из 3 параллельных запросов проходит ровно один), обязательные этапы не удаляются, клиенту, брокеру и подрядчику цена и внутренние документы не видны, изоляция между клиентами (IDOR) соблюдается, деактивация брокера сразу закрывает ему доступ.

**Что мешает запуску в бою (критично, неделя работы):**
1. **В публичном репозитории лежит пароль** (в `check-master-pass.js` — пароль мастера из worklog) и 6 файлов с токенами сессий (`cmv*`). Пароль нужно сменить везде, где он использовался, а историю git — очистить.
2. **CI не запускался ни разу**: все 5 прогонов GitHub Actions упали на шаге «Set up job» (проблема настроек/биллинга Actions, а не кода). Кроме того, локально `eslint` падает с 3 ошибками в том же `check-master-pass.js`, так что после починки Actions CI всё равно будет красным.
3. **Блокировка входа может запереть владельца**: 10 неверных попыток на телефон мастера блокируют вход по этому телефону на 5 минут, с любого IP. Я воспроизвёл это в ходе теста.
4. **Нет миграций БД** (только `db push`). На боевой базе с данными это прямой риск потерять данные.
5. **Пакет документов в репо противоречив**: заголовок `LOGISTICS-ROADMAP.md` v2.0 обещает 47 карточек задач, фазы и сводку, но файл обрывается на разделе 5.9 (разделов 6–8 нет). В корне лежит роадмап другого проекта (APEX Moto, 5 210 строк про «наряды»), README ссылается на несуществующий `LOGISTICS-TASK-QUEUE.md`. Программисту непонятно, какой документ главный.

**Главный продуктовый вывод.** Система хорошо отвечает на вопрос «как вести сделку», но пока не экономит время компании, потому что:
- никто не получает уведомлений: ни менеджер о новом запросе, ни клиент о смене статуса, ни перевозчик о назначении, поэтому звонки и мессенджеры остаются;
- у заявки нет ответственного менеджера, поэтому нельзя сделать фильтр «мои заявки» и посчитать нагрузку;
- деньги хранятся только в рублях, целым числом, без себестоимости, поэтому для международной логистики (USD/EUR/CNY) маржу не посчитать;
- маршрут (откуда/куда), тип перевозки и дата хранятся в свободном JSON, поэтому фильтров и аналитики по направлениям нет.

**План.** Примерно 12 недель работы одного full-stack разработчика, 4 фазы с проверяемыми критериями выхода:
- **Фаза 0** (1 нед.): безопасность и гигиена репозитория.
- **Фаза 1** (3 нед.): пилот с реальными менеджерами — ответственный, деньги и валюты, маршрут, статусная модель, права.
- **Фаза 2** (4 нед.): уведомления и самообслуживание внешних участников, чтобы снять звонки.
- **Фаза 3** (4 нед.): финансы, маржа, дашборд владельца.

Сайт и SEO — отдельный трек: только после ответа, нужен ли входящий трафик.

Существующий в репозитории план v2.0 (47 задач, брендбук, гейты, R01–R17) я предлагаю **упростить**. Для проекта без единого живого пользователя он слишком тяжёлый по процессу и при этом не содержит главного: уведомлений, денег и пилота.

## 3. Аудит девяти специалистов

Формат: сильные стороны → проблемы → рекомендации (ID задачи роадмапа).

### 3.1 Бизнес/продукт-аналитик — цели, метрики, контекст

**Сильные стороны.** Правильно выбран центр системы — сделка от запроса до доставки. Закреплены разумные инварианты: снимок условий при конвертации, ручные статусы, обязательные этапы. Причины отказа уже собираются.

**Проблемы.**
- Цель «эффективность» не переведена в измеримые показатели, и в системе нет ни одной метрики.
- Время экономят три вещи, и все три отсутствуют: автоматические уведомления, самообслуживание внешних участников, шаблоны расчётов.
- Денежная модель не подходит для международной логистики: `priceEstimate Int` в рублях, нет валюты, НДС, себестоимости и маржи.
- У клиента (`Customer`) нет ИНН/КПП и реквизитов, это контакт, а не компания. Для B2B-документов этого мало.
- Номер договора — автоинкремент `Int`. Реальные договоры («0105/1-СВ») и их даты завести нельзя.

**Рекомендации.**
- Зафиксировать KPI эффективности. Базовые значения замерить на пилоте (P1-14), цели — по итогам пилота:

| KPI | Как считаем | Ориентир |
|---|---|---|
| Время до расчёта (time-to-quote) | медиана `первый QuoteOption.createdAt − Lead.createdAt` | < 4 рабочих часов |
| Конверсия запрос → заявка | won / (won + lost) за 30 дней | рост на 5–10 п.п. |
| Заявок на менеджера в месяц | count(Order) по `assignedToId` | рост на 20–30% |
| Доля статусов этапов, обновлённых самим перевозчиком | actorType=contractor / все смены статусов | > 60% |
| Доля документов через платформу | документы в системе / все документы по заявке | > 80% |
| Просроченные этапы | plannedDate < сегодня и статус ≠ done | < 10% |
| Маржа по заявке | выручка − себестоимость | видна по каждой заявке |

### 3.2 UX-исследователь / UX-аудитор — сценарии, удобство, проблемы

**Сильные стороны.** Есть экран «Требует внимания», глобальный поиск, хлебные крошки, понятная лента событий. Мобильная вёрстка списков и карточки клиента в целом адаптирована (проверено на 375 px).

**Проблемы (проверено на скриншотах).**
- Карточка заявки — экран высотой ≈ 3 500 px. Главный рабочий объект, этапы, находится в самом низу, под условиями, брокерами и документами. Менеджер скроллит каждый раз.

- Нет прогресса загрузки файла (4 МБ с телефона выглядят как зависание). Нет HEIC (фото с iPhone) и TIFF (сканы).
- Мобильное меню админки — горизонтальная полоса, где видно 4 из 11 разделов.
- Поля дат — нативные `mm/dd/yyyy` в браузерах с английской локалью.

**Рекомендации.** P1-10 карточка заявки на вкладках («Этапы» первыми), P1-02 редактирование лида, P2-02 человекочитаемые статусы для клиента + публичный комментарий к этапу, P2-03 «быстрые действия» подрядчика, P2-05 загрузка с прогрессом и форматами, P1-12 UI-баги. ### 3.6 Технический специалист / архитектор — ограничения, производительность, интеграции

**Сильные стороны.** Строгий TypeScript (`ignoreBuildErrors: false`), zod на входе, единый `apiErrorResponse`, файлы недоступны без авторизации, retry на гонки нумерации, регион Vercel совпадает с Neon.

**Проблемы.**
- **Нет миграций** (`db push`), при этом worklog и DEPLOY предписывают гонять `db push` на прод.
- **Нет транзакций в многошаговых операциях**: конвертация = 6–8 отдельных запросов (клиент, договор, заявка, статус лида, брокеры, документы, лента). При сбое посередине данные расходятся; в коде даже есть ветка «самопочинки».
- `isUniqueViolation` ловит **любой** P2002, а не только коллизию номера. Например, гонка по `leadId` 5 раз повторяет создание заявки.
- 4 копии auth-модуля: каждую правку безопасности нужно вносить четырежды.
- Файлы в Postgres: база растёт пропорционально документам, бэкапы тяжелеют, лимит 4 МБ — из-за ограничения тела serverless-функции.
- Нет `middleware`/`proxy`: защита страниц держится на layout-ах, а security-заголовков нет.
- Нет фоновых задач (cron/очередь), поэтому уведомления и напоминания сделать некуда.
- Нет наблюдаемости: логов задержек, отслеживания ошибок, health-check.
- Комментарии в коде — история разработки (ссылки на «Дорожку Г4», «урок APEX Moto»). Это повышает порог входа нового разработчика; schema.prisma на 678 строк — в основном комментарии.

**Рекомендации.** E0-03 Prisma Migrate (baseline), P1-15 транзакции `db.$transaction` для конвертации/рождения подрядчика/документов, E0-08 единый `portal-auth`, P2-05 файлы в S3-совместимое хранилище (Yandex Object Storage / Cloudflare R2) с presigned upload — снимает лимит 4 МБ, P2-01 таблица `Notification` (outbox) + Vercel Cron, E0-10 Sentry + `/api/health`. ### 3.9 Аналитик данных / CRO-специалист — воронки, конверсии, точки потерь

**Сильные стороны.** Данные для воронки уже есть: статусы, источник (manual/cabinet), причина отказа, лента с автором и временем, план и факт этапов.

## 4. План развития (стратегия)

**Принцип: сначала в работу, потом красота.** Ценность системы появляется только когда менеджеры перестают дублировать работу в Excel и мессенджерах. Поэтому порядок такой:

1. **Безопасно** (Фаза 0): закрыть утечки и риски потери данных — без этого нельзя заводить реальных клиентов.
2. **Пригодно для ежедневной работы** (Фаза 1): ответственный, редактирование, деньги в валютах, маршрут, корректные статусы, права. Итог — **пилот 2 недели с реальными заявками**.
3. **Экономит время** (Фаза 2): уведомления и самообслуживание клиента, перевозчика и брокера, чтобы убрать звонки «где груз?» и «пришлите документ».
4. **Даёт управленческие цифры** (Фаза 3): маржа, дашборд, причины потерь.
5. **Рост** (Фаза 4): сайт, интеграции (ЭДО, 1С, трекинг), калькулятор — по решениям владельца.

Процесс разработки — облегчённый: одна задача = одна ветка = один PR, зелёный CI, Definition of Done (см. правила). От гейтов, брендбука и R01–R17 из v2.0 остаются только реально проверяемые пункты.

## 7. Что сохранить из текущего плана v2.0 и что изменить

**Сохранить:** принципы раздела 3 (4 кабинета = 4 типа пользователей; терминальные статусы только операциями; заявка — источник правды; видимость через связь со сделкой; файлы только через авторизацию; неразрушающие изменения схемы), правило reuse-first, «одна задача = одна ветка = один PR», красный CI не мержится.

**Изменить:**
- 5 фаз с гейтами и 47 карточками → 4 фазы с измеримыми критериями выхода, привязанными к пилоту и KPI.
- Брендбук, SEO и CRO для закрытой системы без пользователей → после пилота, кроме noindex.
- Правила R01–R17, где R16 и R17 «зарезервированы», → короткий набор проверяемых правил (файл правил проекта).
- worklog как основной журнал → CHANGELOG + описания PR; worklog — в архив.
