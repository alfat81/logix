## 1. Цель и границы

Цель (ТЗ §1): полноценная работа с несколькими независимыми вариантами транспортного расчёта в рамках одного запроса клиента — клиент сохраняет запрос даже неполным, менеджер создаёт к нему несколько альтернативных расчётов с автозаполнением исходных данных из запроса, каждый вариант имеет собственные маршрут, параметры перевозки, коммерческие условия и снимок данных груза, выбранный и согласованный вариант корректно переносится в заказ.

Границы (ТЗ §10): правила ролей не меняются; действующие правила согласования и конвертации сохраняются — все точки, где предложено их касание, вынесены в дефолты Р-1…Р-6 (§12) и требуют отдельного решения владельца; кабинет подрядчика не затрагивается; миграции и правки общей тестовой БД — только по отдельному разрешению.

## 3. Целевая модель данных — одна additive-миграция

Миграция волны 1 — имя-маркер `df_27_quote_variants` (additive, совместима с кодом v0.9.1 — обращения к новым колонкам до релиза отсутствуют; прецедент `bl_phone_ops`):

```text
Lead                 + wishes            TEXT?      -- «Пожелания к перевозке», свободный текст (ТЗ §2.4)
QuoteOption          + routeSnapshot     Json?      -- снимок маршрутных полей запроса на момент создания
                     + cargoSnapshot     Json?      -- снимок грузовых полей запроса
                     + routeStops        Json?      -- промежуточные точки варианта (ТЗ §4)
                     + sourceFields      Json?      -- provenance: ключи, скопированные из запроса
                     + editedFields      Json?      -- provenance: ключи, переопределённые менеджером
                     + isPreliminary     Bool NOT NULL DEFAULT false   -- предварительный расчёт (ТЗ §5.3)
                     + missingData       Json?      -- зафиксированный перечень недостающих критичных данных
                     + priceReviewRequired Bool NOT NULL DEFAULT false -- «данные запроса изменились — пересмотрите цену» (ТЗ §5.5)
                     + updatedAt         DateTime @updatedAt
                     + updatedById       String?    -- кто последним правил (имя — снимком в событии)
                     + updatedByName     String?
LeadApprovalSnapshot + routeSnapshot     Json?      -- снимок согласования v2 (ТЗ §6.4)
                     + cargoSnapshot     Json?
```

Структура снимков (Json, помечается v:1; источник — серверный бланк запроса, те же поля, из которых BL-5 собирает снимок заявки):

- routeSnapshot: originCity, originCountry, originCountryCode, destinationCity, destinationCountry, destinationCountryCode, readyDate, incotermCode, incotermPlace, wishes;
- cargoSnapshot: cargoName, hsCode, placesCount, packaging (+code), weightKg, volumeM3, cargoValue, cargoValueCurrency, dangerous, stackable, tiltable, specialRequirements, shipper, consignee, documents — справочный список привязанных к запросу документов ({id, kind, name}, без правовой связи).

Читатели снимков — толерантные (прецедент quote-snapshot.ts: пустые ключи не ломают чтение).

История правок: отдельные таблицы НЕ заводятся — Activity-события уже фиксируют «кто/когда/что» (actor-снимки, дифф по прецеденту lead_edited); option_updated обогащается перечнем изменённых ключей. Это соответствует принципу схемы «история дольше справочника» и не дублирует механизм.

Backfill не требуется: null-снимок = «легаси-вариант» (только коммерческие поля, как сегодня); UI показывает ему «Данные — как в запросе» и действие «Заполнить из запроса» (создание снимка постфактум, волна 1). Существующие варианты, согласованные снимки и заказы не изменяются (ТЗ §10).

## 4. Правила копирования и provenance (ТЗ §3–§4)

1. Источник копирования — всегда исходный запрос (Lead), никогда — предыдущий вариант (ТЗ §3.5): единая серверная функция buildOptionSnapshots(leadBlank) → {routeSnapshot, cargoSnapshot, sourceFields}; unit-тесты на состав и на переопределения.
2. Создание варианта (POST): снимки строятся автоматически (ТЗ §3.3–3.4); тело может содержать overrides (маршрут, груз, пожелания, промежуточные точки) — переопределённые ключи уходят в editedFields, остальные — в sourceFields. Ручного повторного заполнения имеющихся сведений нет.
3. Правка варианта (PATCH): снимки правятся свободно; изменённые ключи дописываются в editedFields; updatedAt/updatedBy* — автоматически. Правка варианта не меняет запрос и другие варианты — по построению (снимки копируются значениями, ТЗ §4).
4. Diff «вариант ↔ исходный запрос» — чистая функция diffOptionVsLead(lead, option) → перечень расхождений по ключам: UI «чем вариант отличается от запроса» (ТЗ §4).
5. Ответы на вопросы ТЗ §4: скопировано — sourceFields; изменено менеджером — editedFields; кем и когда — updatedBy*/Activity-снимки; отличие от запроса — diffOptionVsLead.

## 5. Полнота данных и предварительные расчёты (ТЗ §5)

1. Серверная константа критичных параметров достоверного расчёта: обе точки маршрута, дата готовности груза, вес или объём, количество мест, код ТН ВЭД, стоимость груза и валюта, условия Инкотермс. Функция completeness(lead, option) → {ready, missing[]} (unit).
2. POST варианта при незакрытых критичных параметрах — только с isPreliminary=true и фактическим missingData; без предварительной отметки → 422 с перечнем недостающего (ТЗ §5.1–§5.3).
3. Предварительный вариант помечается в UI менеджера и в кабинете клиента («Предварительный расчёт — не окончательная стоимость»). По дефолту Р-3 согласование предварительного варианта запрещено (409 «Заполните недостающие данные и пересчитайте») — ТЗ §5.4.
4. Индикатор готовности запроса к расчёту — вычисляемый (тот же missing) на карточке запроса, не хранимое поле (ТЗ §2.3).
5. Пересмотр цены (ТЗ §5.5): при правке запроса (lead_edited), если изменились ценозначимые ключи — маршрут, дата готовности, вес/объём/места, стоимость груза, опасные свойства, ТН ВЭД, Инкотермс — сервер в той же транзакции ставит priceReviewRequired=true всем вариантам запроса и пишет событие с перечнем изменённых ключей; флаг снимается правкой/пересохранением варианта. Незаметного изменения нет: варианты хранят собственный снимок на момент создания.

## 6. Согласование и перенос в заказ (ТЗ §6)

Не меняется (уже соответствует ТЗ): выбор варианта клиентом (select-option) или менеджером (confirm от имени клиента); атомарная фиксация согласия; неизменяемый LeadApprovalSnapshot; BL-4 — конвертация только после согласия; сброс согласования с сохранением истории снимков; после конвертации запрос → won, его правки и правки вариантов заявку не меняют (ТЗ §6.6 — по построению).

Меняется:

1. Снимок согласования v2: при подтверждении варианта со снимками routeSnapshot/cargoSnapshot копируются в LeadApprovalSnapshot — иммутабельно, как коммерческие поля сегодня; у легаси-вариантов — null, поведение прежнее (ТЗ §6.4–§6.5).
2. Конвертация: buildOrderQuoteSnapshot расширяется снимками v2 — Order.quoteSnapshot (Json, схема не меняется) получает маршрут/груз/условия именно согласованного варианта.
3. Маршрутные колонки заявки — Р-6: дефолт (А) — из снимка согласованного варианта, если он есть; иначе из запроса, как сейчас (BL-5). Альтернатива (Б) — всегда из запроса, с предупреждением. При расхождении «вариант ↔ запрос» ответ конвертации содержит предупреждение optionLeadDivergence — решение менеджера осознанное; правило «заявка — источник правды» сохраняется.
4. При реализации волны 2 — ревизия печатных форм заявки (источник колонок меняется только при Р-6=А и только для вариантов со снимками).

## 7. Таможенные расчёты и ТН ВЭД (ТЗ §7) — проверка совместимости

Существующий механизм версий CustomsCalculation (isCurrent):

1. «Процентные ставки и коды ТН ВЭД фиксируются в версии согласованного расчёта» — выполняется: в позициях снимок dutyPercent/addDutyPercent/vatPercent и hsCode (снимок ответа брокера DF-18); ✅
2. «Смена валюты и даты курса позволяет пересчитать суммы без изменения ставок» — выполняется: fxDate/fxRates + пересчёт итогов, ставки позиций не трогаются; ✅
3. «Исправление кода/ставок — через новую версию с сохранением истории» — выполняется: PUT правит только isCurrent-версию, POST создаёт новую; исторические версии не правятся; ✅

Разрывы и предложения (волна 2):

1. PUT текущей версии доступен и после согласования, и после конвертации — печатное приложение заявки читает isCurrent-версию, поэтому её правка задним числом меняет печатные итоги без новой версии (возможность «незаметного изменения согласованных данных», которую ТЗ предписывает устранить). Р-4: после конвертации запроса расчёты запроса замораживаются (PUT → 409 «Запрос конвертирован — расчёты создаются на заявке»); расчёт заявки, по которому уже собиралось печатное приложение, PUT-ом не правится — только новая версия (POST); каждое изменение — событие с диффом ключей.
2. ТЗ §7.4 «при переносе в заказ должны сохраняться согласованные сведения и история расчётов»: сейчас расчёты при конвертации не переносятся (зафиксированное в схеме решение «запрос остаётся источником истории, заявка считает свои»). Р-5: при конвертации копировать последнюю isCurrent-версию запроса на заявку новой версией с пометкой origin=carried_from_lead — история сохраняется в обеих точках, последующие пересчёты — новыми версиями заявки. Это касание правил конвертации — по ТЗ §10 вынесено на отдельное решение владельца (обоснование: без переноса согласованные таможенные сведения не следуют за согласованным вариантом в заказ).
3. Связь расчёта с вариантом: nullable-колонка quoteOptionId у CustomsCalculation (additive, волна 2) — расчёты, которые велись в контуре конкретного варианта; при согласовании в снимок согласования записывается ссылка на версию расчёта — фиксируется «какой расчёт был при согласовании» (ТЗ §7.4).

## 9. UI (ТЗ §8)

1. Форма создания/правки варианта — блоками: (1) Исходные данные запроса — автозаполнено, только чтение; (2) Маршрут и транспорт — адаптация маршрута, видов транспорта, промежуточные точки; (3) Характеристики груза — снимок с корректировкой; (4) Коммерческие условия — цена, валюта, НДС, срок, ориентир (как сейчас); (5) Внутренняя экономика — себестоимость и её валюта (зона сотрудника, D3); (6) Недостающие сведения и предупреждения — missing, priceReviewRequired, расхождение с запросом.
2. Метки происхождения: «из запроса» / «изменено» на полях блоков 1–3 по sourceFields/editedFields — визуальное различение унаследованного и правленного (ТЗ §8).
3. Карточка запроса: список вариантов с признаками (выбран / предварительный / требует пересмотра цены / отличается от запроса), «Создать вариант» (источник — запрос), индикатор готовности.
4. Кабинет клиента: пометка предварительных расчётов; блок «Зафиксированные условия» и согласование — как сейчас; пожелания к перевозке в анкете — волна 2 (Р-1).
5. Гигиена: компоненты ≤300 строк (RULES 2.14, IC-09) — форма разносится на подкомпоненты (прецедент StageRequirementsDialog).

## 10. Права, безопасность, границы

1. Роли не меняются (ТЗ §10): варианты создают и правят сотрудники; клиент — выбор/согласование и дополнение запроса по Р-1.
2. D3: costEstimate/costCurrency — по-прежнему вне клиентских и брокерских проекций; перечень missing — только сотрудникам; в клиентскую проекцию варианта добавляется только isPreliminary; снимки груза — данные самого клиента (его анкета); ClientOptionRow расширяется явно, e2e-проверка состава проекций (сценарий 11).
3. Заморозка кабинета подрядчика (D31) не затрагивается; e2e_contractor_frozen (16/16) — без изменений.
4. Скоупинг: варианты доступны только через запрос и его роуты; брокерские проекции вариантов не содержат.

## 11. Волновой план, миграция, откат

1. **Волна 1 «снимки и независимость» (≈3–4 д, ±30%):** миграция df_27_quote_variants; автозаполнение + provenance; полнота и предварительные расчёты; API вариантов; UI менеджера (блоки 1–6, метки); события; unit + e2e-блок независимости. Гейт 1 — полный прогон (tsc/lint/vitest/build/e2e/заморозка/integrity/knip/gitleaks) + смоук трёх кабинетов + мобильные скриншоты 1440/375.
2. **Волна 2 «запрос, согласование, заказ, таможня» (≈3–4 д):** wishes в кабинетах; статус needs_data + индикатор готовности; окно правки клиента (Р-1); снимок согласования v2 + Р-3; конвертация (расхождение, Р-5, Р-6); таможенные гарды (Р-4); клиентский UI. Гейт 2 + сводный отчёт об изменениях → решение владельца о выкате (по образцу DF-26, очередь №23 → §6.1).
3. Миграция — одна, additive, применяется владельцем по протоколу А (статус миграций → deploy → контрольные запросы на состав колонок). Совместимость: прежний код не обращается к новым колонкам; backfill не требуется; откат не требуется (колонки игнорируются прежним кодом).
4. Зависимости: DF-24/DF-25/DF-26 — в main; конфликтов файлов нет, кроме согласованных точек расширения (§8). С DF-24/DF-25/DF-26 не пересекается по объёму.

| Риск | Вероятность / влияние | Мера |

## 15. Критерий завершения

Из ТЗ §11 — функциональность считается реализованной, когда клиент может сохранить неполный запрос, менеджер может создавать к нему несколько независимо редактируемых вариантов с автоматическим заполнением исходных данных, клиент может выбрать вариант, а менеджер — преобразовать его в заказ с полным сохранением согласованных условий и истории. Плюс прохождение гейтов обеих волн и приёмка владельцем (§6.1). Существенно: до согласования настоящего плана (и решений Р-1…Р-6) реализация не начинается — код не пишется, миграции не выполняются.
