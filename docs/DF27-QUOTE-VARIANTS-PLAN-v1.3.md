## 1. Цель и границы

Цель (ТЗ §1): полноценная работа с несколькими независимыми вариантами транспортного расчёта в рамках одного запроса клиента — клиент сохраняет запрос даже неполным, менеджер создаёт к нему несколько альтернативных расчётов с автозаполнением исходных данных из запроса, каждый вариант имеет собственные маршрут, параметры перевозки, коммерческие условия, полноценный расчёт и снимок данных груза, выбранный и согласованный вариант корректно переносится в заказ.

Границы (ТЗ §10): правила ролей не меняются, кроме полномочия, открытого решением владельца (D73) — информационный пересчёт таможенного расчёта для клиента собственной сделки (§11.1); действующие правила согласования и конвертации уточняются по решениям владельца Р-1/Р-3/Р-5 (§13); решения Р-2, Р-4, Р-6 закрыты правками владельца (D72, таможенная часть уточнена формулировкой D73) и реализуются как обязательные требования; кабинет подрядчика не затрагивается; миграции — additive, поэтапные, каждая — отдельное разрешение владельца; исторические данные не удаляются и не переписываются.

## 3. Целевая модель данных — поэтапные additive-миграции

Миграции (исправление модели миграции v1.0 — правка №5): **по одной additive-миграции на волну**, каждая применяется владельцем по протоколу А с отдельным разрешением; обе совместимы с кодом v0.9.1 (обращений к новым колонкам/таблицам до релиза нет — прецеденты `bl_phone_ops`, `df_26_docs_center`).

**Волна 1 — `df_27_option_snapshots`:**

```text
Lead                 + wishes            TEXT?      -- «Пожелания к перевозке», свободный текст (ТЗ §2.4)
QuoteOption          + routeSnapshot     Json?      -- снимок маршрутного блока запроса (см. ниже)
                     + cargoSnapshot     Json?      -- снимок грузового бланка запроса ЦЕЛИКОМ + пожелания
                     + routeStops        Json?      -- промежуточные точки варианта (ТЗ §4)
                     + sourceFields      Json?      -- provenance: ключи, скопированные из запроса
                     + editedFields      Json?      -- provenance: ключи, переопределённые менеджером
                     + isPreliminary     Bool NOT NULL DEFAULT false   -- предварительный расчёт (ТЗ §5.3)
                     + missingData       Json?      -- перечень недостающих критичных данных при сохранении
                     + priceReviewRequired Bool NOT NULL DEFAULT false -- флаг актуализации расчёта после любой правки редактируемых данных заявки (D75)
                     + updatedAt         DateTime @updatedAt
                     + updatedById       String?    -- кто последним правил (имя — снимком в ревизии/событии)
                     + updatedByName     String?
+ таблица QuoteOptionCalcLine    -- строки транспортного расчёта (§5)  [новая]
+ таблица QuoteOptionRevision    -- история изменений варианта (§4)    [новая]
```

**Волна 2 — `df_27_approval_and_customs`:**

```text
LeadApprovalSnapshot + routeSnapshot     Json?      -- снимок согласования v2 (ТЗ §6.4)
                     + cargoSnapshot     Json?
                     + calcSnapshot      Json?      -- снимок строк и итогов расчёта на момент согласования
                     + customsCalculationId String? FK CustomsCalculation -- какая версия расчёта была при согласовании
                     + printRevisionId   String? FK LeadPrintRevision -- неизменяемая печатная редакция, подтверждённая сторонами
CustomsCalculation   + quoteOptionId     String? FK QuoteOption -- расчёты, которые велись в контуре варианта
                     + origin            String?    -- null = собственный; 'carried_from_lead' = перенесён при конвертации (Р-5)
+ таблица LeadPrintRevision        -- неизменяемые редакции печатной формы заявки (Р-3) [новая]
+ таблица LeadPrintRevisionConfirmation -- подтверждения клиента и менеджера для одной редакции (Р-3) [новая]
+ таблица CustomsFxRecalc        -- информационные пересчёты курса (§8.4, D73) [новая]
+ таблица CustomsFinalPayment    -- окончательные платежи по ДТ (§8.6, D73)    [новая]
```

Структура снимков (Json, помечается `v:1`; источник — серверный бланк запроса; **правка №4 — полный состав исходной анкеты**):

- `routeSnapshot`: originCity, originCountry, originCountryCode, destinationCity, destinationCountry, destinationCountryCode, transportType, readyDate, incotermCode, incotermPlace — все маршрутные колонки запроса и условия поставки;
- `cargoSnapshot`: `{ v:1, cargo: <cargoInfo запроса целиком>, wishes: string|null }` — грузовой бланк verbatim: известные ключи формы (cargoName, hsCode, placesCount, packaging/packagingCode, weightKg, volumeM3, cargoValue, dangerous, stackable, tiltable, specialRequirements, shipper*, consignee*, shipDate…) **и все произвольные ключи, которые клиент/менеджер внесли в cargoInfo** — ничего не теряется независимо от эволюции бланка; `wishes` заполняется с волны 2 (до этого `null`).

Контакты (`rawContact`, привязанный клиент) в снимки не входят — не расчётные данные (гигиена D3). Документы в снимки не входят (§7.4 — модель «документы следуют за сделкой»; v1.0 «справочный список {id, kind, name} без правовой связи» исключён как двусмысленный).

Читатели снимков — толерантные (прецедент quote-snapshot.ts: пустые/незнакомые ключи не ломают чтение).

**QuoteOptionCalcLine** (строка расчёта): id, optionId (FK cascade), sortOrder, article (статья из реестра `OPTION_CALC_ARTICLES` — §5), title, amount Decimal(14,2), currency (валюта строки), fxRateToOffer Decimal(14,6)? — курс к валюте предложения, снимок на момент сохранения; null, если валюта строки = валюте предложения, amountOffer Decimal(14,2)? — сумма в валюте предложения (считает сервер), source (`manual` | `customs_version`), customsCalculationId String? FK (статья по версии таможенного расчёта), comment String?, createdAt/updatedAt; `@@index([optionId, sortOrder])`, `@@unique` нет (порядок — sortOrder).

**QuoteOptionRevision** (история варианта): id, optionId (FK cascade), seq Int — порядковый номер правки внутри варианта, kind (`created` | `updated` | `filled_from_lead` | `calculation_refresh_reset`), actorType/actorId/actorName — снимки исполнителя (прецедент Activity), changedFields Json? — `{ключ: {from, to}}` по верхнеуровневым ключам (коммерческие поля, ключи снимков, агрегат по строкам расчёта), createdAt; `@@unique([optionId, seq])`, `@@index([optionId, createdAt])`. Ревизии не редактируются и не удаляются (эндпоинтов правки нет; каскад — только с удалением варианта/запроса, что соответствует существующей схеме).

**LeadPrintRevision** (неизменяемая печатная редакция заявки — Р-3): id, leadId (FK Lead), seq Int — последовательность редакций, leadSnapshot Json — полный набор полей заявки, включённых в печатную форму, renderedFileId String? — ссылка на прикреплённый файл/Document, contentHash String — хеш содержимого сформированной редакции, createdById/createdByName, createdAt; `@@unique([leadId, seq])`, `@@index([leadId, createdAt])`. После создания содержимое, файл и hash неизменяемы; исправление формирует новую редакцию, а не перезаписывает старую.

**LeadPrintRevisionConfirmation** (двустороннее подтверждение редакции — Р-3): id, revisionId (FK LeadPrintRevision, cascade), partyRole (`client` | `manager`), actorId, actorName, confirmedAt, method (например, действие в кабинете/подтверждение сотрудником после фиксации волеизъявления клиента), comment String?; `@@unique([revisionId, partyRole])`, `@@index([revisionId, confirmedAt])`. Обе записи должны относиться к одному `revisionId`; подтверждение менеджера не заменяет подтверждение клиента и наоборот. При создании новой редакции подтверждения старой не переносятся.

**CustomsFxRecalc** (информационный пересчёт курса — D73): id, calculationId (FK CustomsCalculation, cascade), actorRole (`manager` | `client`), actorId String?, actorName String — снимки исполнителя (прецедент Activity), currency String — валюта представления, fxDate DateTime @db.Date — выбранная дата курса, fxRates Json — снимок курсов на fxDate (тот же формат, что у расчёта: за единицу валюты, источник cbr/manual), totals Json — пересчитанные таможенная стоимость и суммы платежей по позициям и итоги (чистая функция расчёта — §8.4), createdAt; `@@index([calculationId, createdAt])`. Записи append-only: не редактируются и не удаляются (эндпоинтов правки нет), пересчёт не меняет ни нормативный слой версии, ни её собственные fxDate/fxRates/суммы — пересчёты менеджера и клиента независимы и не перезаписывают друг друга.

**CustomsFinalPayment** (окончательные платежи по ДТ — D73): id, orderId (FK Order, cascade), dtDate DateTime @db.Date — дата подачи ДТ, lines Json — суммы по видам платежей `[{kind, amount, currency}]` (в валютах уплаты), note String?, actorId String?, actorName String, createdAt; `@@index([orderId, createdAt])`. Записи append-only: новая запись прежние не меняет, эндпоинтов правки/удаления нет; отображается последняя запись, история доступна развёрнуто (§8.6).

Backfill не требуется: null-снимок = «легаси-вариант» (только коммерческие поля, как сегодня); UI показывает ему «Данные — как в запросе» и действие «Заполнить из запроса» (создание снимка постфактум, волна 1, ревизия `filled_from_lead`). Существующие варианты, согласованные снимки и заказы не изменяются (ТЗ §10).

## 4. Правила копирования, provenance и история изменений (ТЗ §3–§4; правка №4)

1. Источник копирования — всегда исходный запрос (Lead), никогда — предыдущий вариант (ТЗ §3.5): единая серверная функция buildOptionSnapshots(leadBlank) → {routeSnapshot, cargoSnapshot, sourceFields}; unit-тесты на состав (включая произвольные ключи cargoInfo) и на переопределения.
2. Создание варианта (POST): снимки строятся автоматически (ТЗ §3.3–3.4); тело может содержать overrides (маршрутные поля, грузовые ключи, промежуточные точки, пожелания варианта) — переопределённые ключи уходят в editedFields, остальные — в sourceFields. Ручного повторного заполнения имеющихся сведений нет. В той же транзакции — ревизия `created` (kind, актор, перечень overrides).
3. Правка варианта (PATCH): снимки и строки расчёта правятся свободно; изменённые ключи дописываются в editedFields; updatedAt/updatedBy* — автоматически; **в той же транзакции — ревизия `updated` с диффом `{ключ: {from, to}}`** (seq = max+1 внутри варианта). Правка варианта не меняет запрос и другие варианты — по построению (снимки копируются значениями, ТЗ §4).
4. История варианта — таблица QuoteOptionRevision (отзыв позиции v1.0 «отдельные таблицы НЕ заводятся»): Activity-события остаются лентой, но диффы там — текст в description, по ним нельзя показать поле-за-поле историю конкретного варианта и восстановить порядок правок; ревизии дают ТЗ §4 (кем/когда/что изменено — по каждому варианту) в структурном виде. UI «История варианта» — §10.
5. «Заполнить из запроса» (легаси-вариант) — POST /api/admin/options/[id]/fill-from-lead: строит снимки постфактум, sourceFields/editedFields заполняются, ревизия `filled_from_lead`.
6. Diff «вариант ↔ исходный запрос» — чистая функция diffOptionVsLead(lead, option) → перечень расхождений по ключам: UI «чем вариант отличается от запроса» (ТЗ §4).
7. Ответы на вопросы ТЗ §4: скопировано — sourceFields; изменено менеджером — editedFields; кем и когда — ревизии (полная история) и updatedAt/updatedBy*; отличие от запроса — diffOptionVsLead.

## 5. Полноценная модель транспортного расчёта (правка №2)

Вариант — самостоятельный расчёт, а не набор полей коммерческого предложения. Состав варианта: коммерческие поля (как сегодня) + маршрут/груз (снимки §3 + routeStops) + **расчёт** (строки QuoteOptionCalcLine) + provenance + ревизии.

1. Строки расчёта — статьи стоимости перевозки. Реестр статей `OPTION_CALC_ARTICLES` в коде (src/lib/option-calc.ts, правило реестров — инвариант 9): `freight` (фрахт), `terminal` (терминальные/СВХ), `handling` (обработка груза), `customs` (таможенные платежи), `broker` (брокер/декларант), `insurance` (страхование), `lastMile` (доставка до получателя), `other`. Строка: статья, наименование, сумма, валюта, курс к валюте предложения (снимок), сумма в валюте предложения (сервер), комментарий, ссылка на версию таможенного расчёта (для `customs`/`broker`).
2. Итоги — серверная чистая функция sumOptionCalc(lines, offerCurrency) → {по статьям, всего в валюте предложения}; кэшируемых агрегатов в БД нет (строк немного, пересчёт на чтении; unit-тесты на округление и валюты).
3. Сверка с себестоимостью: расхождение суммы строк и costEstimate — не ошибка, а предупреждение (calcMismatch в ответе PATCH и в блоке 6 UI): costEstimate остаётся ручным внутренним полем сотрудника. Маржа (price − всего по строкам) — только сотрудникам (D3).
4. Таможенная статья: строка `customs` может ссылаться на конкретную версию таможенного расчёта (customsCalculationId); при создании из версии — снимок платежей (paymentsTotal; вознаграждение брокера — отдельной строкой `broker` по brokerFeeRub). Автообновления суммы из версии нет — это снимок значений на момент расчёта варианта. **Информационный пересчёт курса связанной версии (§8.4) не меняет ни суммы версии, ни строки варианта и priceReviewRequired не включает** — по D73 денежный слой пересчёта не является обязательством; обязательство — цена предложения варианта. Любая правка редактируемых данных заявки помечает все варианты для актуализации (§6.5, D75); информационный FX-пересчёт остаётся исключением, поскольку не изменяет данные заявки (D73).
5. Согласование фиксирует расчёт: в LeadApprovalSnapshot.calcSnapshot копируются строки и итоги на момент согласования (иммутабельно, §7). В заказе снимок живёт в Order.quoteSnapshot.calc и доступен только сотрудникам — печатная форма клиента по-прежнему показывает перечень услуг и итоговую цену, а не структуру себестоимости (D3).
6. Клиентская проекция: строки расчёта, итоги и маржа не покидают сервер — CLIENT_OPTION_FIELDS не расширяется (e2e-проверка состава, сценарий 11).

## 6. Полнота данных, needs_data и предварительные расчёты (ТЗ §5; правка №3)

**Нормативное правило §6.4:** если после сохранения заявки хотя бы один критичный параметр отсутствует, сервер автоматически устанавливает `needs_data`. Статус `new` допустим только при заполненной критичной анкете и отсутствии вариантов; при наличии вариантов и полной анкете — `calculated`. Приёмочные тесты обязаны проверять именно это правило.

1. Серверная константа критичных параметров достоверного расчёта: обе точки маршрута, дата готовности груза, вес или объём, количество мест, код ТН ВЭД, стоимость груза и валюта, условия Инкотермс. Функция completeness(lead, option?) → {ready, missing[]} (unit; значения — из маршрутных колонок и cargoInfo).
2. POST варианта при незакрытых критичных параметрах — только с isPreliminary=true и фактическим missingData; без предварительной отметки → 422 с перечнем недостающего (ТЗ §5.1–§5.3).
3. Предварительный вариант помечается в UI менеджера и в кабинете клиента («Предварительный расчёт — не окончательная стоимость»). **Предварительный вариант разрешено согласовать**: согласие не превращает предварительную цену в окончательное обязательство и не отменяет список недостающих данных. В снимке согласования сохраняются `isPreliminary=true`, перечень `missingData`, версия заявки и версия печатной формы/редакции, которую подтвердили стороны (§7).
4. **needs_data — автоматический статус** (устранение противоречия v1.0, где Р-2 предлагал ручной режим при вычисляемой готовности):
   - детерминированная функция expectedLeadStatus(текущий статус, optionsCount, missing): `won`/`lost` — автоматикой не трогаются; `missing` непуст → `needs_data`; иначе `optionsCount > 0` → `calculated`; иначе → `new`. Поэтому новая неполная заявка после сохранения получает `needs_data`, а не `new`;
   - `client_approved` не меняется фоновым пересчётом статуса; однако явная правка редактируемых данных заявки (Р-1) в одной транзакции сохраняет прежний LeadApprovalSnapshot, отзывает текущее согласование и переводит заявку в `needs_data` либо `calculated` по результату completeness, после чего ставит флаг актуализации всем вариантам;
   - назначение и снятие — **только сервером**, в транзакции сохранения анкеты (клиентский PATCH, менеджерский PATCH), создания/удаления варианта и заполнения из запроса: вычисленный статус ≠ текущему → переход + стандартное событие смены статуса + пересчёт «мяча»;
   - вручную: переход **в** needs_data запрещён (409 «Статус „Требует дополнительных данных“ выставляется автоматически по полноте анкеты»); **из** needs_data вручную разрешён только `lost` (закрытие запроса);
   - матрица LEAD_TRANSITIONS: `new: [needs_data, calculated, lost]`; `needs_data: [new, calculated, lost]` (первые два — автоматикой); `calculated: [needs_data, lost]` (возврат в needs_data — автоматом, если анкету дополнили до неполной); `client_approved` — только явный атомарный отзыв согласования при правке заявки (Р-1); `won/lost` — без изменений;
   - «мяч» (DF-05): правило `needs_data → manager/no_data` — «Требует дополнительных данных — дополните анкету или запросите у клиента» (computeWaitingLead, unit-тест);
   - индикатор готовности запроса к расчёту на карточке — вычисляемый (тот же missing), не хранимое поле (ТЗ §2.3);
   - Р-2 закрыт: ручной менеджерский режим из v1.0 исключён (правка №3, D72).
5. **Актуализация вариантов после правки заявки (Р-1).** Клиент может корректировать все доступные ему поля и прикрепляемые данные своей заявки после создания вариантов — до конвертации в заказ и закрытия заявки (`won`/`lost`). Менеджер также может дополнять заявку в рамках своих полномочий. Любое сохранённое изменение редактируемых данных заявки (кроме технических полей учётной записи, не относящихся к содержанию заявки) в одной транзакции: (а) сохраняется в истории заявки с автором и diff; (б) оставляет ранее созданные снимки вариантов неизменными; (в) устанавливает `priceReviewRequired=true` **для всех существующих вариантов** этой заявки — флаг по смыслу означает «требуется актуализация расчёта», а не только изменение цены; (г) создаёт уведомление/событие, видимое и клиенту, и менеджеру: «В заявку внесены изменения — варианты расчёта требуют актуализации». В обеих ролях показываются отметка, дата и автор изменения; внутренние расчётные строки, себестоимость и маржа клиенту не раскрываются. Сотрудник актуализирует каждый вариант отдельно: выполняет пересчёт и сохраняет новую ревизию; только это снимает флаг для конкретного варианта. Простое открытие или сохранение без пересчёта флаг не снимает. Если заявка уже `client_approved`, сервер в той же транзакции с изменением автоматически сбрасывает текущее согласование, сохраняет прежний LeadApprovalSnapshot и создаёт событие об отзыве прежнего согласования; изменение не блокируется ожиданием отдельного ручного сброса. После актуализации вариантов клиент подтверждает обновлённый вариант и новую редакцию заявки. После `won`/`lost` правка запрещена. Информационный пересчёт курса таможенной версии (§8.4) сам по себе не меняет данные заявки и не устанавливает флаг актуализации вариантов (D73).

## 7. Согласование и перенос в заказ (ТЗ §6)

Сохраняются: выбор варианта клиентом (select-option) или менеджером (confirm от имени клиента); атомарная фиксация согласия; неизменяемые снимки LeadApprovalSnapshot; BL-4 — конвертация только после подтверждения; сброс подтверждения с сохранением истории; после конвертации запрос → won, его правки и правки вариантов заявку не меняют (ТЗ §6.6 — по построению). Предварительный вариант может быть согласован с явным указанием его предварительного статуса и недостающих данных.

Меняется:

1. **Сценарий предварительного согласования и последующего обновления заявки (Р-3).** Клиент вправе согласовать предварительный вариант с явным перечнем недостающих данных. Когда менеджер получает новые сведения и дополняет заявку, если прежнее согласование уже было зафиксировано, менеджер сначала сбрасывает его с сохранением старого LeadApprovalSnapshot. Затем система формирует новую неизменяемую печатную редакцию заявки и прикрепляет её к заявке. Клиент и менеджер отдельно подтверждают один и тот же файл/редакцию по `revisionId` и `contentHash`. Только после двух подтверждений редакция получает статус «подтверждена сторонами». Подтверждение печатной редакции означает согласие с составом сведений заявки на указанную дату, но само по себе не утверждает изменённую цену или новый вариант расчёта: если пересчёт изменил коммерческие условия, клиент отдельно выбирает/подтверждает актуальный вариант. Любое последующее изменение значимых полей создаёт новую редакцию и требует повторного подтверждения; предыдущие редакции и согласования остаются в истории.
2. Снимок согласования v2: при подтверждении варианта копируются routeSnapshot/cargoSnapshot/calcSnapshot и customsCalculationId — иммутабельно, как коммерческие поля сегодня; у легаси-вариантов — null. Дополнительно фиксируются `isPreliminary`, `missingData`, идентификатор/версия заявки и идентификатор неизменяемой печатной редакции, которую стороны подтверждают (ТЗ §6.4–§6.5).
3. Конвертация: buildOrderQuoteSnapshot расширяется снимками v2 — Order.quoteSnapshot получает маршрут/груз/условия/расчёт именно согласованного варианта.
4. Маршрутные колонки заявки — **Р-6 закрыт правкой №6** (критерий приёмки «печатная форма совпадает с выбранным вариантом» несовместим с альтернативой «всегда из запроса»): колонки Order заполняются из снимка согласованного варианта, если он есть; иначе из запроса (легаси, BL-5). При расхождении «вариант ↔ запрос» ответ конвертации содержит предупреждение optionLeadDivergence — решение менеджера осознанное. Правило «заявка — источник правды» сохраняется: последующие правки запроса/вариантов заявку не меняют. Ревизия печатных форм — в волне 2 (источник колонок меняется только для вариантов со снимками).
5. **Документы — модель «документы следуют за сделкой»** (устранение двусмысленности v1.0, правка №5): собственных документов у варианта нет; документы привязаны к сделке (Document.leadId → Document.orderId) и при конвертации перепривязываются к заявке существующей функцией carryDocumentsToOrder (updateMany: orderId = заявка, leadId = null; счётчик — в событиях lead_converted/order_created) — поведение сохраняется как обязательное; снимки варианта фиксируют только расчётные данные (состав документов на момент расчёта виден в журнале событий запроса). Приёмочный тест сценария 9 проверяет фактический перенос (§14).
6. **Перенос таможенной истории (Р-5).** При конвертации на заявку переносятся версии расчётов, привязанные к согласованному варианту (`quoteOptionId`), и необходимая текущая версия запроса; происхождение отмечается `origin='carried_from_lead'`. Полная история нормативных версий и информационных пересчётов сохраняется и доступна только менеджеру и брокеру в пределах их прав. Клиенту в заявке показывается только актуальный на данный момент результат (предварительная оценка либо окончательные платежи по ДТ, если они внесены), без списка прошлых версий, авторов и истории пересчётов. Перенос не должен раскрывать клиенту внутренние ревизии и служебные комментарии.

## 8. Таможенные расчёты: неизменяемость после фиксации и информационный пересчёт (ТЗ §7; правка №1 D72 + формулировка D73)

Правка №1 владельца (D72): версии действительно неизменяемы после фиксации; пересчёт валюты и исправление ставок — разные операции с разными контрактами. Формулировка D73 фиксирует семантику: фиксация замораживает **нормативные параметры** (коды ТН ВЭД, ставки, характеристики товарных позиций); денежные суммы, валюта и курс предварительных расчётов обязательствами не являются; клиент и менеджер **независимо** выполняют информационный пересчёт; окончательные платежи определяются на дату подачи ДТ. Р-4 закрыт — иммутабельность обязательна, а не дефолт.

1. **Двухслойная модель расчёта (D73).**
   - **Нормативный слой** — то, что фиксирует согласованный расчёт: состав товарных позиций (код ТН ВЭД, ставки — пошлина, доп. пошлина, НДС; характеристики позиций — вес, количество, происхождение), условия расчёта (инкотерм и место, состав начислений), веса и базы, использованные при расчёте.
   - **Денежный (информационный) слой** — расчётные величины, не обязательства: стоимость товара, фрахт/страхование/прочие начисления, курсы и дата курса, таможенная стоимость, суммы платежей по видам, валюта представления. Окончательные обязательства определяются только при декларировании — по применимым правилам и данным на дату подачи ДТ (D41, D73 — §8.6).
   - Изменение нормативного слоя после фиксации — только новой версией (п. 3); денежный слой ни после фиксации, ни после согласования обязательством не становится (п. 5–6).
2. **Фиксация.**
   - Расчёты запроса: фиксируются автоматически при согласовании запроса (переход в client_approved; момент — clientConfirmedAt). Новые версии расчётов запроса, созданные после согласования, считаются зафиксированными с момента создания: после согласования состав расчётов запроса ручными правками не меняется.
   - Расчёты заявки: фиксация — явное действие сотрудника «Зафиксировать расчёт» (новый эндпоинт POST /api/admin/customs-calculations/[id]/finalize; событие customs_calc_finalized). До фиксации текущая версия правится PUT-ом (как сейчас); зафиксированный расчёт печатного приложения не может измениться незаметно.
   - Исторические версии (isCurrent=false) неизменяемы всегда (существующая семантика сохраняется).
3. **После фиксации:** PUT (полная правка состава) → 409 «Расчёт зафиксирован — изменения только новой версией»; исправление ставок/кодов/состава (нормативного слоя) — только POST новой версией (на запросе — до конвертации; после конвертации — на заявке; новая версия создаётся незафиксированной и фиксируется заново). Существующие POST-гарды сохраняются: won → 409 «Запрос конвертирован в заявку — считайте платежи на заявке», lost → 409, заявка cancelled → 409.
4. **Информационный пересчёт — отдельная операция с записью результата** (разделение контрактов, ТЗ §7.2 + D73): POST /api/admin/customs-calculations/[id]/fx-recalc; контракт — **валюта представления** (currency; новый параметр по D73), fxDate и опциональные ручные курсы (только сотрудники); zod-схема strict — поля состава (позиции, ставки, коды ТН ВЭД, инкотерм, фрахт, прочие расходы) в схеме отсутствуют и дают 400. **Результат — не перезапись версии, а новая append-only запись CustomsFxRecalc** (§3): актор и роль (manager/client), валюта представления, дата курса, снимок курсов (manual → курс ЦБ ≤ fxDate → 400 «Курс недоступен — введите вручную», существующая логика), пересчитанные таможенная стоимость и суммы платежей **по зафиксированным ставкам, весам и характеристикам** (чистая функция расчёта в customs-server). Нормативный слой, fxDate/fxRates и суммы самой версии не меняются — пересчёты менеджера и клиента независимы и не перезаписывают друг друга. Доступность: менеджер — на текущей версии (зафиксированной или нет); на запросе — до конвертации, в том числе после фиксации (в этом смысл разделения); после конвертации расчёты запроса полностью заморожены (существующий гард); на заявке — до cancelled. **Клиент** — на зафиксированных расчётах собственной сделки (запрос до конвертации / заявка после; §9, §11): только валюта представления и дата курса, без ручных курсов (недоступный курс → 422 «Курс на выбранную дату недоступен — выберите другую дату»). Событие customs_fx_recalced — с параметрами записи (актор, валюта, дата курса) и ключевыми итогами (каноничные суммы версии → пересчитанные); полная история пересчётов доступна менеджеру и брокеру, клиенту показывается только выбранный/последний актуальный результат без журнала прошлых пересчётов; **priceReviewRequired при пересчёте не выставляется** (D73: денежный слой — не обязательство; §6.5).
5. **Маркировка (D41 + D73).** Подпись «Оценка. Окончательные платежи определяются при декларировании» (D41) остаётся обязательной в UI и печатных формах; в клиентских блоках и печатном приложении актуальные суммы сопровождаются пометкой «предварительный расчёт». В истории менеджера и брокера каждая запись показывается как «информационный пересчёт» с автором, валютой представления и датой курса. Клиенту показывается только актуальный результат без журнала пересчётов — денежный слой нигде не подаётся как согласованное или окончательное обязательство.
6. **Окончательные платежи по ДТ (D73).** По факту декларирования сотрудник вносит на заявке запись «Окончательные платежи по ДТ» (POST /api/admin/orders/[id]/customs-final-payments): дата подачи ДТ, суммы по видам платежей (в валютах уплаты), комментарий; запись — append-only (CustomsFinalPayment, §3): новая запись прежние не меняет, эндпоинтов правки/удаления нет, история сохраняется; событие customs_final_payments_recorded (staff). В кабинете клиента блок виден только после записи — «Окончательные платежи по ДТ от ДД.ММ.ГГГГ»; до этого клиент видит предварительный расчёт с подписью D41 (п. 5). Взаиморасчёты — по курсу на дату оплаты (D41, без изменений).
7. **События-диффы:** customs_calc_saved (PUT/POST) дополняется перечнем изменённых ключей (прецедент buildLeadEditDiff — текстом в description, Activity-диффы не хранятся структурно); новые типы customs_calc_finalized, customs_fx_recalced (параметры записи и ключевые итоги, п. 4) и customs_final_payments_recorded (п. 6) — в event-registry, аудитория staff, без писем (не создавать новый триггер DF-03).
8. **Печатное приложение заявки** читает текущую версию — её состав неизменяем после фиксации, суммы не меняются вовсе (пересчёты живут записями, п. 4); печатный блок выводит признак фиксации и дату курса («зафиксирован ДД.ММ.ГГГГ · курс на ДД.ММ.ГГГГ») и подпись D41 с пометкой «предварительный расчёт» — тихих изменений напечатанных итогов нет, напечатанные суммы предварительными обязательствами не являются.
9. Связь с вариантом (правка №5): CustomsCalculation +quoteOptionId (FK, nullable, индекс) — расчёты, которые велись в контуре конкретного варианта; при согласовании LeadApprovalSnapshot.customsCalculationId фиксирует «какой расчёт был при согласовании»; origin='carried_from_lead' — для версий, перенесённых в заявку по Р-5.
10. UI таможенного контура: кнопки «Зафиксировать расчёт» (до фиксации) и «Пересчитать курс» (открывает форму: валюта представления + дата курса; ручные курсы — только сотрудникам); бейдж «зафиксирован»; список информационных пересчётов текущей версии (актор, валюта, дата курса, ключевые итоги); «Окончательные платежи по ДТ» на заявке (список записей + форма внесения); история версий — как сейчас (строки-сводки архивных версий).

## 10. UI (ТЗ §8)

1. Форма создания/правки варианта — блоками: (1) Исходные данные запроса — автозаполнено, только чтение; (2) Маршрут и транспорт — адаптация маршрута, видов транспорта, промежуточные точки; (3) Характеристики груза — снимок с корректировкой; (4) Коммерческие условия и расчёт — цена, валюта, НДС, срок, ориентир + таблица строк расчёта (статья, наименование, сумма, валюта, курс, сумма в валюте предложения), итог и маржа (сотрудникам), предупреждение расхождения с costEstimate; (5) Внутренняя экономика — себестоимость и её валюта (зона сотрудника, D3); (6) Недостающие сведения и предупреждения — missing, отметка «Требуется актуализация расчёта» (priceReviewRequired), расхождение с запросом.
2. Метки происхождения: «из запроса» / «изменено» на полях блоков 1–3 по sourceFields/editedFields — визуальное различение унаследованного и правленного (ТЗ §8).
3. Карточка запроса: список вариантов с признаками (выбран / предварительный / требует актуализации расчёта / отличается от запроса), «Создать вариант» (источник — запрос), индикатор готовности, бейдж needs_data. При любой правке редактируемых данных заявки клиент и менеджер видят уведомление о необходимости актуализировать все варианты; старые снимки вариантов остаются неизменными.
4. «История варианта» — разворачиваемый список ревизий в карточке варианта для сотрудников: дата, автор, вид (создан/изменён/заполнен из запроса/актуализация расчёта), перечень изменений человекочитаемо (по диффам ревизий). Отметка «Требуется актуализация расчёта» снимается только после новой ревизии с сохранённым пересчётом. История не раскрывает клиенту внутренние расчётные сведения.
5. Таможенный контур (менеджер и брокер в пределах прав; брокер — только по доступным ему сделкам, без доступа к транспортным вариантам/себестоимости/марже): «Зафиксировать расчёт» и «Пересчитать курс» (валюта представления + дата курса — для менеджера), история нормативных версий и информационных пересчётов (актор, роль, валюта, дата курса, ключевые итоги); менеджер дополнительно видит «Окончательные платежи по ДТ» и форму внесения (append-only). Предупреждение «расчёт не зафиксирован» — в контуре печатного приложения. Доступ брокера к этой истории не открывает ему варианты транспортного расчёта, себестоимость или маржу.
6. Кабинет клиента: пометка предварительных расчётов; блок «Зафиксированные условия» и согласование — как сейчас; **блок «Таможенный расчёт (предварительно)»** — только для зафиксированного расчёта собственной сделки: позиции (коды ТН ВЭД, ставки, характеристики), актуальный результат с подписью D41 и пометкой «предварительный расчёт», форма информационного пересчёта (валюта представления + дата курса); клиент видит только текущий результат, без списка прошлых пересчётов и версий; собственный информационный пересчёт D73 доступен; **блок «Окончательные платежи по ДТ»** — после записи сотрудником, показывается актуальный итог; строки расчёта варианта, итоги, маржа и ревизии клиенту не показываются (D3); пожелания к перевозке в анкете — волна 2 (Р-1).
7. Гигиена: компоненты ≤300 строк (RULES 2.14, IC-09) — форма разносится на подкомпоненты (прецедент StageRequirementsDialog).

## 11. Права, безопасность, границы

1. Роли не меняются (ТЗ §10), кроме полномочия, открытого решением владельца (D73): варианты и расчёты создают и правят сотрудники; клиент — выбор/согласование (включая предварительный вариант), редактирование всех разрешённых полей собственной заявки до конвертации/закрытия, подтверждение актуальной печатной редакции и **информационный пересчёт зафиксированного таможенного расчёта собственной сделки**; фиксация таможенных расчётов — сотрудники с правом записи (requireCalcWriter — как сейчас); ручной ввод курсов и запись окончательных платежей по ДТ — только сотрудники.
2. D3: costEstimate/costCurrency, строки расчёта, итоги и маржа — вне клиентских и брокерских проекций; перечень missing — только сотрудникам; в клиентскую проекцию варианта добавляется только isPreliminary; снимки груза — данные самого клиента (его анкета); ревизии — только сотрудникам; таможенный расчёт себестоимости и маржи не содержит, клиентская проекция фиксированного расчёта — белый список (позиции: коды/ставки/характеристики и только актуальный результат); история версий и пересчётов доступна менеджеру и брокеру, но не клиенту; ClientOptionRow расширяется явно, e2e-проверка состава проекций (сценарии 11 и 13).
3. Заморозка кабинета подрядчика (D31) не затрагивается; e2e_contractor_frozen (16/16) — без изменений.
4. Скоупинг: варианты, строки расчёта и ревизии доступны только через запрос и его роуты; клиентский пересчёт — только собственная сделка (скоупинг по lead/order клиента); брокерские проекции вариантов не содержат.

## 13. Решения владельца по Р-1, Р-3 и Р-5 — D75

Решение D75 от 11.11.2026 закрывает Р-1, Р-3 и Р-5. Ниже приведена обязательная нормативная трактовка для реализации; она зафиксирована в `docs/DECISIONS.md`.

| Решение | Указание владельца | Обязательное поведение |
|---|---|---|
| **Р-1 — редактирование заявки после создания вариантов** | Клиент может корректировать все доступные ему данные; после изменения требуется актуализировать варианты | Разрешить редактирование до конвертации/закрытия. Не переписывать снимки вариантов. Все существующие варианты заявки помечать `priceReviewRequired=true` (семантика — актуализация расчёта после любой правки редактируемых данных); клиент и менеджер видят уведомление. Сотрудник актуализирует каждый вариант отдельно; отметка снимается только после сохранения новой ревизии с подтверждённым пересчётом. Если уже есть `client_approved`, сервер автоматически сбрасывает согласование в транзакции изменения с сохранением снимка; после актуализации клиент подтверждает обновлённый вариант и новую редакцию заявки. После `won`/`lost` редактирование запрещено. |
| **Р-3 — согласование предварительного варианта** | Предварительный расчёт можно согласовать; по мере появления данных менеджер дополняет заявку; обновлённая редакция подтверждается клиентом и менеджером | Не блокировать согласование из-за `missingData`. В снимке согласования явно фиксировать предварительность и недостающие данные. Каждая обновлённая редакция заявки после дополнения менеджером формирует неизменяемую печатную форму/документ, прикреплённый к заявке. Клиент и менеджер выполняют отдельные явные действия подтверждения одной и той же версии документа; факт создания/редактирования менеджером сам по себе не считается подтверждением. Сохраняются версия/хеш, акторы, роли, даты и результат подтверждения. Пока нет обоих подтверждений, редакция имеет статус «ожидает подтверждения» и не считается совместно подтверждённой. Новые изменения создают новую редакцию и требуют новых подтверждений; предыдущие редакции и подтверждения остаются в истории. |
| **Р-5 — видимость и перенос истории таможенных расчётов** | Историю расчётов видят только брокер и менеджер; клиент видит итоговый результат на текущий момент | Переносить историю нормативных версий и информационных пересчётов на заказ с сохранением происхождения и связей. Полную историю показывать менеджеру и брокеру в рамках прав. Клиенту показывать только текущий актуальный результат: последнюю информационную оценку и/или окончательные платежи по ДТ, если они внесены; не показывать список прошлых версий, пересчётов и внутреннюю историю. Клиент по D73 может инициировать информационный пересчёт собственной сделки, но видит только его текущий результат; история всех пересчётов остаётся доступной только менеджеру и брокеру. |

**Дополнительные ограничения:**
- Подтверждение печатной редакции заявки — это подтверждение содержания и полноты сведений на конкретную дату, а не превращение предварительной оценки в окончательную цену или окончательные таможенные платежи.
- Согласованный вариант и подтверждённая редакция заявки должны быть связаны с конкретными неизменяемыми версиями. Нельзя подменять файл/содержимое уже подтверждённой редакции.
- Сброс согласования и повторное подтверждение не удаляют предыдущие LeadApprovalSnapshot, редакции печатной формы или события.
- Решения D73 о нормативном слое, информационном денежном слое и окончательных платежах по дате подачи ДТ остаются без изменений.
- Р-1/Р-3/Р-5 закрыты решением D75; волна 2 реализует их как обязательные требования, а не выбирает дефолты. Механизм флага актуализации вариантов и неизменяемости снимков относится к волне 1; разрешение редактирования заявки после появления вариантов и сброс/повторное согласование — к волне 2.

Старт/продолжение работ, миграции и выкат регулируются отдельными разрешениями владельца и действующими правилами проекта; эта редакция плана сама по себе не разрешает изменение БД или Production.

## 14. Тесты и гейты — приёмочные сценарии ТЗ §9 (расширены — правка №6 + D73)

Общий принцип (закрытие замечания №6): **проверяется фактическое совпадение значений, а не наличие структур.** Каждый сценарий переноса/согласования сверяет поля значением-в-значение с выбранным вариантом; наличие quoteSnapshot само по себе тест не закрывает.

| № | Сценарий ТЗ | Уровень | Что сверяется фактически |
|---|---|---|---|
| 1 | Неполный запрос клиентом | e2e | клиентский POST с частичной анкетой; статус `needs_data`; missing виден менеджеру; `new` не выставляется при незаполненных критичных данных |
| 2 | Дополнение → готовность к расчёту | e2e | PATCH клиента/менеджера; lead_edited-дифф; missing пустеет; автоматика needs_data назначает/снимает статус по §6.4; индикатор ready |
| 3 | Два и более вариантов менеджером | e2e | два POST; у каждого свои снимки/строки/ревизии |
| 4 | Автозаполнение каждого варианта из запроса | unit + e2e | buildOptionSnapshots; сверка ПОЛЕЙ: маршрутные колонки и все ключи cargoInfo (включая произвольные) = анкете; sourceFields полон |
| 5 | Разные маршруты и виды транспорта | e2e | overrides route/transportModes/routeStops; editedFields отражает переопределения |
| 6 | Правка одного варианта не влияет на другие | e2e | PATCH opt1 → снимки/строки opt2 и запрос байт-в-байт прежние; у opt1 — ревизия с диффом, у opt2 и запроса ревизий нет |
| 7 | Правка запроса без незаметного изменения вариантов (Р-1) | e2e | клиент PATCH после создания вариантов; все существующие варианты заявки получают `priceReviewRequired=true` при изменении любого редактируемого поля (не только ценозначимого); снимки прежние; уведомление видят клиент и менеджер; история содержит автора и diff; если статус был `client_approved`, согласование атомарно сброшено с сохранением старого снимка; флаг снимается только после фактической актуализации варианта; после `client_approved` требуется сброс и повторное подтверждение |
| 8 | Выбор и согласование предварительного/полного варианта (Р-3) | e2e | select-option → client_approved даже при `isPreliminary=true`; снимок содержит `missingData`, статус предварительности и идентификатор подтверждаемой редакции; расчёты запроса зафиксированы (PUT → 409); предварительный статус не трактуется как окончательная цена |
| 9 | Корректный перенос выбранного варианта в заказ | e2e | convert → сверка: quoteSnapshot (коммерческие + route/cargo/calc) = варианту; колонки Order (города/страны/коды, transportType, readyDate, вес/объём/места, инкотерм) = снимку варианта; **печатная форма**: HTML /admin/orders/[id]/print содержит значения согласованного варианта (города/страны, ТН ВЭД, места, вес, объём, дата готовности, цена, срок) и не содержит значений другого варианта; **документы**: все документы запроса имеют orderId=заявка и leadId=null |
| 10 | Неизменность заказа после последующих изменений запроса | e2e | PATCH запроса/варианта после конвертации → заявку и её печатную форму не меняют (won-гарды) |
| 11 | Разграничение клиентских и внутренних данных | e2e | клиентская проекция без costEstimate/costCurrency/missing/строк расчёта/итогов/ревизий, с isPreliminary; брокерская — без вариантов; снимок согласования без себестоимости |
| 12 | Сохранение истории таможенных расчётов и разграничение видимости (Р-5) | unit + e2e | PUT исторической версии → ошибка; PUT зафиксированной → 409; fx-recalc → новая append-only запись, нормативный слой и версия не меняются; при конвертации история переносится на заказ с `origin='carried_from_lead'`; менеджер и брокер видят историю; клиент видит только актуальный результат и не получает историю версий/пересчётов |
| 13 | Информационный пересчёт — независимость и границы (D73) | unit + e2e | менеджер (валюта A, дата X) и клиент (валюта B, дата Y) пересчитывают независимо → **две записи**, версия и нормативный слой не изменились байт-в-байт; strict-схема: поле состава в payload → 400; клиент: ручной курс → 400, незафиксированный расчёт → 409, чужая сделка → 404, недоступный курс → 422; клиентская проекция — белый список, без себестоимости/маржи/чужих данных (D3) |
| 14 | Маркировка предварительных сумм (D41 + D73) | e2e | кабинет клиента и печатное приложение содержат подпись D41 и пометку «предварительный расчёт»; клиенту показывается только актуальный результат без журнала прошлых пересчётов; менеджеру и брокеру доступна история пересчётов с автором, валютой представления и датой курса; нормативный слой во всех отображениях = зафиксированной версии |
| 15 | Окончательные платежи по ДТ (D73) | e2e | запись сотрудником (дата подачи ДТ, суммы по видам) → событие; история append-only (эндпоинтов правки/удаления нет); у клиента блок «Окончательные платежи по ДТ от …» появляется только после записи; до записи — только предварительный расчёт с подписью D41 |
| 16 | Подтверждение обновлённой редакции заявки обеими сторонами (Р-3) | e2e | менеджер дополняет заявку после предварительного согласования; формируется новая неизменяемая печатная редакция, прикреплённая к заявке; клиент и менеджер отдельно подтверждают один и тот же revision/hash; до обоих подтверждений редакция не считается подтверждённой; подтверждения содержат actor/role/timestamp; изменение после подтверждения создаёт новую редакцию и требует повторного подтверждения; старые редакции и подтверждения сохраняются |

Дополнительно: unit-тесты diffOptionVsLead, completeness, expectedLeadStatus и матрицы переходов, sumOptionCalc (валюты/округление), fxRecalc (чистая часть — результат-запись), CustomsFinalPayment (валидация записей), buildOrderQuoteSnapshot v2, диффы ревизий. Ожидания гейтов: vitest — рост от новых unit; e2e — рост от блока DF-27 (сценарий добавляется в существующий прогон, без новых подъёмов сервера); заморозка 16/16; tsc 0; lint 0; build OK; integrity «новых 0» (docs/INVENTORY.md перегенерировать при новых инструментах); knip — без роста сверх baseline; gitleaks no leaks (имена тестовых фикстур — без high-entropy, урок D70). Точные счётчики фиксируются в отчётах гейтов.

## 15. Риски и меры

| Риск | Вероятность / влияние | Мера |
|---|---|---|
| Дрейф структуры Json-снимков от бланка запроса (cargoInfo — свободный Json) | средняя / среднее | снимок хранит cargoInfo verbatim (полный состав по построению); единая серверная точка сборки; версия структуры v:1; толерантные читатели; unit на состав |
| Объём расчётной модели (строки, валюты, курсы) | средняя / среднее | реестр статей в коде; без кэшируемых агрегатов; sumOptionCalc — чистая функция с unit-тестами; строки не покидают серверные проекции |
| Ревизии растут по объёму | низкая / низкое | хранятся только изменённые ключи (диффы), без снимков целиком; записи — в транзакции правки; удаление — только каскадом с вариантом |
| Расчёт заявки забыли зафиксировать перед печатью | средняя / среднее | предупреждение «не зафиксирован» в контуре печатного приложения; признак фиксации в печатном блоке; состав всё равно меняется только PUT-ом до фиксации, каждое изменение — событие с диффом |
| Информационный пересчёт воспринят как изменение условий (клиентом или менеджером) | средняя / среднее | результат — запись с автором, валютой и датой курса, пометка «информационный пересчёт»; подпись D41 + «предварительный расчёт»; нормативный слой и суммы версии не перезаписываются (байт-в-байт тест сценария 13); priceReviewRequired при пересчёте не включается |
| Клиентский контур пересчёта — новая поверхность | средняя / среднее | только собственная сделка (скоупинг по lead/order), только зафиксированные расчёты, без ручных курсов (недоступный курс → 422 с предложением другой даты), белый список клиентской проекции, e2e-проверка состава (сценарий 13); новые эндпоинты — в замерах e2e, новых подъёмов сервера нет |
| Правки заявки после согласования и подтверждение редакций (Р-1/Р-3) | средняя / высокое | согласование сбрасывается до изменения; каждая редакция неизменяема; двойное подтверждение привязано к revision/hash; история не удаляется |
| Матрица статусов с needs_data | низкая / среднее | единственная детерминированная функция expectedLeadStatus; unit-тесты матрицы + e2e; ручные переходы закрыты; статусы — TEXT без CHECK, легаси-записи совместимы |
| Утечка внутренних данных через новые проекции | низкая / высокое | белые списки полей (прецедент CLIENT_OPTION_FIELDS), типы без поля, e2e-проверка состава (сценарии 11 и 13) |
| Расхождение вариант ↔ запрос при конвертации | средняя / среднее | предупреждение optionLeadDivergence + осознанное решение менеджера; правило «заявка — источник правды» не меняется; приёмочный тест сверяет печать с вариантом |
| Храповики IC/knip и gitleaks | низкая / низкое | INVENTORY перегенерировать; файлы ≤300 строк; ссылки в документах — только на существующие пути (IC-08, урок D61/D70); имена фикстур без high-entropy |
| Событийный шум клиенту | низкая / низкое | новые события (ревизии, фиксация, информационные пересчёты, окончательные платежи) — staff-аудитория; письмо клиенту о предварительном варианте не отправляется (без нового триггера DF-03) |

## 16. Критерий завершения

Из ТЗ §11 — функциональность считается реализованной, когда клиент может сохранить неполный запрос, менеджер может создавать к нему несколько независимо редактируемых вариантов с автоматическим заполнением исходных данных и полноценным расчётом, клиент может выбрать вариант, а менеджер — преобразовать его в заказ с полным сохранением согласованных условий и истории; приёмочные сценарии §14 (фактическое совпадение маршрута, груза, условий, таможенных ставок, печатной формы и переноса документов с выбранным вариантом; актуализация вариантов после правки заявки; согласование предварительного варианта; двойное подтверждение неизменяемой редакции заявки; разграничение истории таможенных расчётов между менеджером/брокером и клиентом; независимость информационных пересчётов без изменения нормативного слоя; корректность окончательных платежей по ДТ) пройдены целиком. Плюс прохождение гейтов обеих волн и приёмка владельцем (§6.1). Существенно: согласование настоящего плана (D75, развитие ранее согласованного v1.2 по D74) само по себе не является стартом реализации; отдельная команда владельца о старте волны 1 была дана ранее и остаётся действующей. Миграции, изменение общей БД и Production deployment регулируются отдельными разрешениями владельца; указания владельца по Р-1/Р-3/Р-5 (§13) реализуются как обязательные требования D75.
