# reference-from-owner — материалы референса TU-01, полученные от владельца

Состав поставки ревизии роадмапа **1.34** (`download/TU02-ROADMAP-REV3/`). Все материалы — **без изменений содержимого**, sha256 зафиксированы; задача приёма и фиксации в проектной документации (`docs/design/reference/tu01/`) — **TU-01.0** роадмапа; замена референса самостоятельной интерпретацией разработчика запрещена; отступления — только вопросы владельцу (реестр отклонений — артефакт TU-G1). Передача макетов не означает автоматического принятия UX/UI-модели владельцем — финальная приёмка отдельно (TU-G2).

## 1. Набор макетов UX Pilot — 12.11.2026 (основной визуальный ориентир TU-01)

Папка `ux-pilot/` (5 файлов — 5 самостоятельных экранов, инвентарь — `ux-pilot/README.md`): Executive DS V2.0 (`Designsystem.png`), Command Center менеджера (`commandcenter.png`), кабинет клиента (`clientcabinet.png`), кабинет брокера (`brockercabinet.png`) и главная страница публичного сайта в тёмной теме (`homedark.png`; ревизия 1.34 — подтверждено владельцем командой «правильный файл», в ревизии 1.33 ошибочно считалась копией брокерского экрана).

Зафиксированные поручением-передачей от 12.11.2026 обязательные требования: Executive Dark — основная тема; Light — альтернативная по предоставленной Design System; согласованные цвета, типографика IBM Plex Sans и IBM Plex Mono, компоненты и состояния; единообразие публичного сайта, кабинета клиента, Command Center и кабинета брокера; кабинет подрядчика не проектируется и не реализуется; бизнес-процессы не меняются; клиенту не раскрываются себестоимость, маржа, внутренние комментарии и полная история таможенных расчётов; заказ не создаётся автоматически после выбора предложения клиентом; создание заказа из согласованной заявки — исключительно действие менеджера; демо-данные заменяются реальными или маркируются тестовыми. Обязательные исправления макетов (без маржи в клиентском интерфейсе; без обещаний реального времени; подтверждение перед преобразованием в заказ; главная публичного сайта отдельно от DS-страницы) — в карточках TU-01.5–TU-01.8 роадмапа 1.34.

## Порядок фиксации (TU-01.0, после TU-G0)

1. Владелец передаёт (при наличии) полноформатные оригиналы LIGHT REBRANDING V2.0 и текст документа TU-01 Frontend Transformation v1.0 файлами (V-2).
2. Агент размещает все принятые материалы — набор UX Pilot, страницы LIGHT REBRANDING V2.0, документ TU-01 Frontend Transformation v1.0 — в `docs/design/reference/tu01/` без изменений содержимого, sha256 каждого файла — в отчёте задачи TU-01.0.
3. BRANDBOOK v2.0 ссылается на референсы как источник истины; токены TU-01.2 — с прослеживаемостью «токен → значение → элемент референса»; отступления — только через реестр отклонений к TU-G1.
4. Значения Design System Executive DS V2.0 совпадают со светлой темой LIGHT REBRANDING V2.0 (Ivory `#FAF3E0`, `#FFFFFF`, акцент `#D95D39`) — коллизии значений не зафиксировано; вопрос заголовочного шрифта (Mont Bold на тёмной странице LIGHT REBRANDING V2.0 vs IBM Plex Sans в поручении и в DS V2.0) остаётся вопросом владельцу в TU-01.2.
5. Особые значения, требующие решения владельца в TU-01.2 (в т. ч. Success-цвет `#2F6A3F` для обеих тем по DS V2.0, поверхностные значения тёмной темы `#1B1B1B`), оформляются вопросами реестра отклонений, не решаются разработчиком самостоятельно (тёмная тема — отдельные семантические токены, не инвертирование).
