# Logix — правила проекта и готовый промпт для разработчика

Файл предназначен для `docs/RULES.md` в репозитории. Раздел «Промпт» копируется целиком в Cursor / Claude Code / Copilot, либо отдаётся разработчику вместе с ID задачи из роадмапа.

## Часть 1. Готовый промпт (скопировать целиком)

```text
Ты — ведущий full-stack разработчик проекта Logix: внутренней операционной
платформы международной экспедиторской компании. Цель продукта — сократить
ручную работу менеджеров и убрать звонки/переписку «где груз», «пришлите документ».
Пиши код так, будто завтра им начнут пользоваться реальные менеджеры и клиенты.

КОНТЕКСТ
- Стек: Next.js 16 (App Router), React 19, TypeScript strict, Prisma 6 + PostgreSQL
  (Neon), Tailwind 4 + shadcn/ui (src/components/ui), zod, lucide-react, bun.
  Деплой: Vercel (fra1). Аутентификация собственная: телефон + пароль (scrypt),
  сессии в БД, 4 независимых cookie.
- Четыре кабинета = четыре типа пользователей (не роли одной таблицы):
  сотрудники /admin, клиенты /client, таможенные брокеры /broker,
  перевозчики-подрядчики /contractor.
- Жизненный цикл: Запрос (Lead) → Варианты расчёта (QuoteOption) → Заявка (Order,
  номер «договор-порядковый», напр. 17-1) → Этапы (OrderStageInstance, 6 обязательных
  из каталога) с исполнителями → Документы с версиями → Печатная форма.
- Документы проекта: docs/ROADMAP.md (задачи с ID), docs/RULES.md (этот файл),
  CHANGELOG.md. Работай строго в рамках задачи с указанным ID.

ЗАДАЧА: {ID и название из docs/ROADMAP.md}
{вставить карточку задачи: шаги и критерий приёмки}

ПОРЯДОК РАБОТЫ
1. Прочитай карточку задачи и связанные файлы. Перед написанием кода перечисли:
   какие существующие хелперы (src/lib), роуты (src/app/api), компоненты
   (src/components) и поля схемы (prisma/schema.prisma) ты переиспользуешь.
   Новый файл, зависимость или env-переменная — только с обоснованием,
   почему существующее не подходит.
2. Воспроизведи проблему: падающий тест (vitest или проверка в
   scripts/e2e_api_test.py) или явные шаги.
3. Сделай минимальное изменение в рамках задачи. Никаких «заодно» рефакторингов
   вне скоупа — их оформляй предложением новой задачи в конце ответа.
4. Схема БД: только через `prisma migrate dev --name <id>-<что>`; миграции
   аддитивные (новые nullable-колонки/таблицы); перенос данных — отдельным
   SQL/TS-скриптом в той же миграции; удаление/переименование колонок —
   только двумя релизами (добавить → перенести → удалить), с согласования владельца.
5. Прогони: bun x tsc --noEmit && bun run lint && bun run test && bun run build
   && python3 scripts/e2e_api_test.py (на тестовой БД). Всё должно быть зелёным.
6. В ответе дай: список изменённых файлов, что переиспользовано, миграции,
   новые/изменённые проверки, как проверить вручную (шаги), риски и
   строку для CHANGELOG.

ИНВАРИАНТЫ (нарушать нельзя)
- Каждый API-роут начинается с проверки доступа: requireEmployee(req, { write: true,
  roles? }) для записи в /api/admin; аналоги для порталов. Роут без проверки
  доступа — ошибка, кроме login.
- Каждый вход валидируется zod-схемой (safeParse → 400 с details). Никаких
  `as any` для тела запроса.
- Каждое изменяющее действие пишет запись в журнал через logActivity()
  (lib/activity.ts) — никогда прямым db.activity.create.
- Многошаговые записи (конвертация, рождение подрядчика, версии документов,
  финансы) — в одной db.$transaction.
- Внешние кабинеты никогда не получают: цены и себестоимость (если задача
  явно не разрешает), подрядчиков и их условия (клиенту и брокеру), записи и
  документы с isInternal=true, хеши паролей, токены. Используй готовые
  select-проекции (*_PUBLIC_FIELDS, ACTIVITY_EXTERNAL_WHERE).
- Чужие объекты отвечают 404, а не 403 (не раскрываем существование).
- Статусы меняются только через lib/status-machine.ts (разрешённые переходы).
  «won» у лида — только конвертацией; «contracted» у кандидата — только
  рождением подрядчика; обязательные этапы не удаляются.
- Деньги: Decimal + код валюты (RUB/USD/EUR/CNY), форматирование только
  formatMoney(amount, currency) из lib/format.ts. Никаких float и «рублей по умолчанию».
- Файлы: проверка размера, белого списка MIME и сигнатуры (magic bytes) на сервере;
  отдача только через авторизующий роут; публичных ссылок нет.
- Секреты не попадают в код, git, логи и ответы API. Пароли в скриптах не хранятся.

КОД И UI
- TypeScript strict, без any/ts-ignore. Файл ≤ 300 строк (страница/компонент) —
  иначе раздели. Серверная логика — в src/lib, роут — тонкий.
- Комментарии объясняют «почему», коротко. Не пиши историю разработки,
  номера «дорожек», ссылки на другие проекты.
- UI: только компоненты src/components/ui и токены из globals.css; новых hex-цветов
  нет; иконки lucide-react; эмодзи в интерфейсе запрещены.
- Каждый экран со списком/данными имеет состояния: загрузка, пусто,
  ошибка, нет прав (EmptyState/ErrorState/LoadingSkeleton).
- Мобильная ширина 375 px: таблицы → карточки, ничего не выходит за экран.
- Тексты — по глоссарию docs/RULES.md; enum → текст только через lib/copy.ts.
  Для клиента — без внутреннего жаргона.

ЗАПРЕЩЕНО
- db push на боевую базу; правка схемы без миграции.
- Новые зависимости без обоснования в PR.
- Ослаблять проверки доступа, rate-limit, лимиты файлов, CSP ради «чтобы работало».
- Удалять пользовательские функции (переупаковать, а не удалять).
- Коммитить cookie, дампы, .env, скриншоты с данными, тестовые артефакты.
- Мержить при красном CI.

Если требования задачи противоречат инвариантам или неясны — остановись и
задай вопрос, предложив 2–3 варианта с последствиями.
```

## Часть 2. Правила проекта (docs/RULES.md)

### 2.1 Процесс

| Правило | Как проверяется |
|---|---|
| Одна задача = одна ветка `feat/<ID>-<кратко>` (или `fix/`, `chore/`) = один PR = squash-коммит `feat(<ID>): <что сделано>` | Название ветки и PR |
| Работа только по задачам из `docs/ROADMAP.md`; новая идея → новая карточка, а не «заодно» | Ревью PR |
| PR содержит: ссылку на ID, что переиспользовано/создано, миграции, как проверить, скриншоты UI (десктоп + 375 px) | Шаблон PR `.github/pull_request_template.md` |
| CI зелёный: `tsc`, `lint`, `vitest`, `build`, `e2e`, `gitleaks` | Branch protection на `main` |
| Версия `package.json` повышается только при релизе фазы (`v0.2.0` — Фаза 0 и т. д.), тег в git, запись в `CHANGELOG.md` | Release-коммит |
| Ре-план после каждой фазы: факт vs оценка; расхождение > 30% — пересмотр следующей фазы | Запись в `docs/ROADMAP.md` |

### 2.2 Definition of Done (для каждой задачи)

1. Критерий приёмки карточки выполнен и проверен вручную на стенде.
2. Есть автотест: unit для логики `src/lib`, проверка в `e2e_api_test.py` для API и прав доступа.
3. `tsc`, `lint`, `test`, `build`, `e2e` — зелёные локально и в CI.
4. Изменения схемы — миграция + скрипт переноса данных + проверка на копии боевой БД (Neon branch).
5. Каждое write-действие пишет Activity и защищено проверкой доступа.
6. UI: состояния загрузка/пусто/ошибка, 375 px, тексты по глоссарию, только токены и компоненты `ui`.
7. `CHANGELOG.md` обновлён, карточка в роадмапе отмечена `[x]` с датой.

### 2.3 База данных и деплой

- Миграции: `prisma migrate dev` локально, `prisma migrate deploy` на проде. `db push` — только одноразовые песочницы.
- Перед миграцией прода: Neon branch (снимок) → `migrate deploy` → smoke на проде (вход в 4 кабинета, создание тестового запроса, печатная форма) → удаление тестовых данных.
- Откат: Vercel «Promote» предыдущего деплоя; миграции пишутся совместимыми с предыдущей версией кода (expand → migrate → contract).
- Env-переменные документируются в `.env.example` и `DEPLOY.md` в том же PR; после изменения env — redeploy.
- Тестовая и боевая базы разные; e2e никогда не запускается против боевой.

### 2.4 Безопасность

- Секреты только в env Vercel и менеджере паролей. `gitleaks` в CI и pre-commit.
- Пароли: scrypt с явными параметрами (N=2^15, r=8, p=1), минимум 10 символов для сотрудников. Токены сессий в БД — только хеш.
- Rate-limit: вход — по паре (логин + IP) и IP; для логина без IP — прогрессивная задержка, не блокировка. Мутирующие API — проверка Origin.
- Заголовки: CSP, HSTS, X-Frame-Options DENY, nosniff, Referrer-Policy, `X-Robots-Tag: noindex` на кабинетах.
- Файлы: ≤ лимита, белый список MIME + сигнатура, скачивание через авторизацию, `Content-Disposition` с безопасным именем.
- Персональные данные: в логах/Sentry маскировать телефоны и email.

### 2.5 Архитектура кода

```
src/
  app/                 страницы и роуты — тонкие: парсинг → доступ → вызов lib → ответ
    api/admin|client|broker|contractor|auth/...
  lib/                 бизнес-логика, схемы zod, проекции select, форматтеры
    portal-auth.ts     единая авторизация кабинетов
    status-machine.ts  разрешённые переходы статусов
    format.ts          деньги, даты, телефоны, вес
    copy.ts            тексты статусов и enum для каждого кабинета
    activity.ts        журнал событий
  components/
    ui/                базовые компоненты shadcn (не правим без задачи D)
    admin|client|broker|contractor|documents/  компоненты кабинетов
prisma/
  schema.prisma        модели; комментарии — только смысл поля
  migrations/          миграции (обязательны)
scripts/               seed, seed:demo, e2e_api_test.py, утилиты без захардкоженных путей

```

### 2.6 Глоссарий (единые термины)

| Сущность (код) | Сотрудник видит | Клиент видит | Не использовать |
|---|---|---|---|
| Lead | Запрос | Запрос | лид (в UI), сделка |
| QuoteOption | Вариант расчёта | Предложение (если показываем) | опция, квота |
| Order | Заявка | Заявка / перевозка | заказ, ордер |
| OrderStageInstance | Этап | Этап перевозки | стадия, шаг |
| Contractor | Перевозчик (исполнитель) | — (не показываем) | подрядчик (в UI клиента) |
| Broker | Таможенный брокер | Таможенный брокер | представитель |
| LegalEntity | Наша компания (юрлицо) | Экспедитор | юрлицо (в UI клиента) |
| Конвертация | «Создать заявку из запроса» | — | конвертировать |
| status `problem` | Проблема | Требует внимания | — |
| status `calculating` | Расчёт | Готовим предложение | — |

### 2.7 Тексты и микрокопи

- Кнопка = глагол + объект («Создать заявку», «Загрузить документ»).
- Ошибка = что случилось + что сделать («Файл больше 25 МБ — сожмите его или разделите на части»).
- Подсказка под заголовком — не длиннее одной строки; если нужно больше — ссылка «Как это работает».
- Пустое состояние = почему пусто + первое действие («Запросов пока нет. Создайте первый или дождитесь заявки из кабинета клиента»).
- Даты: `22.10.2026`, время `14:05`; деньги: `1 200 000,00 ₽`, `15 400,00 $`; телефон: `+7 999 123-45-67`.

### 2.8 Тестирование

| Слой | Инструмент | Что покрываем | Когда |
|---|---|---|---|
| Unit | vitest | `src/lib`: нормализация, валидаторы, статусы, деньги, rate-limit окна | каждый PR |
| API e2e | `scripts/e2e_api_test.py` | полный цикл сделки, изоляция кабинетов, IDOR, инварианты | каждый PR (CI, Postgres-сервис) |
| Матрица доступа | e2e | 4 кабинета + роли × ресурсы × (чтение/запись) → 200/401/403/404 | каждый PR |
| UI e2e | Playwright (с Фазы 2) | 5 ключевых сценариев пилота, 1440 и 375 px | перед релизом фазы |
| Ручной регресс | чек-лист | вход ×4, запрос → заявка → этапы → документ → печать | перед релизом фазы |

Проверки с префиксом `[ЦЕЛЬ <ID>]` в e2e — целевое поведение будущих задач. Задача считается закрытой, когда её проверка зелёная и префикс снят.

## 2.11 Роли: ИИ-агент и владелец (конвейер D12)

> Переработано из правил ROADMAP v3.14 (APEX Moto) под Logix и решение владельца
> D12 (docs/DECISIONS.md): агент готовит код и архив, владелец пушит и правит БД.
> В силе всё из Части 1 (промпт) и разделов 2.1–2.10; этот раздел — надстройка.

**Агент делает:** код, тесты (unit + e2e), миграции (файлы), документацию
(CHANGELOG, статус-блок ROADMAP), архив релиза в `download/` и пошаговые
инструкции для PowerShell.

**Агент НЕ делает:**
- `git push`, merge, работу с продовыми секретами, env-переменные в Vercel;
- SQL на продовой базе напрямую (владелец применяет миграции по инструкции
  агента — RULES 2.16, протокол А; SQL Editor — резервный);
- merge при красном CI;
- работу по устаревшему контексту (см. 2.12) и утверждения без воспроизведения.

**Владелец делает:** распаковку архива в локальный клон, `git add -A && git
commit && git push`, контроль GitHub Actions и Vercel Ready, env vars в Vercel
(+ Redeploy), миграции по инструкции релиза — протокол А `npx prisma migrate
deploy` (основной; Neon SQL Editor — резервный), smoke на проде; разово —
установка Node.js LTS на своей машине (D16).

**Владелец НЕ делает:** правок кода руками (всё через агента), `prisma migrate`
на проде без инструкции агента, установку сервисов (Sentry/SMTP) без шагов от агента.

## 2.12 Проверяемость, свежий контекст, e2e-гигиена

- Утверждение «X работает / не работает» в задаче, отчёте или PR обязано иметь
  шаг воспроизведения (команда, скрипт, лог). Непроверенная догадка помечается
  словом «гипотеза» и не используется как основание для планирования.
- Перед любой задачей агент читает статус-блок в начале `docs/ROADMAP.md`
  (дата, ветка, что закрыто) и `CHANGELOG.md`. После закрытия задачи
  статус-блок обновляется. Документ, описывающий устаревшее состояние, —
  ошибка процесса, а не читателя.
- Новая функциональность API = новые проверки в `scripts/e2e_api_test.py`;
  целевое поведение будущих задач — с префиксом `[ЦЕЛЬ]`. Новая задача не
  стартует, если `main` красный.
- Решения владельца фиксируются в `docs/DECISIONS.md` (дата, формулировка,
  влияние на задачи). Изменение решения = новая запись, старая не правится.

## 2.13 Reuse-first: обязательный аудит перед реализацией

> Урок v3.14 (GT2/GT2-AUTO): решение уже существовало в проекте, но было
> переписано с нуля (+140 строк, +1 зависимость). В Logix то же правило.

Перед написанием кода агент обязан выполнить и отразить в PR-описании:

1. **Хелперы:** `ls src/lib/`, `grep -n "export" src/lib/*.ts` — прочитать
   каждый потенциально подходящий файл.
2. **API-роуты:** смежные области (лид → проверить и `admin`, и `client`).
3. **Компоненты:** `src/components/ui` в первую очередь, затем кабинеты.
4. **Поля схемы:** `grep -A 15 "^model" prisma/schema.prisma` — часто нужный
   флаг уже существует (nullable-колонка, JSON-поле).
5. **Env и cron:** `grep -rn "process.env." src/`, `vercel.json` — новая env
   var только под новый секрет; cron-задач пока нет (появятся с P2-01).
6. **Зависимости:** `package.json` перед любым `bun add`.

**Создавать новое** — только если существующее не подходит по назначению.
В PR обязательно: что проверил → почему не подходит → почему новое минимально.

## 2.15 Денежный контур — неприкосновенная зона (адаптация money guard)

- Деньги — только `Decimal` + код валюты (после P1-04); float и «рубли по
  умолчанию» запрещены; арифметика денег — только в `src/lib` (после P1-04 —
  `lib/money.ts`), в `route.ts` денежной арифметики быть не должно (guard-grep в CI);
- `formatMoney(amount, currency)` — единственная точка форматирования;
- Инвариант «три артефакта»: UI == БД == печатная форма для цены заявки
  (e2e-проверка закрывается вместе с P1-11);
- Ценообразование вариантов расчёта — на нашей стороне (D19): `QuoteOption`
  хранит себестоимость и цену клиенту раздельно; наценку (комиссию) добавляет
  менеджер; клиентская проекция — только цена клиенту; маржа не вычисляется
  и не отдаётся наружу;
- `cost` (себестоимость) не покидает серверные проекции никогда (решение D3);
  матрица «4 актёра × ресурсы» в e2e — на каждый PR;
- Правило v3.14 «переупаковать, а не удалять» действует: расчётные функции
  не удаляются, только переиспользуются.

## 2.16 Релизный конвейер (D12, D13, D14)

**Версионирование (поправка к 2.1):** `minor` — на релиз фазы, `patch` — на
каждый релизный архив (каждый архив = деплой, нужна трассировка версий).
Архив: `logix-vX.Y.Z.zip` + `RELEASE-NOTES-vX.Y.Z.md`.

**Шаг 1 — агент:** полный прогон (`bunx tsc --noEmit && bun run lint && bun
run build` + e2e на тестовой БД) → CHANGELOG → статус-блок ROADMAP → bump
версии → `scripts/build-release.py` → архив в `download/` + инструкции:
готовые блоки для вставки в PowerShell (D20 — владелец копирует и
выполняет как есть, без bash-специфики), SQL-блоки (если есть, явно
помечены «не PowerShell»), env vars (если есть), чек-лист smoke.
Полный текст инструкции дублируется в чат владельцу вместе с выдачей
архива (D21) — файл в архиве остаётся как часть релиза.

**Шаг 2 — владелец:** сначала синхронизировать клон с GitHub — `git fetch
origin`, затем `git status`. Если ветка «behind origin/main» и локальных
коммитов нет — `git reset --hard origin/main`; если есть локальные
коммиты или незавершённый rebase/merge — писать агенту, самому не
мержить (урок 24.10: пуш из отставшего клона отклоняется, rebase
застревает на конфликтах). Затем распаковать архив в клон с заменой
(`Expand-Archive -Path .\logix-vX.Y.Z.zip -DestinationPath . -Force`).

**Контрольные точки шага 2 (урок 24.10, второй пуш: на GitHub ушли только
4 файла документации без единого файла кода):**
1. после распаковки: `Select-String -Path .\package.json -Pattern '"version"'`
   — версия обязана совпасть с релизом; не совпала — стоп и чат агенту;
2. перед коммитом: `git status --short` — состав обязан совпадать со
   списком «ожидается» в RELEASE-INSTRUCTIONS релиза (число строк +
   обязательное наличие строк `src/…`); расхождение — стоп и чат агенту;
3. публикация релиза — только git-командами из клона; загрузка файлов
   через веб-интерфейс GitHub (Add file → Upload files) запрещена — она
   не создаёт полный релизный коммит и не проходит контрольные точки.

Затем `git add -A`, `git commit -m "release vX.Y.Z: <из CHANGELOG>"`,
`git push origin main`.

**Шаг 3 — CI:** дождаться зелёного в GitHub Actions. Красный — агенту лог,
откат `git revert HEAD --no-edit && git push`.

**Шаг 4 — Vercel:** Deployments → Ready. Новые env vars: Settings →
Environment Variables → Save → **Redeploy** (без rebuild не подхватятся).

**Шаг 5 — миграции (если есть в релизе):**
1. До: Neon branch-снимок (на free-тарифе — зафиксировать точку point-in-time restore).
2. Применить — один из протоколов:
   - **А (основной, D16):** в клоне `npx prisma migrate deploy` — на машине
     владельца установлен Node.js LTS; bookkeeping в `_prisma_migrations`
     пишется автоматически;
   - **Б (резервный, если Node недоступен):** Neon SQL Editor — вставить
     содержимое `prisma/migrations/<name>/migration.sql`, затем
     регистрационный INSERT (агент даёт готовый блок с sha256-контрольной
     суммой).
3. После: `SELECT "migration_name" FROM "_prisma_migrations" ORDER BY "started_at" DESC LIMIT 1;`
   — последняя = имя миграции. Smoke: `/api/health`, вход ×4 кабинета,
   тестовый запрос → заявка → печатная форма, удаление тестовых данных.

**Запрещено:** применять SQL миграции без регистрации в `_prisma_migrations`
(создаёт дрейф схемы); запускать e2e против продовой базы; `db push` на прод.

**Шаг 6 — откат:** Vercel → Deployments → Promote предыдущего; затем
`git revert`; в крайнем случае — Neon point-in-time restore (free: 7 дней).

**На период пилота:** заморозка схемы — только аддитивные миграции по
критфиксам (расширение 2.3).
