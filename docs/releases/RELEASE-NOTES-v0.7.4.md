# RELEASE-NOTES v0.7.4 — DF-06: подсказка статуса заявки по этапам

Карточка DF-06 (🟡 0.5 д, зависимость DF-05 закрыта в 0.7.2/0.7.3). Проблема карточки: верхнеуровневый статус заявки ставится вручную и расходится с этапами — цифры списков и раздела «Требует внимания» недостоверны. Решение — подсказка-действие в карточке заявки: **статусная машина, ручной Select статуса и роут PATCH не менялись**, новых API нет.

## Правило подсказки

Чистая функция `suggestOrderStatus(stages, current)` — `src/lib/status-suggest.ts`, без серверных зависимостей (реюз матрицы `ORDER_TRANSITIONS` и `TERMINAL_ORDER_STATUSES` из `lib/status-machine.ts`):

- **«Все этапы завершены — завершить заявку?»** — все этапы в `done` И переход разрешён матрицей (только из «В работе»). Кнопка «Завершить заявку» применяет существующий `PATCH status=completed`; готовность обязательных этапов, как и раньше, проверяет роут (`getIncompleteMandatoryStages`) — при полном done-покрытии проходит без перекрытия.
- **«Работа началась — перевести в „В работе“?»** — есть этап в `in_progress | done | problem`, а заявка в «Расчёте» или «Согласовании» (из обоих переход в «В работе» разрешён). Кнопка применяет `PATCH status=in_progress`.
- **Иначе подсказки нет** — ручное управление не меняется, лишнего UI не появляется.
- **Терминальные статусы («Завершена»/«Отменена») подсказок не получают.** Матрица формально пускает их в «В работе», но роут требует мастера и причину — это осознанный возврат, а не шаг «в одно нажатие»; подсказка для менеджера дала бы 403. Выявлено тест-матрицей, подавление через `TERMINAL_ORDER_STATUSES`.
- **Лестница для «застывшей» заявки**: этапы завершены, а статус застрял в «Расчёте» → сначала подсказка «В работе», после применения — «Завершить заявку» (подсказка считается на рендере, пересчёты не нужны).

## UI

- Новый компонент `src/components/admin/order/StatusSuggestion.tsx`: muted-строка «иконка + вопрос + outline-кнопка», состояние `applying` со спиннером, скрытие при отсутствии подсказки. Видна только сотрудникам (страница `/admin` за проверкой доступа). Нейтральный muted без красного — подсказка не сигнал о проблеме (§3.3 брендбука v1.3); токены, lucide-иконки, `flex-wrap` для 375 px.
- Интеграция — одна точка в шапке карточки заявки (после блока ответственного); страница заявки осталась ровно в лимите 300 строк (компонент вынесен в отдельный файл — RULES 2.14/IC-09).
- Применение подсказки — существующий PATCH с валидацией zod, матрицей переходов, ролями и записью в журнал; тост и перезагрузка карточки — прежний `patchOrder`. Новых API нет — e2e-дополнений не требуется (RULES 2.12: новая функциональность API = новые проверки).

## Решения внутри реализации (зафиксированы, чтобы не «всплывали»)

1. **Подсказка ≠ автоматика** — этапы статус не диктуют (принцип P1-05 сохранён): функция только предлагает, применяет менеджер.
2. **«Все этапы завершены» = каждый этап заявки в `done`** — обязательность здесь не различается: если все завершены, то и обязательные завершены; неполное покрытие обязательных ловит роут (409 со списком) — это прежний контракт.
3. **«Работа началась» = `in_progress | done | problem`** — этап с проблемой тоже означает, что заявка уже не «Расчёт» (проблема ставится на идущей работе).
4. **Тексты — из формулировок карточки DF-06**, статусы — только из словаря `ORDER_STATUS_LABELS` (глоссарий RULES 2.6).
5. **Заморозка D31 не затронута**: файлы только в `src/lib` и `src/components/admin`, кабинет подрядчика не упоминается, уведомлений нет.
