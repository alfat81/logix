# RELEASE-NOTES v0.7.3 — D45: невыбранный расчёт — плашка менеджеру через 2 рабочих дня

**Закрытие открытого вопроса DF-05** (отчёт 0.7.2, RELEASE-NOTES-v0.7.2, вариант (б)). Решение владельца зафиксировано записью **D45** в `docs/DECISIONS.md`: «Если есть несколько расчетов и ни один не выбран, надо повесить плашку у менеджера через 2 рабочих дня, с целью уточнить видел ли клиент расчет и о дальнейших действиях».

## Правило

- **Состояние.** На запросе **≥2 варианта расчёта** (QuoteOption) и **выбранного нет** (`isSelected`) → `waitingOnKind = client`, `waitingReason = awaiting_client_choice`, `waitingOnId = customerId`. Клиент сообщает выбор менеджеру **вне системы** (как и раньше — действий клиента в системе нет); фиксирует менеджер (PATCH `/api/admin/options/[id]`, событие в транзакции пересчитывает ожидание).
- **Эскалация.** Выбор не сделан **2 рабочих дня** (пн–пт по МСК) → менеджеру плашка-действие:
  - в бейдже карточки/шапки: «Ждёт: клиента · N дн. — уточнить расчёт», в tooltip — «Уточнить, видел ли клиент расчёт, и согласовать дальнейшие действия»;
  - в секции «Ждут дольше N часов» на «Требует внимания»: строка запроса с этим текстом-действием (попадает по рабочим дням — раньше общего порога часов).
- **До пороги** — обычное «Ждёт: клиента · N ч» (мяч у клиента — честное состояние), красным не подсвечивается: красный сигнал — только просрочка/проблема (§3.3 брендбука v1.3).
- **Снятие.** Менеджер выбирает вариант → событие → пересчёт → ожидание и строка из секции исчезают в той же транзакции.

## Решения внутри реализации (зафиксированы, чтобы не «всплывали»)

1. **«Несколько» = ≥2** — по букве D45. **Один вариант без выбора правилом не покрыт** (осознанная неполнота, тест фиксирует): если нужно покрыть и один — правка одной константы, отдельным решением владельца.
2. **Якорь отсчёта** — `waitingSince` состояния «варианты есть, выбора нет»: ставится пересчётом в момент события, создавшего состояние (создание варианта, оценка брокера); после деплоя для существующих запросов — момент запуска backfill (если он запускается; без backfill — первый пересчёт по событию сделки).
3. **Рабочие дни** — пн–пт по МСК (UTC+3 без DST), гранулярность MSK-день: «через 2 рабочих дня» = 00:00 МСК второго рабочего дня после якоря (пт → во вторник). **Гос. праздники РФ не учитываются** — допущение D45: без справочника праздников правило консервативно (плашка не раньше срока). Справочник можно добавить отдельной задачей без смены контрактов.
4. **Состояние не зависит от времени** — правило выдаёт `client/awaiting_client_choice` сразу; порог 2 р.д. — свойство ОТОБРАЖЕНИЯ (бейдж/секция внимания вычисляются на рендере). Это устраняет классическую проблему time-based правил: не нужен крон для переключения состояния, «мяч» не устаревает.
5. **Приоритеты сохранены**: нет описания/проформы (`awaiting_proforma`) и нет вариантов (`no_quote`) срабатывают раньше правила 4. В `WAITING_CLIENT_LABELS` новый код не добавлялся: waiting запроса наружу не отдаётся (клиент выбирает вне системы).
6. **Заморозка D31 не затронута**: перевозчик (подрядчик) в правиле не участвует, кабинет не открывается, уведомлений/загрузок от подрядчика нет — только видимые сотрудникам бейдж и строка секции.
7. **IC-09**: сборка секции внимания вынесена из роута (322 > 300 строк) в чистый `src/lib/attention-waiting.ts` — тип `WaitingLongAttention`, `buildWaitingLong` (SQL-срез роута 24 ч шире точного фильтра по рабочим дням, «не дозревшие» строки отбрасываются).
