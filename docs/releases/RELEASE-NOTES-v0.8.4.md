# RELEASE-NOTES v0.8.4 — DF-12 «Виды документов, статус „финальный", привязка к этапу» (03.11.2026)

Закрыта карточка DF-12 очереди фазы DF (зависимости DF-01, DF-11 — обе закрыты). Документы получают вид по D5 вместо свободного «типа», жизненный цикл с финальным статусом и обязательной причиной возврата, привязка к этапу — колонка-задел. Это фундамент следующей задачи DF-13 «Пакет документов по заявке» (слоты по видам) и DF-14 «Чек-листы по этапам». В релизе одна миграция (additive + backfill), новых env и зависимостей нет.

## Что сделано

1. **Справочник видов `DOCUMENT_KINDS` (D5)** — 15 кодов с подписями: заявки (`client_request`, `contractor_request`), расчёт (`proforma_invoice`, `goods_description`), контракт и коммерческий набор (`foreign_trade_contract`, `commercial_invoice`, `packing_list`), перевозочные (`bill_of_lading`, `cmr`, `awb`), таможенные (`customs_declaration`, `permit_document`), контур подрядчика (`contractor_agreement`, `contractor_rates`), `other`. Паспортов в списке нет (D5). Группы по фазам сделки — «Расчёт → Оформление и перевозка → Заявки и договоры → Прочее» (`DOCUMENT_KIND_GROUPS`): порядок виден в форме загрузки, фазовая группировка переиспользуется слотами DF-13. Виды контура подрядчика **всегда внутренние**: сервер гасит `isInternal:false` от сотрудника, UI фиксирует видимость «Только сотрудникам» (задел DF-15).
2. **Схема `df_12_document_lifecycle` (additive):** `Document.kind String?`, `status String @default("draft")` (`draft|in_review|final`), снимок финализации `finalizedAt/finalizedByName/finalVersion Int?`, `stageCode String?` — колонка expand, точка записи приходит с UI-привязкой в DF-13/DF-14 (карточка допускала такой expand-шаг; колонка задокументирована в роадмапе). Удалений нет — совместимо с кодом 0.8.3.
3. **Backfill вида — в той же миграции** (карточка): `invoice→commercial_invoice`, `customs→customs_declaration`, `application→client_request`, `permit→permit_document`; `contract` — по признаку видимости: внутренний → `contractor_agreement` (в интерфейсе «внутренний договор» всегда означал договор с подрядчиком), внешний → `other` («чей это договор» по данным прод-базы не определить — документов единицы, владельцу виден вид в карточке, при необходимости правим точечно); остальные → `other`.
4. **Легаси-окно (expand → migrate → contract):** колонка `type` остаётся NOT NULL и пишется **производной** от вида (`LEGACY_TYPE_FOR_KIND`), поле `type` в теле загрузки принимается как алиас (`legacyKindFromType`: ветку contract разбирает легаси-намерение `isInternal`). Старые клиенты API и существующие проверки работают без правок. Запись в DEPRECATIONS: удаление — contract-релиз 0.9.0 (вместе с `fileData`).
5. **Жизненный цикл.** Топология — в единой точке `lib/status-machine.ts` (`DOCUMENT_TRANSITIONS`): `draft|in_review → final`, `final → in_review`. Финализирует только сотрудник — `POST /api/admin/documents/[id]/finalize` (клиент/брокер на админ-роуте получают 401; правило карточки «клиент не может финализировать» закрыто архитектурой кабинетов). Финальная версия = текущая на момент нажатия; снимок пишется в документ (`finalizedAt/By/Version`). Повторное нажатие — 400 «Статус уже: Финальный»; документ без подтверждённых версий финализировать нельзя (409). Новая версия поверх финала — **409 всем трём кабинетам** (гард дважды: быстрый отказ и повторная проверка внутри транзакции против гонки с одновременной финализацией). Единственный путь — «Вернуть в работу»: `POST …/reopen`, причина обязательна (400 без неё), статус → `in_review`, причина уходит в журнал сделки.
6. **События** `document_finalized` и `document_reopened` — в той же транзакции, что и смена статуса (DoD 9); аудитория — `documentEventAudience(isInternal)` (внутренний документ не раскрывает факт существования), уведомлений нет — переход виден всем адресатам в ленте (§8). Код `document_uploaded` из карточки реализован существующим `document_created` — переименование типа события переписало бы историю БД (reuse-first, IC).
7. **UI.** Форма загрузки: выбор **вида** вместо свободного типа — группы с подписями (SelectGroup). Карточка документа (единая `DocumentsSection` на три кабинета): статус-бейдж по брендбуку §3.2 — «Черновик» (нейтральный), «На проверке» (движение), «Финальный» с замком (успех) — маппинг `DOCUMENT_BADGE_VARIANTS`; кнопки «Финальный» / «Вернуть в работу» (диалог с обязательной причиной) — только у сотрудников (`lifecycleUrlFor` передают LeadCard и OrderSidePanel); кнопка «Новая версия» скрыта у финального; под карточкой — строка «Финальная версия vN · кто · когда».
