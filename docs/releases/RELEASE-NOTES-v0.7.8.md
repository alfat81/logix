## Что сделано (по пунктам карточки)

### 1. Меню администратора (G1)
- Состав меню вынесен в **единый источник** `src/components/admin/nav-config.ts`: сайдбар (md+) и новая нижняя панель телефона читают ОДИН список — рассинхрон навигации невозможен по построению.
- Гард-тест `nav-config.test.ts` (5 кейсов): запрещены навсегда несуществующие разделы наброска **«Котировки», «Мониторинг», «Перевозчики», «Лиды»** (и по подстроке), зафиксирован обязательный состав реальных разделов (Пульс, Заявки, Запросы, Клиенты, Брокеры, Подрядчики, Справочники, Настройки + существующие Договоры/Юрлица/Этапы/Сотрудники/Журнал отправок/Главная — все пункты существуют, несуществующих нет), маршруты уникальны, masterOnly-фильтр работает.
- **Бейдж «Заявки» и табы статусов — один источник:** `src/lib/order-counts.ts` (`orderStatusCounts()` — одна форма groupBy для layout и API списка; чистая `activeOrdersTotal()`, 5 unit-кейсов). Раньше layout считал `db.order.count`, роут — свой groupBy: определения групп совпадали, но равенство не было доказуемым. Теперь e2e сверяет число бейджа в SSR (`data-nav-badge="/admin/orders"` — новый локатор) с суммой активных табов API.

### 2. Карточка заявки в списке
- Строка под степпером переименована: **«Ближайший этап: …»** (было «Сейчас: …») — формулировка макета; исполнитель и план в строке сохранены (колонки Ж4 не потеряны).
- Один статус-тег (как и было), плашка **«Ждёт: …»** (DF-05) на месте; красный только у срочного: сплошной красный тег у статусов заявок отсутствует (§3.2/§3.3 v1.3), просрочка — Brick-строка с иконкой.

### 3. Правая панель заявки (320 px) — вкладки
Новый `src/components/admin/order/OrderSidePanel.tsx`:
- Заголовок **«Заявка № N»** — тот же `order.number` из того же GET, что и шапка страницы/крошки: рассинхрон номеров невозможен (проблема наброска «номер в панели не совпадает» устранена по построению).
- Вкладки **«События | Документы | Расчёт»** — реюз `ListTabs` (эталон табов v0.4.0), липкие под шапкой на прокрутке. Чата и «AI Assistant» нет (запрет карточки). «Расчёт» скрыт у отменённой заявки (как и секция раньше).
- **«События»:** лента журнала — у каждой записи человек и компания (проекция DF-02A при чтении, «Имя (Компания)») и метка видимости **«видно клиенту» / «внутреннее»** — носитель `audience` события (DF-01), бейджи нейтральные (глаз/замок, без красного). Внизу — заметка с переключателем **«внутренняя / видна клиенту»** (см. ниже).
- **«Документы»:** существующий документооборот (`DocumentsSection`) — версии, авторы, метки видимости, «+ Добавить» в заголовке секции. Статусы документов (DF-12) и блок «Ожидается» с разрешительными (DF-16) — со своими карточками; **заглушек с выдуманными данными нет** (правило инкрементальности карточки).
- **«Расчёт»:** DF-19 закрыт — вкладка содержательная с первого дня. Для ширины 320 px у компонентов расчёта добавлен проп `compact` (`CustomsCalcScreen/Form/Result/FxInputs/AllocationSelects/ItemsEditor`): вьюпортные сетки `sm:/lg:` в узкой панели заменяются одно-колоночными, строки итогов ТН ВЭД — стопкой «код + пары поле:значение». Реюз компонентов, без копий (IC-14); широкая форма на карточке запроса не менялась.

### 4. Заметка «видна клиенту» — петля видимости замкнута
- `POST /api/admin/orders|leads/[id]/notes` принимает `visibleToClient` (zod, опционально — контракт старых клиентов формы не сломан): аудитория `['staff']` → `['staff','client']`; `isInternal` в ответе — производная аудитории (`lib/activity.ts`), колонок БД не потребовалось (носитель видимости — `audience`, инвариант df_03_contract сохранён).
- Клиент реально **видит** адресованную заметку: GET клиентских заявок/запросов теперь отдаёт журнал (`eventWhereFor('client')`, имена актёров — ридер клиента DF-02A: коллеги по имени, чужие — компания); в карточках клиента — секция «Журнал событий» (тот же `ActivityFeed`, без служебных меток). Брокеру заметка не отдаётся (его аудитория 'broker'), кабинет подрядчика заморожен (D31).
- Внутренние события и заметки клиенту по-прежнему не видны — e2e-регресс сохранён и расширен (каждое событие клиентской ленты обязано иметь 'client' в audience).

Контенту — нижний отступ (pb-20), футер на мобильных скрыт.
- Карточка заявки/запроса — полноэкранный «лист деталей» с кнопкой **«Назад»** (md:hidden, ведёт в список).
- **Фильтры списка не обрезают подписи:** на ширинах < xl (1280) фильтры «Откуда/Куда/Тип» свёрнуты под кнопку «Фильтры» (в раскрытой панели поля на всю ширину), на xl+ — видны сразу; «Ответственный: все/Мои/Без ответственного» — всегда видимы (по макету).

## Отступления от наброска (макеты PNG отсутствуют)
Каталог `docs/design/mockups/` пуст (только .gitkeep) — по карточке построено по брендбуку v1.3 и текстовым описаниям UXPILOT-BRIEF §3.1/§4.1. Осознанные отступления:
1. **Панель с вкладками — на карточке заявки, а не на списке.** Набросок рисует один экран «список + панель» (master-detail); приложение с v0.3.x живёт в двухэкранной навигации (список → отдельная карточка), панель 320 px на карточке — установленный паттерн (P1-18/P1-19, карточка лида). Перенос панели на список = переделка навигации, не входящая в карточку.
2. **«Липкая основная кнопка»** листа деталей: реализована как липкие вкладки панели + «+ Добавить» в заголовке «Документов»; фиксированная нижняя кнопка «+ Добавить документ» из макета 02-orders-mobile — это DF-12 (статусы документов), придёт со своей карточкой.
3. **Состав меню** — реальный (существующие разделы), а не точный список наброска: пункты Договоры/Юрлица/Этапы/Сотрудники/Журнал отправок/Главная существуют и удалены быть не могут (G1: сверка с существующими пунктами).
