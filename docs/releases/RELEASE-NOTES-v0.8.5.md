# RELEASE-NOTES v0.8.5 — DF-13 «Пакет документов по заявке + скачивание архивом» (03.11.2026)

Закрыта карточка DF-13 очереди фазы DF (зависимость DF-12 — закрыта, прод-смоук принят 03.11.2026). Раздел «Документы» заявки стал пакетом слотов: видно, какой вид документа на какой стадии и чего не хватает; финальные документы скачиваются одним архивом — критерий приёмки Г3 выполнен. Миграций, env-переменных и изменений схемы НЕТ; зависимость одна — `fflate` (разрешена роадмапом для DF-13).

## Что сделано

1. **Слоты пакета.** Строки по видам документов D5 × статус «Нет / Черновик / На проверке / Финальный»; статус слота — худший из документов вида (несколько BL/CMR мультимодальной перевозки допустимы). У каждого слота подсказка «кто предоставляет» — статичные дефолты до DF-14 (`DOCUMENT_KIND_PROVIDERS`): клиент — проформа-инвойс, описание товара, внешнеторговый контракт, инвойс и упаковочный лист от продавца, заявка клиента (D35); брокер — декларация и разрешительный контур; сотрудник — перевозочные BL/CMR/AWB (документы перевозчика вносит менеджер — формулировка DF-14) и внутренний контур подрядчика; «Прочее» — без фиксированного владельца. Слоты сгруппированы по фазам сделки DF-12 и рендерятся всегда — «Нет» это полноценная строка с кнопкой «Загрузить» (чек-лист пакета, а не пустой экран).
2. **Аудитория.** Сотрудник видит все 15 слотов с внутренним контуром; клиенту и брокеру подрядческие виды не показываются вовсе — их документы всегда внутренние (DF-15), сам факт строки раскрывал бы внутренний контур. Владение заявкой по кабинету: клиент — своя заявка, брокер — связь OrderBroker, чужая — 404 (факт существования не раскрываем).
3. **API:** `GET /api/{admin|client|broker}/orders/[id]/package` — слоты с документами (списочные проекции, авторы версий по DF-02A) и `orderNumber`; `GET …/package/zip` — архив финальных. Роуты — auth-guard и вызов общего ядра; резолв владения и видимость — в `lib/document-package-server.ts`.
4. **«Скачать финальные документы» — ZIP одним действием.** Только документы со статусом `final`, видимые данной аудитории; версия — снимок `finalVersion`. Структура внутри архива — `<номер заявки>/<вид>-<название>-v<версия>.<расширение>`; имена санитизируются и транслитерируются (кириллица → латиница ГОСТ-подобно с сохранением регистра, «Инвойс №1» → `Invoys-1`), чтобы архив открывался на любой машине без битой кириллицы. Архив собирается `fflate` на store-уровне (pdf/офис/картинки уже сжаты — пересжатие только тратило бы CPU); байты читаются из хранилища по размеру из метаданных (DF-11) либо из БД для легаси-версий.
5. **Порог ответа Vercel (проверка из карточки).** Serverless-функция отдаёт максимум 4,5 МБ тела ответа — константа `PACKAGE_ZIP_MAX_TOTAL_BYTES = 4 МиБ` с запасом. Пакет больше порога: тот же роут отвечает JSON-списком ссылок на отдельные файлы (каждая — существующий авторизующий роут версий, 302 на presigned GET) с пояснением; интерфейс показывает диалог «скачайте по одному». Пустой финальный пакет — 400 с внятным текстом, кнопка на пустом пакете задизейблена.
6. **UI.** Новый `DocumentsPackageSection` — один компонент на три кабинета: группы фаз, слоты с бейджами §3.2 («ФИНАЛЬНЫЙ» с замком, «Нет» — нейтральный), «Загрузить» в слоте открывает диалог загрузки с уже выбранным видом, «Скачать финальные» в шапке. Карточка документа вынесена в общий part `DocumentCard` — плоский список на лидах и слоты на заявке рендерят один и тот же элемент (версии, скачивание, «Новая версия», жизненный цикл, удаление — без изменений). Лиды остаются плоским списком: пакет живёт только на заявках.
