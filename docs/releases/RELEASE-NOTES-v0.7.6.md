# RELEASE-NOTES v0.7.6 — DF-08: Ежедневная сводка владельцу (30.10.2026)

Версия 0.7.6 (patch, RULES 2.16). База — v0.7.5. **Миграций нет, новых env нет, новых зависимостей нет** (окна и пояс — настройки реестра DF-00D, зарегистрированные заранее). Кабинет подрядчика не затронут (D31).

## Что сделано

Письмо `type=digest` мастеру раз в сутки, чтобы узнать обстановку без входа в систему (зависимость Г1 от того, что владелец открыл Пульс): цифры блока 1 Пульса, топ-5 «тормозящих» заявок, число неотправленных писем, ссылка на Пульс. Пустой день — письмо всё равно («Существенных изменений нет» — владелец знает, что система жива). Запуск — ходом существующего диспетчера DF-03 (`POST /api/internal/notifications/dispatch`, Bearer `CRON_SECRET`), новых cron и эндпоинтов нет.

- **Содержимое письма** (текстовый шаблон, как все письма DF-03): `Показатели:` — новых запросов за 24 ч, активных заявок (в пути), ждут дольше порога (`waiting.attention_hours`), этапов с проблемой; `Тормозят:` — топ-5 заявок с самым старым мячом по всем группам, формат строки «заявка №17-3 — ООО Ромашка — мяч у клиента · 2 дн.» (заголовки — те же `PULSE_KIND_TITLES`, что в блоке 3 Пульса); `Неотправленных писем: N` — одно число по карточке (очередь `pending` + неудачные `failed`; детально — журнал отправок DF-04); `Открыть Пульс: {APP_BASE_URL}/admin/pulse` (APP_BASE_URL не задан — письмо валидно без ссылки, как и остальные письма).
- **Окно отправки** — диапазон [start, end] в поясе `notifications.timezone` (дефолт `Europe/Moscow`, O-6); границы — настройки `owner_digest.window_start`/`window_end` (дефолт 09:00–10:00). Решение — чистая функция `ownerDigestDecision`: внутри окна — отправить; пропущенное окно (сервис недоступен) не молчит до завтра — сводка уходит ближайшим проходом после end, всё равно одна за сутки; до окна — ожидание; «уже отправлено сегодня» — пропуск. Невалидная пара (end ≤ start или мусор) — откат на дефолты реестра (не литералы: дефолт реестра меняется — откат меняется с ним).
- **Идемпотентность** — `dedupKey = ownerdigest:{employeeId}:{yyyy-mm-dd}` (уникальный индекс `Notification.dedupKey`): повторный вызов в тот же день письма не создаёт; гонка двух диспетчеров гасится P2002 (тот же приём, что в digest.ts DF-03). Дата — календарная в поясе рассылок (`nowInZone` из windows.ts DF-03, своих вычислений пояса нет). `windowKey = owner:{дата}` — намеренно НЕ начинается с даты: `digest.ts` считает лимит regular-дайджестов получателя по префиксу даты — сводка владельца не занимает слоты обычных писем.
- **Адресаты** — активные сотрудники с ролью `master` и email (мастера без email пропускаются; менеджеру сводка не уходит — проверено e2e). Письмо собирается ОДИН раз на проход диспетчера (цифры общие), создаётся по строке на мастера; созданное письмо уходит этой же пачкой (`type='digest'` забирается `claimBatch` — отправка fake/Resend без изменений).
- **Отказоустойчивость**: сбой сводки не валит проход диспетчера (лог + cron повторит через 5 минут, как с курсами ЦБ); в ответе диспетчера — новое поле `ownerDigests` (создано писем за проход), старые поля без изменений.
- **Reuse-first (G1/IC-14)**: сборка блоков 1–3 Пульса вынесена из роута в `src/lib/pulse-db.ts` (`loadPulseCore`) — сводка и экран используют ОДНУ выборку активных заявок с этапами: числа письма и Пульса сходятся по построению, а не повторным SQL. Возраст мяча — общий с плашкой «Ждёт: …» форматтер `formatWaitingHours` (`lib/waiting.ts`; `WaitingBadge` переведён на него, тексты «N ч»/«N дн.» без изменений). Подвал письма и база ссылок — существующие `renderFooter`/`readAppBaseUrl` (templates.ts). Гард DF-01 (events-guard) дополнен третьей легитимной точкой записи очереди — `lib/notifications/owner-digest.ts` (по образцу enqueue/digest).

## Решения по реализации (не требуют записи в DECISIONS.md)

- **Пропущенное окно** — сводка уходит ближайшим проходом после `window_end` того же дня (не переносится на завтра): карточка требует «владелец знает, что система жива», дедуп гарантирует одну за сутки; при работающем планировщике (GitHub Actions каждые 5 минут) письмо уходит практически в `window_start`, критерий «в окне 09:00–10:00» выполняется.
- **«Не отправлено»** — pending + failed одним числом (формулировка карточки); pending — письма, ещё ожидающие отправки/окна, failed — исчерпавшие повторы; разбивка — в журнале отправок DF-04.
- **Топ-5** — глобальный порядок по `waitingSince` между группами (внутри групп `groupSlowingOrders` уже отсортировал), независимо от kind: письмо показывает самые «застарелые» мячи.
- **Разрешительные (DF-16)** в письмо не входят — их карточка ещё не реализована; точка расширения помечена в модуле (как в digest.ts для блока «ждём от вас»).
- **Мастер без email** — сводка ему не создаётся (письмо не по чему доставить); адрес — человек, не фолбэк компании: сводка персональная, получатель — владелец.
