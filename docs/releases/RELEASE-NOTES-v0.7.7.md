## Что случилось

Первый прогон репозитория в GitHub Actions (ci.yml) — красный: `owner-digest.test.ts` — «письмо создаётся один раз за сутки: повторный вызов — дедуп», `expected 2 to be 1` на ПЕРВОМ же вызове `processOwnerDigest()`. Локально тест стабильно зелёный.

## Разбор (без правок прода — поведение корректно)

- `processOwnerDigest()` сканирует ГЛОБАЛЬНО всех активных сотрудников с ролью `master` и email — это правильное продовое поведение диспетчера (сводка — каждому мастеру, дедуп — свой ключ на мастера).
- vitest гоняет 26 тест-файлов ПАРАЛЛЕЛЬНО по одной БД. `participants.test.ts` (DF-02B) держит в фикстуре активного мастера С email (`master{RUN}@test.ru`) всё время жизни файла. Если проход сводки совпал с жизнью этой фикстуры — чужой мастер тоже получал письмо: `sent = 2`. На локальной машине тайминги не совпадали, на раннере — совпали.
- Ошибка в САМОМ тесте: утверждение глобального счётчика (`first.sent == 1`, `second.sent == 0`) — счётчик включает чужих мастеров, попавших в тот же проход. Это нарушало конвенцию репо: утверждения скоупятся своими получателями (прецеденты в notifications.test.ts:384 и :498 — «остатки e2e не в счёт»).

## Что сделано

- `first.sent` — `toBeGreaterThan(0)`: наш мастер гарантированно получает письмо (окно в beforeAll ставится вокруг текущего времени пояса, дедуп-строки нашего случайного `ownerId` в чистой БД нет).
- Состав, адрес, тема/тело письма — как и было, по `dedupKey startsWith ownerdigest:{ownerId}:`.
- Дедуп доказывается СИЛЬНЕЕ прежнего: после повторного прохода у нашего мастера по-прежнему ровно одна строка, и это то же самое письмо (`after[0].id === rows[0].id`).
- Счётчик второго прохода не утверждается осознанно (между проходами могли появиться чужие мастера других файлов); комментарий в тесте фиксирует урок.
- Остальные два интеграционных теста без изменений: «окно в будущее» остался на `sent == 0` (окно глобально — чужие мастера тоже ждут), «менеджеру не уходит» скоупен своим ключом с самого начала.

## Решения по реализации (не требуют записи в DECISIONS.md)

- **Не изолировать БД на файл** (`fileParallelism: false`): сериализация замедляет конвейер и маскирует класс проблемы — правильнее держать конвенцию «глобальные счётчики глобальных сканов не утверждать»; параллельный прогон продолжает ловить такие места.
- **Фикстуру participants.test.ts не трогаем**: активный мастер с email — легитимные данные для проверки участников; один тест с глобальным сканом обязан быть устойчивым к чужим строкам, а не все остальные — под него.
- **Прод не менялся**: глобальный скан — корректное поведение (в бою мастеров мало и они реальные); дедуп по `dedupKey` гарантирует «одна сводка за сутки НА мастера» — карточка DF-08 выполняется.
