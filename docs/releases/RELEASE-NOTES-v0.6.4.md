# Release Notes v0.6.4 — DF-02 «Участники сделки»

Дата: 28.10.2026 · Оценка карточки: 1 д · Зависимости: DF-01 (v0.6.0), DF-02A (v0.6.2)

## Что изменилось

**Проблема.** «Кто в сделке» определялся тремя способами (`customerId`, `OrderBroker`/`LeadBroker`, `contractorId` этапа), и каждый роут собирал участников сам. Перед DF-03 (очередь уведомлений) правилу «кому писать» нужна единая точка правды.

**Решение.** `src/lib/participants.ts` — единственная функция сборки участников сделки:

- `participantsOf(tx, { orderId | leadId })` → `{ staff, client, brokers, contractors }`:
  - **staff** — активный ответственный менеджер (`Lead/Order.assignee`); при его отсутствии или деактивации — все активные мастера (кастодины системы);
  - **client** — компания-заказчик и её активные пользователи кабинета (DF-02A); неактивная компания остаётся в составе участников (реквизиты), но адресатов не имеет — деактивация закрывает доступ целиком;
  - **brokers** — подключённые брокеры (`OrderBroker`/`LeadBroker`) и их активные пользователи; не подключённый брокер участником не является;
  - **contractors** — исполнители этапов заявки, СПРАВОЧНО для сотрудников: письма подрядчикам не отправляются (замороженный кабинет D31), в адресаты они не попадают никогда (юнит-тест закрепляет).
- `recipientsOfCustomer(customerId)` — получатели клиента: активные пользователи компании с email (адресат-человек, DF-02A); если ни у одного активного пользователя email нет — фолбэк на общий адрес компании (`Customer.email`). Единственная точка изменения получателей после пересмотра P1-07.

**Контактные email у сотрудника и компании брокера.** Проверка по карточке (`rg "email" prisma/schema.prisma`): у `Customer`/`CustomerUser`/`BrokerUser` email был, у `Employee` и `Broker` — нет. Добавлены nullable `Employee.email` и `Broker.email` (миграция `df_02_contact_email`, expand), поля «Email для уведомлений» в формах создания/правки обоих справочников, строка в карточках, поле в API-ответах. Правила валидации — как в DF-02A (`resolveEmail`): непустое значение обязано быть адресом (`isEmail`), мусор — 400, `null` в PATCH — очистить, отсутствие — не менять.

## Границы релиза

- **Ни один существующий роут не переведён на `participantsOf`** — по карточке новый код (DF-03+) обязан собирать адресатов только через модуль; существующие точки видимости (аудитории событий DF-01) не трогались.
- `recipientsOfBroker` не создавался — не входит в карточку DF-02; при потребности DF-03 добавляется рядом по тому же образцу.

## Схема данных (expand, миграция `df_02_contact_email`)

```sql
ALTER TABLE "Broker" ADD COLUMN "email" TEXT;
ALTER TABLE "Employee" ADD COLUMN "email" TEXT;
```

Обе колонки nullable — **старый код v0.6.3 работает с новой схемой без изменений** (откат деплоя не требует действий с БД).
