Вторая волна единого центра документов (основание: команда владельца D61 «Принимаю гейт 1; разрешаю DF-26, волну 2»; гейт 2 прогнан целиком и сдан на приёмку отчётом `DF26-WAVE2-GATE2-REPORT-v1.0.md` — D62; передача пакета по запросу владельца на архив — D63; приёмка гейта 2 (§6.1 п. 4) и production deployment (§6.1 п. 5) — отдельные команды). В релизе **одна миграция** `20261107120000_df_26_docs_center` — additive (3 новые таблицы + 10 nullable-колонок и `bindingState` у `PermitRequirement` + 4 снимковые колонки; удаления и правки существующих колонок нет), совместима с кодом 0.8.6. Env-переменных и новых зависимостей НЕТ. Номер 0.9.0 занят этим релизом (Р-4: назначен при упаковке; 0.9.1 — резерв при раздельном выкате).

## Что сделано

1. **«Загрузка ≠ принятие» (SPEC v1.6 §5.4).** Загрузка по разрешительному → строка «НА ПРОВЕРКЕ» (`submitted`) вместо немедленного «ПОЛУЧЕН»; событие `permit_submitted` ответственному. Решение принимает сотрудник: «Принять» — с привязкой `acceptedVersion` к фактически принятой версии, «Отклонить» — с обязательной причиной (строка возвращается в «ОЖИДАЕТСЯ», контроль возобновляется, документ остаётся в заявке). Повторное решение — 409; чужая сделка — 404. После авто-возврата — подпись «ранее принята версия N (кто, дата)».
2. **Автоматика жизненного цикла.** Финализация документа закрывает и `submitted`-требования автоматически (`acceptedVersion` = финальная версия, «принят автоматически»); новая версия поверх принятого или «Вернуть в работу» возвращает в «НА ПРОВЕРКЕ» только ранее принятые требования (§6.4 п. 4, событие `permit_reopened`).
3. **Дифф-сохранение оценки брокера (§5.7 п. 0а ред. 1.6).** PUT оценки — обновление/создание/удаление строк по `id` (вместо полной замены с remap по коду); чужой/дубль `id` — 400 (контракт D35: `EstimateDiffError.statusCode`); ответ несёт `id` строк. Смена кода сохранённой строки — строки и история не переносятся, авто-запись «ТРЕБУЕТ ПЕРЕСМОТРА»; удалённая позиция → требования «ТРЕБУЕТ РУЧНОЙ ПРИВЯЗКИ» (`pending_manual`, ссылка заморожена, событие); ручная привязка сотрудником — выбор актуальной строки или осознанное «ко всей сделке»; авто-расширение области требования запрещено.
4. **Контур проверок ТН ВЭД (§5.1–5.3).** При появлении кода — auto-запись «ТРЕБУЕТ УТОЧНЕНИЯ» с охватом позиций (физическая дедупликация: CHECK «ровно одна цель», частичные уникальные индексы открытых записей с `NULLS NOT DISTINCT`, UNIQUE пары «проверка — позиция» — 23505 → объединение); «Требуется/Не требуется» — сотрудник и брокер (без основания — 400); пересмотр с решениями по каждому требованию (waived/replace/new/mixed), повторный пересмотр — 409, требования создаются по охваченным позициям без дублей. Инварианты проверены конкурентными тестами на реальной PostgreSQL 16.4 (Р-3).
5. **Блокировка этапа по требованиям.** Завершение/смена этапа блокируется не только чек-листом документов, но и требованиями `pending|submitted` своего `stageCode` (409 перечисляет и документы, и требования); обход — только мастер с комментарием в журнал (StageOverrideDialog; менеджер — 403).
6. **Напоминания и сводки.** Настройка `permits.warn_days_before` (дефолт 7) — усиленная нейтральная плашка «до срока N дн.» (без красного и без писем); скан просрочки не трогает «НА ПРОВЕРКЕ»; сводка панели — «на проверке» отделено от «не готово» (§3.4); Пульс — submittedPermits по сделкам/этапам; дайджест владельца — «документов ждут проверки».
7. **Двойные исторические снимки (§6.1).** События аудита (+9 типов) и бэкафил снимков `Activity`/`DocumentVersion` — «кто + от имени какой компании» на момент действия; переименование профиля больше не переписывает историю; легаси без снимка — честный NULL.
8. **UI.** Строки «НА ПРОВЕРКЕ» с кнопками «Принять/Отклонить/Править» (десктоп 99×32 по макету 10; мобильный 375 — кнопка 99×44, протокол гейта 1 Р-2 закрыт), строки проверок «ТРЕБУЕТ УТОЧНЕНИЯ»/«ТРЕБУЕТ ПЕРЕСМОТРА»/история пересмотра, метка «ТРЕБУЕТ ПРИВЯЗКИ», фильтр «Разрешительные» включает требования по стадиям; пакетный роут + `checks`/`stagePhase`/`bindingState` (staff)/`warnDaysBefore`.

## Известные ограничения (не в этом релизе)

- `acceptedVersion` бэкафилится только для исторических `received` с единственной готовой версией документа (честная деградация §10.3); при следующем принятии заполняется.
- knip на гейте 2 — BLOCKED (окружение песочницы); при упаковке прогон выполнен — 37=37 после устранения 8 находок.
- Кабинет подрядчика остаётся замороженным (D31) — 3 e2e-FAIL вне объёма.
- Почтовый контур на песочнице проверен с `EMAIL_PROVIDER=fake`; на реальном SMTP-провайдере — контроль по чек-листу §13.1 при выкате (№23).
