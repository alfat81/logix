## Замечание 1 — подрядчик: полное исключение из тестирования CI

- Из `.github/workflows/ci.yml` удалены шаги «Сквозной тест заморозки D31 — кабинет подрядчика отвечает 404» и «Проверки заморозки (кабинет 404, база подрядчиков живёт)»: перезапуск сервера с отдельными env + 16 проверок заморозки (обращения к кабинетным эндпоинтам подрядчика и к базе подрядчиков) прекращены как **косвенное тестирование подрядческих сущностей и процессов**.
- Скрипт заморозки `e2e_contractor_frozen.py` удалён из репозитория.
- Заморозка кабинета подрядчика (D31) держится как и прежде кодом: `src/proxy.ts` отвечает 404 на все пути `/contractor/**`, `/api/contractor/**`, `/api/auth/contractor/**` до любой логики при `CONTRACTOR_PORTAL_ENABLED=false` (флаг в e2e-job сохранён); статическими проверками IC-02 (гард аутентификации у каждого роута) и IC-03 (write-роуты) и компиляцией. Бизнес-функции кабинета не проверяются, кабинет не размораживается, код кабинета не тронут.
- В основном e2e (`scripts/e2e_api_test.py`) рождение подрядчика демотировано в **безымянную фикстуру данных** для менеджерских проверок (назначение исполнителя на этап — «Не заморожено» по D31/FROZEN.md; правило 7 ожиданий; внутренние документы DF-15). Проверки-сценарии «кандидат-подрядчик» и «подрядчик рождён» удалены из прогона (−2), обращений к кабинетным эндпоинтам в e2e нет. `docs/FROZEN.md` синхронизирован.
- **Diff CI:** e2e-job состоит из шагов «Версии тулчейна → Миграции → Сид → Сборка → Запуск приложения → Сквозной API-тест → Лог приложения при падении»; подрядческих шагов и упоминаний заморозки нет. Перечень реально запускаемых сценариев — в отчёте `DF27-WAVE2-GATE2-REPORT-v1.1.md` (§«Замечание 1»).

## Замечание 2 — конкурентность Р-1: гонка «PATCH лида ↔ конвертация» закрыта

- **`src/lib/lead-patch.ts` (менеджерский PATCH):** пакетная транзакция заменена интерактивной. Первым оператором — блокировка строки `SELECT id FROM "Lead" WHERE id = … FOR UPDATE` (тот же паттерн, что в convert-роуте с К-01/К-06), затем повторные проверки состояния **под блокировкой**: won → 409 «уже конвертирован»; окно правки анкеты Р-1 (validateLeadAnketaEdit по свежей строке); явный переход статуса — матрица заново; автомат статуса §6.4 и ценозначимые ключи — пересчёт по свежей строке. События журнала пишутся по заблокированному состоянию (актуальному на момент коммита).
- **`src/lib/client-lead-patch.ts` (кабинет клиента):** внутри существующей интерактивной транзакции — та же блокировка строки и повторная проверка окна правки (менеджер мог конвертировать запрос между чтением и записью); diff, слияние анкеты, автомат статуса и сброс согласования пересчитываются по свежей строке.
- Конвертация уже держала блокировку и перепроверяла состояние (волна 1, К-01/К-06) — теперь все три операции сериализуются на строке лида: проигравшая видит состояние-после победителя и отвечает 409; правка анкеты на сконвертированном/закрытом запросе невозможна физически; флаги актуализации не выставляются сконвертированному.
- **Конкурентные e2e-тесты:** **К-11** — клиентский PATCH (Р-1) ↔ конвертация, 3 круга; **К-12** — менеджерский PATCH ↔ конвертация, 3 круга. Инварианты каждого круга: ровно одна из двух операций успешна; если конвертация выиграла — PATCH 409 и правка не применена (вес, флаги вариантов, статус won); если правка выиграла — конвертация 409 (согласие сброшено), правка применена, флаги актуализации выставлены, заявок нет; 5xx нет.

## Замечание 3 — миграция: анализ каскадов + read-only контроль (без применения)

- Влияние `ON DELETE CASCADE` на исторические редакции (`LeadPrintRevision`), подтверждения (`LeadPrintRevisionConfirmation`) и таможенные расчёты (`CustomsCalculation` + `CustomsFxRecalc`/`CustomsFinalPayment`) проанализировано по фактическим FK миграции `df_27_approval_and_customs` и прежних миграций — таблица в отчёте v1.1 (§«Замечание 3»). Итог: три новых FK — SET NULL (строки истории сохраняются, обнуляется только ссылка); четыре каскадные цепочки достижимы только через мастер-only удаление лида целиком (DELETE лида 409-гардом запрещён для конвертированных; Order и CustomsCalculation через API не удаляются вовсе); при конвертации история расчётов переносится на заявку (origin=`carried_from_lead`), не удаляется.
- Владельцу передан **read-only контрольный запрос** `CONTROL-QUERY-DF27-MIGRATION-READONLY.sql` (NEON SQL Editor, транзакция `BEGIN TRANSACTION READ ONLY`): статус миграции в `_prisma_migrations`, существование объектов волны 2, фактические `delete_rule` по всем затронутым FK, счётчики исторических таблиц и проверка сирот.
- Миграция `df_27_approval_and_customs` **в этой поставке не применялась** и применяется только владельцем по протоколу А с отдельного разрешения. Дополнительных миграций и изменений общей БД нет.
