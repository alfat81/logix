# RELEASE-NOTES v0.6.1 — DF-00D «Настройки системы: минимум хардкода» (27.10.2026)

Дата: 27.10.2026. Задача: DF-00D «Настройки системы: минимум хардкода»
(карточка — `docs/ROADMAP-DEALFLOW.md` §7, директива D32, инвариант 9).
Версия: 0.6.1 (patch — RULES 2.16; в очереди §6 стояла оценка 0.5.4,
фактический patch назначен как следующий свободный после v0.6.0).
Миграция БД: **есть** (`20261027094403_df_00d_settings`, additive — одна
новая таблица).

## Для пользователя

Мастер получает раздел **«Настройки»** в админ-панели: 17 бизнес-параметров
в 7 группах (часы рассылок, часовой пояс, лимиты писем, пороги ожидания и
разрешительных документов, лимит размера файла, название и подпись
компании, адрес ответа на письма). Изменение значения действует сразу,
без выката; каждое фактическое изменение записывается в журнал событий
(`setting_changed`, аудитория staff, «старое → новое», без секретов).
Менеджер раздела не видит и по API получает 403 — настройки внутренняя
кухня системы. Секреты и адреса инфраструктуры (ключи, DATABASE_URL,
домены) по-прежнему только в переменных окружения — в настройки они не
попадают по правилу выбора места (D32).

## Что сделано

### Схема данных (expand, без ломающих изменений)

- Модель `Setting`: `key` (первичный ключ), `value` Json, `updatedAt`,
  `updatedByName`. Имя изменившего — снимком строки, без FK (история
  живёт дольше справочников). Миграция `df_00d_settings` — одна таблица,
  никаких ссылок на остальные; существующие данные не трогаются.
- **Пустая таблица легитимна**: `getSetting` откатывается на значение по
  умолчанию — система полностью работает до первого изменения владельцем.
- `Activity.type` — строка, поэтому событие `setting_changed` добавлено в
  реестры (`ACTIVITY_TYPES`/`EVENT_TYPES`, аудитория `staff`) без
  миграции журнала.

### `src/lib/settings.ts` — реестр и доступ (единая точка)

- Типизированный реестр `SETTINGS` — 17 ключей карточки DF-00D в 7
  группах: у каждого ключа подпись, подсказка, тип редактора (`uiType`),
  значение по умолчанию и валидатор. Типы `SettingKey`/`SettingsValues`
  выводятся компилятором — потребитель не кастует вручную. Свободные
  ключи закрыты: `getSettingDef` бросает ошибку на незнакомом ключе.
- `getSetting(key)` — короткий кэш ≤ 60 с (технический параметр чтения —
  константа с обоснованием в комментарии, не настройка) и откат на
  дефолт.
- `setSetting(key, value, actor, tx)` — валидатор → no-op по
  **эффективному** значению (строка БД, а без неё дефолт — не плодим
  строки и события без фактического изменения) → upsert → сброс кэша →
  `emitEvent('setting_changed')`. Всё в одной транзакции: откат записи
  откатывает и событие (покрыто интеграционным тестом на живой БД).
- `resetSetting` — «Сбросить» на экране: строка удаляется, возврат к
  дефолту, событие; сброс отсутствующей строки — no-op без события.

### `src/lib/settings-validators.ts` — валидаторы значений

10 валидаторов: время ЧЧ:ММ (00:00–23:59), список времён, IANA-пояс
(Mars/Olympus отклоняются), целые с границами, непустая строка,
опциональная строка, список строк с ограничениями, белый список
(`staff_mode`), email, коды из реестра событий. Каждый **нормализует**
значение (trim, сортировка, дедуп) — «16:00, 09:00» эквивалентно
отсортированному варианту и не создаёт ложного «изменения». Вынесены в
отдельный файл ради лимита 300 строк (RULES 2.14); единая точка импорта
остаётся `settings.ts` (реэкспорт `SettingValidationError`).

### Экран `/admin/settings` и API `/api/admin/settings` (мастер-only)

- Экран: группы с подписями; у каждой настройки — подпись, подсказка,
  «По умолчанию: …», «Изменено: …»; редакторы по типу (время, список
  времён, число, строка, многострочный текст, список строк через
  запятую); «Сохранить» (активна только при изменениях) и «Сбросить».
  По брендбуку §1–§5: токены, без новых hex; пункт меню «Настройки» —
  только мастеру.
- API: GET — реестр с эффективными значениями (`isModified`,
  `updatedByName`); PATCH — изменение (неверный ввод → 400 с сообщением
  валидатора; свободный ключ → 400); DELETE — сброс на дефолт. Раздел
  мастер-only ЦЕЛИКОМ: менеджеру 403, анониму 401 (API — единственная
  защита, экран — удобство).
- Рендер панели **общий** (по реестру, без вшитых ключей) — новый ключ
  реестра автоматически появляется на экране; гардируется IC-15.

## Миграция

`20261027094403_df_00d_settings` — только добавление: `CREATE TABLE
"Setting"` с заголовком-комментарием и индексом первичного ключа.
Таблица создаётся пустой и на работу существующего кода не влияет
(читают её только настройки, значения — с откатом на дефолт). Откат
совместим: старый код v0.6.0 таблицу не знает и не трогает. Дрейф схемы
проверяется пустым выводом
`npx prisma@6 migrate diff --from-url "<direct>" --to-schema-datamodel prisma/schema.prisma`.

## Кандидаты переноса констант (по мере касания, не «заодно»)

- `DOC_FILE_MAX_BYTES` (4 МБ, `src/lib/document-constants.ts`) → ключ
  `files.max_mb` уже в реестре с дефолтом 25; фактический перенос — при
  касании файловой логики (DF-11), о чём подсказка настройки говорит
  явно. Дублирующих констант не возникло — записи в DEPRECATIONS.md не
  требуются.
- Окна/лимиты рассылок в коде отсутствуют и не появятся до DF-03 —
  DF-03 обязана читать их из реестра (IC-15 будет красным иначе).

## Риски

- Ошибочная настройка (например, пустой список окон) останавливает
  письма — mitigировано валидаторами, дефолтами при пустой таблице и
  событием в журнале (§9 роадмапа); проверка «не сломать рассылки
  настройкой» — обязанность DF-03/DF-08 при чтении ключей.
- Кэш ≤ 60 с: изменение настройки уже сбрасывает кэш ключа немедленно;
  TTL — страховка для внешних правок, которых не должно быть (прямой
  writeSetting мимо setSetting ловит IC-15).
- Квота Neon CU ~80/100, сброс 1 ноября: миграция (одна таблица) и
  приёмка тратят единицы CU, риска нет.
- Раздел мастер-only: у менеджера пункт меню скрыт и API отвечает 403 —
  e2e покрывает оба слоя.
