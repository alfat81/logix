# RELEASE-NOTES v0.7.13 — DF-09 «Двухфакторный вход для мастера» (31.10.2026)

Версия 0.7.13 (patch, RULES 2.16). База — v0.7.12. **Миграция одна** (`20261030214826_df_09_totp`, additive — 3 nullable-колонки `Employee` + новая таблица `TotpRecoveryCode`, backfill не требуется), **env одна новая** (`TOTP_ENCRYPTION_KEY`), **новых зависимостей нет** (карточка: TOTP на `node:crypto`). Заморозка D31 не затронута. До включения TOTP конкретным сотрудником прод-поведение не меняется: без `TOTP_ENCRYPTION_KEY` обычный вход работает как раньше, TOTP-пути честно отвечают 503 (fail closed).

## Что сделано

- **Ядро TOTP** (`src/lib/totp.ts`, без зависимостей): base32 (RFC 4648), HOTP (RFC 4226, HMAC-SHA1, динамическое усечение), TOTP 30 с/6 цифр с окном проверки ±1 шаг, `otpauth://` URI (параметры SHA1/6/30 явно), генератор кодов восстановления `XXXX-XXXX` (алфавит без I/L/O и 0/1). Корректность — эталонные векторы RFC 4226 в unit-тестах (755224/254676/520489).
- **QR** (`src/lib/qr.ts`, чистый энкодер ISO 18004 — без зависимости): байтовый режим, уровень M, версии 1–8, выбор маски по штрафу, SVG с тихой зоной 4 модуля; цвет — токен `currentColor` (IC-09 без hex). Машинная верификация: 5/5 матриц декодируются zxing-cpp в песочнице с точным совпадением текста, включая границы ёмкости v4 (62 байта)/v8 (152 байта) и кириллицу. В UI QR дублируется секретом текстом — ручной ввод в приложение-аутентификатор работает всегда.
- **Крипто-контур** (`src/lib/totp-crypto.ts`): ключи из env `TOTP_ENCRYPTION_KEY` (scrypt, кэш на процесс). Секрет хранится как `v1:<iv>:<ct>:<tag>` — AES-256-GCM с **AAD = id сотрудника**: шифротекст привязан к учётке, подмена между аккаунтами не расшифровывается (vitest). Критерий приёмки карточки «дамп БД без ключа не даёт секретов» выполняется по построению: в колонке нет ни открытого base32, ни хеша. Challenge второго шага — HMAC-SHA256, срок 5 минут.
- **Схема**: `Employee.totpSecret` / `totpEnabledAt` / `totpLastStep` + таблица `TotpRecoveryCode` (только sha256-хеши). Повтор кода шага ≤ последнего принятого отклонён (RFC 6238 §5.2). Одноразовость кода восстановления — атомарный `updateMany` по `usedAt: null` (гонка двух одновременных входов не списывает код дважды).
- **Вход** (`src/app/api/auth/employee/login/route.ts` + новый `.../login/totp/route.ts`): у сотрудника с включённым TOTP верный пароль возвращает `{ totpRequired: true, challenge }` **без сессии**; успех в аудит и сессия — только после кода. Второй шаг: подпись/срок challenge → guard `login-guard` (тот же ключ «телефон+IP» — «смена двери не даёт новых попыток») → учётка → код (6 цифр — TOTP, иначе код восстановления). Неверный код — провал в `LoginAttempt`: перебор второго шага замедляется так же, как перебор пароля. Формулировки ошибок не раскрывают вид кода.
- **Профиль** (новая страница `/admin/profile`, компоненты `ProfileTotpSection` / `ProfileSessionsSection`): статус; включение (QR + секрет текстом + код из приложения); одноразовый показ 10 кодов восстановления; выключение с подтверждением паролем; «Выйти на всех устройствах» — удаляет ВСЕ `EmployeeSession`, включая текущую. Доступна мастеру и менеджеру (карточка: manager — по желанию). Ссылка — в юзер-блоке сайдбара и иконкой в шапке телефона; в `nav-config` сознательно не входит (состав меню зафиксирован гард-тестом DF-21).
- **События** `totp_enabled` / `totp_disabled` (реестр DF-01, аудитория `staff`, без писем) — в транзакции включения/выключения. IC-03 дополнен делегированием `enableTotp(`/`disableTotp(` по прецеденту `setSetting` (DF-00D); чекер прокомментирован.

## Решения по реализации (не требуют записи в DECISIONS.md)

- **Профиль вне меню** — по гард-тесту DF-21 (состав меню утверждён наброском); доступ через юзер-блок — стандартный паттерн личных настроек, периметр «Профиль» не сделочный.
- **`totpLastStep` добавлен к карточке** (в ней не упомянут): без него успешный код принимался бы повторно в пределах того же 30-с шага (прямо противоречит RFC 6238 §5.2 и духу критерия «дамп не даёт секретов» — защита от replay). Nullable-колонка в той же миграции, backfill не нужен.
- **Challenge без состояния в БД** (HMAC, не таблица): одноразовость пары «пароль+код» обеспечивают лимиты guard'а и срок 5 минут; подделка/подмена ловятся подписью и перепроверкой учётки (активность, телефон, TOTP всё ещё включён) на втором шаге — e2e покрывает подделанный challenge.
- **Ключи KDF — scrypt с дефолтными параметрами**: вход — уже случайный длинный ключ env (не пароль человека), повышение N сверх дефолта упирается в `maxmem` Node без выигрыша к безопасности этого сценария.
