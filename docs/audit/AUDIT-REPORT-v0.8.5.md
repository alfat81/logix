## Проверка №6. Конкурентные операции

- **6.1 Двойная конвертация:** два одновременных POST → 201 + 409, в БД ровно 1 заявка, лид won. Механизм: `SELECT…FOR UPDATE` на строке лида внутри транзакции + уникальность Order.leadId. **PASS**
- **6.2 Гонка «смена варианта ↔ конвертация»:** параллельно «создать вариант Б с isSelected:true» + «конвертировать». Итог: заявка получила снимок варианта А (того, что был выбран под блокировкой) — ядро конвертации консистентно; НО вариант Б был создан выбранным **уже на won-лиде**: pre-check варианта (409 при won/order) стоит ДО транзакции без блокировки строки лида → TOCTOU. Состояние после гонки: на лиде выбран вариант Б (300 000), в заявке снимок варианта А (100 000) — несогласованность отображения. → **AUD-01**
- **6.3 Параллельное назначение подрядчика:** два одновременных PATCH одного этапа разными подрядчиками → оба 200, итог last-write-wins (Подрядчик Б), порчи/потери нет (скалярная колонка). **PASS**
- **6.4 Ошибка в середине конвертации:** тестовая БД-бомба (триггер BEFORE INSERT ON "Order" с RAISE EXCEPTION; снят после теста) на лиде, клиент которого рождается ВНУТРИ транзакции. Итог: HTTP 500, состояние БД равно состоянию «ДО»: клиента нет, заявки нет, лид по-прежнему calculated, событий и писем нет — **откат полный**. **PASS**
- **6.5 Повторные события и диспетчеры:** повторная эмиссия события не добавляет строк очереди (dedupKey @unique + createMany skipDuplicates); дубликатов dedupKey в БД 0. Три параллельных прохода диспетчера по одной immediate-строке: терминальный статус ровно один раз, attempts=0, реальных отправок 0 — НО два прогона отчитались «обработано» по одной строке → окно гонки подтверждено фактически. Двойная отправка продемонстрировать в песочнице невозможно (нет e-mail-провайдера) → **AUD-05**, PARTIAL.

## Д. Решение о готовности

1. **Сквозной процесс «запрос → заявка → завершённая перевозка» работоспособен?** Да. Доказано фактически: 37 полей запроса сохраняются и видны обеим сторонам; 35/35 полей переносятся в заявку (снимок груза, маршрут, Инкотермс, ТН ВЭД, выбранный вариант без себестоимости, брокеры, документы с версиями и S3-ключами); лид архивируется в won с двухсторонними ссылками; этапы создаются по каталогу, чек-листы DF-14 блокируют завершение без финальных документов; заявка завершается только после всех обязательных этапов и валидных переходов статуса; откат транзакции при сбое полный; двойная конвертация исключена.
2. **Можно ли допустить текущую версию к пилотной эксплуатации?** Да, при выполнении условий из п.3 (три точечных исправления, суммарно ~0.5–1 день).
3. **Что блокирует пилот:** AUD-02 (кликджекинг-защита — одна строка в CSP), AUD-01 (гонка варианта/конвертации — рассинхрон цен на сделке), AUD-06 (fail-fast storage — защита от тихой потери файлов при ошибке конфигурации деплоя).
4. **Что блокирует полноценный production (за пределами пилота):** AUD-03 (уникальность телефона пользователей — дублирование при росте числа одновременных выдач доступа), AUD-04 и AUD-05 (гонки второго фактора и диспетчера — вероятность растёт с нагрузкой), плюс завершение DF-14 (AUD-12) до её выката.
5. **Что можно безопасно отложить:** AUD-07, AUD-08, AUD-09, AUD-11; AUD-10 — как продуктовое решение отдельной карточкой.
6. **Архитектурные ограничения:** связь «вариант расчёта ↔ подрядчик» отсутствует (осознанное ограничение MVP — расширение возможно без ломки существующего); заметки/история остаются на лиде и не дублируются в заявку (доступ через order.lead); статус in_progress при конвертации не ставится — осознанный ручной шаг менеджера. Для расширения функциональности не блокируют.
