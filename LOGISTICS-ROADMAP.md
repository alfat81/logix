## 1. Продукт в одном абзаце

Внутренняя операционная платформа международной мультимодальной логистики:
воронка запросов (лиды) → расчёт вариантов → конвертация в заявку → этапы
перевозки с исполнителями → обмен документами с клиентом и брокером →
печатные формы. Четыре контура доступа: сотрудники (`/admin`), клиенты
(`/client`), таможенные брокеры (`/broker`), подрядчики (`/contractor`).
Стек: Next.js 16 (App Router, Turbopack) + Prisma + PostgreSQL (Neon) +
Tailwind/shadcn, деплой Vercel, аутентификация собственная (scrypt +
сессии в БД, четыре независимых набора cookie).

Название `logix` — плейсхолдер (см. README): влияет на SEO, домен,
юридические документы и микрокопи — блок «Контент» в разделах 5.4/5.5.

## 3. Принципы (непротиворечивая часть старой карты + новые решения)

1. **Четыре портала — четыре типа пользователей, не четыре роли в одной
   таблице.** Отдельные таблицы сессий и cookie; пересечение куков
   проверяется смоуком.
2. **Статусами верхнего уровня управляет человек, не триггеры** (Lead,
   Order, ContractorLead — ручные переводы; терминальные статусы
   достигаются только операциями: won — конвертацией, contracted —
   рождением подрядчика).
3. **Заявка — источник правды после конвертации.** Груз и условия
   переносятся снимком (cargoInfo/quoteSnapshot); правки лида заявку
   не меняют.
4. **Обязательные этапы подставляются автоматически и не удаляются**
   ни в UI, ни на сервере (lookup каталога живой, не снимок).
5. **Видимость определяется связью со сделкой**, а не этапом: брокер
   видит заявку целиком; подрядчик — только свои этапы; внутренние
   документы/события (isInternal) внешним контурам недоступны.
6. **Файлы — в БД, отдача — только через авторизующий роут**; лимит 4 МБ,
   белый список MIME. Публичных URL у файлов нет.
7. **Цены подрядчиков и ставки менеджерского пула клиенту не показываются**
   (решение №1, 14.10.2026). Ценообразование как модуль — отложено.
8. Каждое write-действие пишет Activity (лог активности) и защищено
   `requireEmployee(req, {roles?, write})` / аналогами порталов.
9. Схема меняется неразрушающе (db:push, новые nullable-колонки/таблицы);
   миграции с потерей данных запрещены без отдельного решения.

Внутри каждой группы задачи упорядочены 🔴 критично → 🟡 важно → 🟢 средне.

трекинг) — если ответ «нет», S/M/N-сайт-часть переквалифицируются в
«SEO-гигиена служебных зон» (M1–M2 остаются всегда).

## 4b. Правила работы (обязательны для всех задач)

- Одна задача = одна ветка (`feat/L1-smoke-in-ci`) = один PR = один squash-коммит (`feat(L1): <что>`).
- Перед задачей — воспроизвести проблему (manual-сценарий или падающий тест).
- После задачи — чек-лист приёмки (4f) + регресс-проверка соответствующего gate.
- **Bump версии в `package.json` — только в release-коммите после фазы**
  (`release v2.1.0 — Фаза 0: Q+L+E0`), не после каждой задачи.
- Каждая задача: пункт в CHANGELOG (или шапке worklog) + `[x]` в карточке этой
  карты + коммит со ссылкой на ID задачи.
- **Запрещено:** менять денежный/нумерационный контур вне задач группы L/E;
  удалять функции («переупаковать, а не удалять»); мержить красный CI;
  применять `db:push` к боевой БД (см. R13/R17 раздела 4c).
- **Ре-план каждые 2–3 спринта:** объёмы уточняются по факту прогонов; задачи
  внутри фазы можно переставлять, но не переносить назад через gate без
  явного решения владельца и перезамера. Решение — записью в `worklog.md`
  (`## Ре-план после Спринт X.Y`).

## 4d. Правило reuse-first (обязательно для всех задач)

> **Урок GT2/GT2-AUTO из соседнего проекта (APEX Moto):** была написана новая
> magic-link-механика (+140 строк, +1 зависимость), хотя в проекте уже были
> `hashPassword`, `sendEmail`, готовый reset-эндпоинт. Откатили, переиспользовали:
> тот же результат, zero new deps. В Logix риск тот же: четыре auth-модуля
> (`auth.ts`, `client-auth.ts`, `broker-auth.ts`, `contractor-auth.ts`) выглядят
> как повод написать пятый — а правильный шаг (K-консолидация) наоборот убирает дубли.

**Правило: перед реализацией задачи обязательно проверить существующие
инструменты и в первую очередь пользоваться ими. Новые библиотеки/файлы/env vars
создавать только при отсутствии подходящих существующих.**

### Чек-лист агента перед реализацией (mandatory)

1. **Аудит хелперов `src/lib/`** (23 файла):
   ```bash
   ls src/lib/ && grep -rn "export \(async \)\?function" src/lib/ | head -60
   ```
   Ключевые: `password.ts` (hashPassword/verifyPassword/needsRehash),
   `login-guard.ts` (checkLoginGuard/recordLoginAttempt/getClientIp),
   `phone.ts` (normalizePhone/phoneVariants/isEmail), `orders.ts`
   (createOrderWithStages/summarizeOrderStages/todayUtcMidnight),
   `leads.ts` (схемы zod + статусные словари), `documents.ts` (полный цикл
   файлов), `activity.ts` (logActivity/четыре actor'а), `list-query.ts`,
   `api-errors.ts` (apiErrorResponse).
2. **Аудит API-роутов** (68): `find src/app/api -name route.ts` — прежде чем
   плодить новый эндпоинт, проверить PATCH/POST в смежных (`/api/admin/orders/*`,
   `/api/client/*`, `/api/broker/*`).
3. **Аудит компонентов**: `src/components/admin/` — списки/карточки уже есть
   (LeadsList, LeadCard…); новый экран сначала собирается из существующих.
4. **Аудит полей Prisma-схемы** (23 модели): `grep -A 30 "^model Order" prisma/schema.prisma` —
   часто нужное поле уже существует nullable (например `cargoInfo`, `quoteSnapshot`).
5. **Аудит env vars**: сейчас их пять — `DATABASE_URL`, `MASTER_PHONE`,
   `MASTER_PASSWORD`, `DISABLE_RATE_LIMIT`, `NODE_ENV`. Новая переменная —
   только если ни одна из этих не покрывает.
6. **Аудит зависимостей** `package.json`: Next 16 / Prisma / Tailwind / shadcn /
   zod / scrypt (node:crypto). JWT/nodemailer/web-push нет — если задача
   «просит» новую библиотеку, в PR описать, чем плохо существующее решение.

### Когда создавать новое

- **Новый хелпер** — только если ни один из 23 в `src/lib/` не подходит по назначению.
- **Новая библиотека** — только если задача не решается стандартными средствами
  (пример будущего: `@aws-sdk/client-s3` для K-выноса файлов в R2).
- **Новый env var** — только для нового секрета (пример: `SENTRY_DSN`).
- **Новый cron** — только если периодическая задача не покрывается существующими
  (сейчас cron-задач нет вообще — первая появится в K2/E8).

### Документирование решения

Если принято решение «создать новое» — в описании PR указать: какие инструменты
проверил, почему не подходят, почему новое минимально и не дублирует существующее.

## 4e. Правило brand-book compliance (обязательно для всех задач)

> Пока брендбука нет (вопрос Q14 открыт), роль эталона выполняет **сам код**:
> токены в `globals.css`/Tailwind-конфиг и компоненты `src/components/ui/`.
> Задача D4 создаёт `BRAND-BOOK.md` как первый официальный эталон; с этого
> момента каждый PR обязан ему соответствовать.

### Автоматические guard-скрипты (появляются в задачах D1/D4, встают в CI)

```bash
bash scripts/check-hardcoded-colors.sh   # hex/rgb вне токенов — 0 совпадений
bash scripts/check-status-badge.sh       # бейджи статусов только через единый компонент
bash scripts/check-money-format.sh       # fmtMoney определён ровно в одном месте
```

Если любой скрипт падает — PR не мержится (до его появления — ручная проверка).

### Ручная проверка (в описании PR, обязательно)

- [ ] Цвета/отступы — только классы токенов, никаких новых hex.
- [ ] Иконки — Lucide, эмодзи в UI запрещены.
- [ ] Тексты пользовательских экранов соответствуют глоссарию H1/J1 (enum → термин портала).
- [ ] Термины «лид/заявка/запрос» употреблены по матрице H1, жаргон («Конвертировать») наружу не попадает.
- [ ] Форматирование денег/дат/телефонов — только общие функции (`fmtRuDate`, `formatPhoneInput`, единый fmtMoney после D2).
- [ ] Тёмная тема не сломана новыми компонентами (или явно отложена решением J4/I4).
- [ ] Мобильная ширина 375px: новые таблицы/формы не выходят за экран (G4).

### Документирование проверки

В PR — строка `brand-book: OK` + перечень проверенных пунктов; нарушения,
вынесенные в отдельные задачи, указываются ссылками на ID этой карты.

## 4f. Универсальный чек-лист приёмки (Definition of Done)

0. **Reuse-first аудит выполнен** (4d) — в PR описано, что переиспользовано,
   что создано заново и почему.
0b. **Brand-book compliance выполнен** (4e) — guard-скрипты + ручная выборка.
1. **Проблема воспроизведена ДО правки** (тест или manual-шаги).
2. **Исправление минимально точечное**, без «заодно»-рефакторингов вне скоупа.

### 5.3 Информационный архитектор — структура, навигация, логика

**Что посмотрел:** карту маршрутов (25 страниц, 68 API-роутов), AdminNav
(секции «Сделки»/«Справочники»), GlobalSearch, Breadcrumbs, grouping
`(dashboard)`/`(portal)`, структуру URL всех четырёх порталов.

**Вердикт.** URL-структура ровная и предсказуемая (`/portal/сущность/id`),

кодом; (2) объекты одного жизненного цикла живут в разных ветках без
перекрёстных ссылок-«семейств» (заявка ↔ её лид ↔ документы ↔ счёт);
(3) навигация внешних порталов не имеет «корня-обзора» — каждый начинается
со своего списка, и переход «все мои дела на этой неделе» отсутствует.

**Рекомендации.**
- **П1-ИА-1.** Словарь терминов (глоссарий) — обязательный артефакт в
  репо: клиент видит «Запрос» (Lead source=cabinet), менеджер — «Лид»,
  результат — «Заявка» (Order). Зафиксировать, какие слова где легальны,
  и пройтись по микрокопи (совместно с 5.5). В коде: `Lead` — внутреннее
  имя, наружу — «запрос».
- **П1-ИА-2.** «Карточка сделки» как объединяющий слой: в Order Card
  свести блоки Этапы → Документы → Брокеры → Подрядчики → История в
  едином порядке убывания важности, добавить ссылку на лид-источник
  (есть) и обратную из лида; сейчас порядок блоков исторический
  (дорастал по дорожкам).
- **П1-ИА-3.** Разделить в AdminNav «Сделки» и «Ресурсы»: подрядчики и
  брокеры — это не «справочники», это пул исполнителей; группа
  «Справочники» из 7 пунктов размывает приоритет (сотрудники оказываются
  рядом с этапами перевозки). Предложить: Сделки · Ресурсы (подрядчики, брокеры) ·
  Контрагенты (клиенты, договоры, юрлица) · Настройки (этапы, сотрудники).
- **П2-ИА-4.** Стабильные идентификаторы сущностей в URL оставить cuid,

- **П2-ИА-5.** Документооборот: типы документов (DOCUMENT_TYPES) —
  плоский список из 7; при росте ввести группировку (транспортные /

### 5.6 Технический специалист / архитектор — ограничения, производительность, интеграции

**Что посмотрел:** next.config.ts, package.json, auth-библиотеки (4
параллельных модуля), lib/db.ts, list-query, orders.ts (retry P2002),
schema.prisma (индексы, Bytes в DocumentVersion), DEPLOY.md, CI, отсутствие
миграций (db:push), отсутствие rate-limit на API, serverless-модель Vercel.

**Вердикт.** Архитектура выбрана трезво: stateless-сервер + сессии в БД
совместимы с Vercel; retry-петли на гонки номеров; изоляция portal-auth.
Но пять решений имеют цену на горизонте года:
(1) файлы в Postgres (Bytes) — база растёт скачками, Neon bill и backup
деградируют, лимит 4 МБ лечится только объектным хранилищем;
(2) db:push без миграций — на боевой базе с данными это риск потери
колонок при конфликтах; (3) дублирование auth-модулей (4 копии ~90 строк)
— правки безопасности придётся делать четырежды; (4) нулевой rate-limit
на бизнес-роуты (защита только на входе) и отсутствие CORS-политики —
при публичном домене API доступен любому с валидной парой cookie из
другого origin (lax частично спасает POST-forms, но GET-чтение с
подсказками времени — вопрос); (5) scrypt без явных параметров cost —
зависит от дефолтов Node, апгрейд рантайма меняет стоимость проверки.

**Рекомендации.**

- **П1-QA-2.** Unit-тесты чистых ядер: normalizePhone, parseListQuery,

- **П1-QA-3.** Матрица прав доступа как экспресс-тест: 4 актёра × 12
  ресурсов (read/write/404/401/403) — автоматическая проверка изоляции

### 5.8 SEO-специалист — индексация, семантика, техническое SEO

**Что посмотрел:** layout.tsx (metadata: только title/description «Logix»),
отсутствие robots.txt/sitemap, лендинг `/`, страницы входов ×4, доменную
главу DEPLOY.md (vercel.app-поддомен, плейсхолдер названия), lang="ru".

**Вердикт.** Важно разделить два объекта: **закрытая ERP-платформа**
(индексировать нечего и незачем — ей нужен noindex, а не оптимизация) и
**публичный сайт компании** (его нет: лендинг-заглушка живёт на том же
origin, что кабинеты). Текущее состояние хуже обоих миров: служебные
страницы (`/admin/login`, куки-зоны, print-маршруты) формально открыты
краулеру, canonical/hreflang отсутствуют, мета одинаковы для всех
страниц (наследуются из root layout), og-тегов нет. При покупке домена
это ударит и по бренду, и по безопасности (раскрытие структуры админки).

**Рекомендации.**
- **П0-SEO-1.** `robots.ts`: Disallow для /admin, /api, /client, /broker,
  /contractor + `X-Robots-Tag: noindex` на все не-публичные маршруты
  (middleware). Это не про трафик — про то, чтобы ссылка на вход в
  логистическую базу компании не висела в поиске.
- **П1-SEO-2.** Когда появится маркетинговый сайт — вынести на отдельный
  subdomain/домен (`www.` vs `app.`), sitemap.xml + structured data
  (Organization, LocalBusiness), уникальные metadata по маршрутам
  (сейчас наследуются).
- **П1-SEO-3.** Домен: решить название до покупки (плейсхолдер logix
  занят десятками проектов; .vercel.app в РФ блокировался волнами —
  DEPLOY.md сам это отмечает). Семантика бренда: «международная
  логистика + [регион/ниша]» — кластеры запросов задать до написания
  лендинга (совместно с 5.9 воронкой).
- **П2-SEO-4.** Если лендинг остаётся на app-origin — хотя бы
  `canonical` + разные description для `/` и страниц входов; og:image
  с текстом «вход для клиентов/подрядчиков/брокеров» (шаринг ссылок в
  мессенджерах — основной канал B2B-трафика сюда).

**Открытые вопросы.**
1. Планируется ли вообще входящий трафик (сайт-витрина), или клиенты
   приходят только через менеджеров? Если второе — весь блок сводится
   к П0-SEO-1 (защита от индексации).
2. Будет ли публичная страница трекинга заявки по номеру (классика
   логистики: «17-1 → где груз»)? Это единственный случай, когда у
   платформы появляется публичный URL с содержательным SEO-смыслом.
3. Какой регион/языки продвижения (RU/KZ/UZ/EN)? Определяет hreflang
  и доменную зону.

### 5.9 Аналитик данных / CRO-специалист — воронки, конверсии, точки потерь

**Что посмотрел:** модель воронки (Lead: new/calculated/won/lost +
lostReason; source manual/cabinet; QuoteOption isSelected; конвертация
→ Order.leadId; Activity-лента timestamps; planned/actual даты этапов),
экран «Требует внимания» (порог 3 дня), дневной лимит запросов клиента
(CLIENT_LEAD_DAILY_LIMIT).

**Вердикт.** Данные для полноценной аналитики уже собираются — это редкая
удача: события в ленте имеют автора и время, лиды — источник и причину
отказа, этапы — план/факт. Не хватает ровно одного: **идентификатора
ответственного**. Ни Lead, ни Order не хранят managerId — нельзя посчитать
конверсию «по менеджерам», нагрузку, скорость реакции; нельзя построить
воронку «время до первого ответа» (первое событие в Activity есть, но
привязать его к человеку-владельце лида нельзя, если лид создан одним,
а ведёт другой). Вторая дыра — точка потери «calculated → lost» без
контекста цены конкурента; третья — клиентский request (source=cabinet)
не отличается от ручного по SLA: менеджер может не знать, что кабинетный
запрос ждёт быстрее.

**Рекомендации.**
- **П0-CRO-1.** Поле `assignedToId` (Employee) на Lead и Order +
  проставление при создании/конвертации; без него невозможно ни
  распределение нагрузки, ни мотивация, ни cohort-анализ. Дешёвая
  nullable-колонка сегодня, болезненная backfill-миграция завтра.
- **П1-CRO-2.** Воронка-отчёт (read-only агрегат над существующими
  таблицами): new → calculated (медиана времени расчёта!) → won/lost;
  срез по source (кабинетные лиды конвертируются лучше ручных? гипотеза),
  по priorityFit варианта, по incoterm/направлению.
- **П1-CRO-3.** Точки потерь, которые система видит, но не показывает:
  лиды `new` старше 3 дней (есть на экране внимания — но нет эскалации),
  лиды `calculated` без движения >N дней (клиент «подумает»), заказы со
  статусом этапа `problem` (единственный негативный сигнал в исполнении —
  собрать вокруг него SLA-уведомления).
- **П1-CRO-4.** Время расчёта — главная метрика скорости B2B-логистики:
  замерить `first Option createdAt − Lead.createdAt`; цель «<4 часов»
  превращается в конкретные очереди задач, если посчитать текущую медиану.
- **П2-CRO-5.** A/B не применимы (малый трафик) — вместо экспериментов
  красть время: причинно-следственные срезы lostReason × «были ли у
  клиента альтернативы» (кол-во options) — проверить гипотезу
  «1 вариант = отказ, 2–3 варианта = win».
- **П2-CRO-6.** Дашборд владельца: 6 чисел на неделю (лидов пришло/ушло,
  median time-to-quote, активных заявок, % problem-этапов, docs-sla,
  revenue proxy = сумма quoteSnapshot won-заявок) — на базе экрана
  «Требует внимания», не отдельным продуктом.

**Открытые вопросы.**
1. Есть ли внешние источники выручки (1С, банк), чтобы сверять «цена в
   QuoteOption» с фактически выставленным счётом? Без счёта маржу не
   посчитать никогда.
2. Как считаем «скорость ответа клиенту», если первое действие может
   быть звонком мимо системы? Нужен ли «зарегистрировать звонок» паттерн?
3. CLIENT_LEAD_DAILY_LIMIT защищает от спама — но не искажает ли он
   воронку (клиент с 3 правками запроса = 3 лида)? Обсудить редактирование
   запроса вместо повторного создания.
4. Кто и как часто будет смотреть отчёты? Если никто — строим не дашборд,
   а еженедельную авторассылку чисел.
