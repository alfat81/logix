# Changelog

## [0.5.5] — Фикс e2e-заморозки: лендинг читает флаг в рантайме (26.10.2026)

Прогон v0.5.4 впервые дошёл до шага «Сквозной тест заморозки» (основной e2e 149/149 стал зелёным — фикс мок-базы 0.5.4 сработал), но заморозка дала 15/16: «на лендинге нет ссылки „Вход для подрядчиков"» нашла ссылку. Корень: лендинг — серверный компонент без динамики, Next пререндерил его в статику и вшил значение `CONTRACTOR_PORTAL_ENABLED` в HTML на этапе `next build`. В CI сборка идёт с флагом `true` (job-level env для основного e2e), поэтому перезапуск сервера шага заморозки с `false` ссылку из кэша сборки убрать не мог. Локально дефект не воспроизводился: агент собирал без флага. На проде проявлений нет (там флаг не задан, HTML без ссылки) — дефект чисто CI-механический плюс нарушение заявленного контракта флага.

Фикс: `export const dynamic = "force-dynamic"` в `src/app/page.tsx` — лендинг рендерится на каждый запрос, флаг читается в рантайме. Этим возвращено обещание `src/lib/flags.ts` («смена env не требует пересборки»): из трёх потребителей флага `proxy.ts` — всегда runtime, страница «Подрядчики» — динамическая из-за auth, лендинг был единственной статикой. Основной e2e не проверяет HTML лендинга — не задет. Приёмка в конфигурации CI (build с флагом=true, сборка не пересобирается перед заморозкой): основной e2e 149/149, заморозка 16/16; вывод сборки: маршрут `/` стал `ƒ` (dynamic) вместо `○` (static). Цена: лендинг рендерится на каждый запрос — страница без обращений к БД, для служебной системы приемлемо.

## [0.5.4] — Фикс CI e2e: удаление мок-базы AI Studio (26.10.2026)

Job «e2e API (PostgreSQL)» был красным во всех прогонах контура проверок (v0.5.2 #27, v0.5.3 #28/#29): логин администратора 401 «Неверный телефон или пароль» и каскад «Не авторизован», хотя сид отчитывался о создании мастер-учётки, а все статические job'ы были зелёными. Корень: проверка `isDummyUrl()` в `src/lib/db.ts` считала «фиктивной» любую строку подключения с `localhost` — CI-раннер (`DATABASE_URL=postgresql://logix:logix@localhost:5432/logix`) получал пустой in-memory мок вместо реальной БД: сид писал учётку в PostgreSQL, сервер искал её в моке. Проверка health «БД доступна» (E0-10) отвечала из того же мока — потому и вводила в заблуждение. Вторая мок-ветка — Proxy-фолбэк на `createMockDb` при недоступности БД (P1001) — в бою молча подменяла реальные данные.

Фикс по принципу fail fast (З1): `src/lib/mock-db.ts` (727 строк) удалён целиком; `src/lib/db.ts` без `DATABASE_URL` бросает явную ошибку, единственный источник данных — PostgreSQL из `DATABASE_URL`, ветка «localhost — фиктивный» убрана. CI: job checks получил сервис `postgres:16` + миграции + сид — интеграционные unit-тесты (convert-atomic, password) раньше «зеленели» через мок (фиктивный PASS), теперь идут по живой БД. Новый `tests/setup-env.ts` (vitest `setupFiles`): загрузка `.env` для интеграционных unit-тестов (vitest сам `.env` не читает), только недостающие переменные. `scripts/integrity_check.py`: из IC-04 убрано исключение `mock-db.ts`. Локальный репро CI-сценария на чистой БД (миграции → сид → сервер → e2e) — 149/149; заморозка — 16/16; негативный контроль: фиктивный `DATABASE_URL` → `/api/health` честно отвечает 503 `{db:"error"}`. Известный косметический warning Next.js (`next start` при `output: standalone`) на работу не влияет — вне скоупа.

## [0.5.1] — Фундамент: атомарная конвертация, разграничение прав, гигиена (DF-00, 26.10.2026)

Первый релиз Фазы DF («Единая картина сделки»): закрыты задачи P1-09 (минимальный скоуп разграничения прав), P1-10 (атомарная конвертация лида в заявку), ужесточена безопасность паролей и скриптов.

### Атомарная конвертация лида (P1-10)
- `POST /api/admin/leads/[id]/convert`: все мутирующие операции объединены в единую интерактивную транзакцию `db.$transaction` с таймаутом 15с.
- Клиент (findOrCreateCustomer), заявка (createOrderWithStages), обязательные этапы, won-статус, перенос брокеров (carryBrokersToOrder), перенос документов (carryDocumentsToOrder) и аудит-логи в обе ленты (logActivity) коммитятся или откатываются целиком.
- В `createOrderWithStages`: добавлена блокировка строки контракта (`SELECT id FROM "Contract" WHERE id = ${contract.id} FOR UPDATE`) для предотвращения гонок нумерации `numberInContract` без retry-петли на P2002.
- Ветка самовосстановления убрана: повторная конвертация всегда возвращает 409 с номером существующей заявки.
- Разгрузка `orders.ts` (368 → 252 строки): сводка этапов и расчет ETA вынесены в `src/lib/order-summary.ts` (RULES 2.14).

### Разграничение прав ролей (P1-09)
- Только мастер (`roles: ['master']`):
  - Каталог этапов: POST /api/admin/stage-catalog, PATCH и DELETE /api/admin/stage-catalog/[id].
  - Юридические лица: POST /api/admin/legal-entities, PATCH /api/admin/legal-entities/[id].
  - Удаление запросов: DELETE /api/admin/leads/[id].
  - Возврат из терминальных статусов: `lost`/`won` у лида, `completed`/`cancelled` у заявки.
  - Менеджерам возвращается 403 Forbidden.
- Добавлен автоматический аудит-тест `permissions-guard.test.ts`, гарантирующий наличие `{ write: true }` у всех мутирующих эндпоинтов и защиту мастер-онли роутов.

### Безопасность и гигиена
- `src/lib/password.ts`: убран фолбэк на открытый текст в `verifyPassword`. Значения без префикса `scrypt:` отвергаются (401/false).
- `scripts/seed.ts` и `.env.example`: удален режим `file:` (SQLite); режим `--dev` разрешен только при подключении к `localhost` или `127.0.0.1`.
- `docs/SECURITY-ACTIONS.md`: команды переведены на PowerShell (`$env:DATABASE_URL`, `Read-Host -AsSecureString`).
- CSRF-прокси: подтверждена корректная работа защиты Origin в `src/proxy.ts`.

## [0.2.4] — Фаза 1: ответственный менеджер (24.10.2026)

### Ответственный менеджер (P1-01)
- `Lead.assignedToId` и `Order.assignedToId` (nullable FK на Employee, индекс) + `Order.updatedAt` (маркер движения, как у лида — Ж5). **Первая миграция после baseline** — см. протокол А в инструкции релиза.

Повторная установка того же — 400 (контракт статуса); несуществующий/деактивированный сотрудник — 400; у won-лида ответственный не меняется (409) — лид после конвертации история, ответственность живёт в заявке.

- Backfill в миграции: существующие лиды/заявки получают ответственным создателя (первое событие `lead_created`/`order_created` с актёром-сотрудником в Activity); кабинетные запросы и битые ссылки остаются NULL.
