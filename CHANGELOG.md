## [0.7.11] — DF-16 «Разрешительные документы: обязательства и напоминания» (31.10.2026)

На расчёте брокер определяет перечень необходимых разрешительных — их оформление тормозит сделки чаще всего, а отследить было нечего. Теперь каждое обязательство — строка `PermitRequirement` на запросе/заявке: кто предоставляет (клиент/брокер/сотрудник), к какому сроку, блокирует ли отправку; пока строка `pending` — плашка «Ожидается: … — от …, до …» видна всем сторонам сделки, мяч (DF-05) у держателя, строка в «Ждём от вас» писем; закрывается загрузкой документа прямо в строке (клиент/брокер/сотрудник) или «не требуется» с причиной (сотрудник); блокирующая с близким/прошедшим сроком даёт красное `permit_overdue` (скан диспетчера, не чаще раза в `permits.remind_every_days`).

- **Модель и миграция `df_16_permits`** (первая с DF-19): `PermitRequirement` — цель ровно одна (`leadId`/`orderId`), `providedBy client|broker|staff`, `isBlocking`, `neededBy`, `status pending|received|waived`, `documentId`, `receivedAt/Name`, `waivedReason`, `staffNote` (видна только сотрудникам), `itemId` (привязка к строке ответа брокера DF-18), `source manual|estimate`, `createdBy*`, `lastRemindedAt`; инвариант цели — как у Document/Activity. Expand-часть + перенос данных: `BrokerEstimate.requiredPermits` (Json-список DF-18) → pending-строки `source='estimate'` (providedBy=client, дедуп по паре сделка+lower(title), lost-лиды пропущены); поле остаётся до contract-релиза (DEPRECATIONS).
- **Ядро** (`src/lib/permits.ts` чистый, `permits-db.ts` серверный, `permits-access.ts` доступы — D35): запись только через ядро (события — только через `emitEvent`, гард DF-01); строки анатомии: `permit_added` (клиенту письмо: расчёт — сразу, перевозка — обычный), `permit_received` (ответственному), `permit_waived` (без писем), `permit_overdue` (красный); PATCH `received` запрещён (только файлом), `waived` требует причину; удаление документа возвращает строку в ожидание (`revertPermitDocument` + пересчёт мяча); бизнес-ошибки ядра — `Error.statusCode` 4xx, `apiErrorResponse` теперь отдаёт их честным кодом (единый хелпер).
- **API трёх кабинетов**: `GET+POST /api/admin|broker/{leads|orders}/[id]/permits`, `PATCH /api/admin/permits/[id]`, `POST /api/{admin|client|broker}/permits/[id]/document` (reюз `createDocumentOnDeal`, type=`permit` — IC-14); чужая строка — 404 (Г4/И1); GET-карточки всех шести отдают строки (наружу — без `staffNote`/`source`/`lastRemindedAt`); цель брокерского лида — заявка после конвертации (семантика `resolveLeadDealTarget`).
- **Ответ брокера (DF-18)**: `requiredPermits` синхронизируется в строки при сохранении оценки (`syncEstimatePermits`: добавленные создают pending одним событием, исчезнувшие удаляют СВОИ pending без документа); привязки `itemId` перемапливаются после пересоздания строк оценки (`remapPermitItemIds` по коду ТН ВЭД); свободный список в EstimateView больше не рисуется — его место заняла секция строк.
- **UI — секция «Разрешительные документы»** (`src/components/permits/*`, единый `PermitsSection` на три кабинета — паттерн DocumentsSection): сводная плашка «Ожидается: …» по самой срочной строке (`pickMostUrgentPermit`), строки §4.3-lite (срок tabular + бейджи статуса PERMIT_BADGE_VARIANTS и «Блокирует» / название / «Предоставит: …»), красная только блокирующая просроченная (§3.3; «окно N дней» — забота скана писем, интерфейс красит по факту); кнопки строки — «Загрузить документ» (клиент/брокер/сотрудник), «Править» (сотрудник, включая «не требуется» с причиной), «Добавить» в шапке секции (брокер/сотрудник); подключения: карточка запроса и заявки админки, клиентские запрос/заявка, брокерские расчёт/заявка.
- **«У кого мяч» (DF-05)**: причина `awaiting_permit` — правило 2а (заявка, после проблемы этапа) и 1а (запрос, после proforma); держатель — по `providedBy` (клиент/брокер/менеджер); waiver/получение отпускает мяч (пересчёт в транзакции события).
- **Письма**: блок «Ждём от вас: …» в regular-дайджесте получателя (DF-03) и секция разрешительных в сводке владельцу (DF-08); скан просрочки — в проходе диспетчера до дайджестов (ответ: `permitOverdue`), красный дефолт `notifications.red_event_types += permit_overdue` (§8).
- **Конвертация В4**: строки переносятся в заявку (`carryPermitsToOrder`), событие конвертации считает их в перечне переносов; дубликат события — нет (updateMany с фильтром).
- **Гейты:** vitest **409/409** (+37: чистые правила permits 24, `awaiting_permit` в waiting 10, красное permit_overdue по providedBy 3, гард дефолта red_event_types), e2e **475/475** (+41: sync, письмо клиенту, проекции трёх кабинетов, закрытие строкой, 404 чужих, перенос при конвертации, красный скан с идемпотентностью, «Ждём от вас» в дайджесте, легаси-оценка теперь держит мяч у клиента — правило 2а, waiver возвращает правило 7), заморозка D31 **16/16**, tsc 0, eslint 0 ошибок (8 старых warning), build OK, integrity 0-новых (baseline IC-14 +22 — единый паттерн роутов/диалогов permits с reason), knip 38=38, scope OK; **миграция одна** (`df_16_permits`), новых env и зависимостей нет (pg-клиент обёртки песочницы — вне проекта); скриншоты — `download/screenshots-v0.7.11/`.

Скачивание: повторная проверка сигнатуры (в том числе для старых файлов), несовпадение → `attachment` + `application/octet-stream`; картинки — с `CSP: sandbox`. (E0-07)
