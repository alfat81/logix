# Changelog

## [0.2.4] — Фаза 1: ответственный менеджер (24.10.2026)

### Ответственный менеджер (P1-01)
- `Lead.assignedToId` и `Order.assignedToId` (nullable FK на Employee, индекс) + `Order.updatedAt` (маркер движения, как у лида — Ж5). **Первая миграция после baseline** — см. протокол А в инструкции релиза.
- При создании лида и ручной заявки ответственный — текущий сотрудник; запрос из клиентского кабинета (И1) рождается «Без ответственного». Конвертация лида (В4) переносит ответственного в заявку; у лида без ответственного заявку ведёт тот, кто конвертировал.
- Смена ответственного — PATCH лида/заявки (`assignedToId`: id сотрудника или null — снять) с записью в журнал (`lead_assignee_changed` / `order_assignee_changed`: «Ответственный: X → Y», назначение/снятие — отдельными формулировками). Повторная установка того же — 400 (контракт статуса); несуществующий/деактивированный сотрудник — 400; у won-лида ответственный не меняется (409) — лид после конвертации история, ответственность живёт в заявке.
- Списки лидов и заявок: фильтр `?assigned=mine|unassigned|all` («Мои / Без ответственного / Все»), колонка «Ответственный», сортировка `sort=stale` — «давно без движения» (`updatedAt` asc).
- Backfill в миграции: существующие лиды/заявки получают ответственным создателя (первое событие `lead_created`/`order_created` с актёром-сотрудником в Activity); кабинетные запросы и битые ссылки остаются NULL. Связь FK — `ON DELETE SET NULL` (прецедент — подрядчик на этапе): API-удаления сотрудника нет, история назначений живёт в Activity-снимках.

### UI (минимально необходимое по D18)
- Новый компонент `AssigneeField`: в карточках лида и заявки выбор ответственного (мастер — справочник сотрудников, менеджер — read-only подпись: справочник сотрудников читает только мастер, Ж6в). Деактивированные сотрудники в выборе не участвуют.
- Списки лидов и заявок: кнопки фильтра «Мои / Без ответственного / Все», сортировка «Давно без движения», колонка ответственного.

### Тесты
- e2e: **82/82** (+21 проверка P1-01, включая приёмку «менеджер B не видит лид A в фильтре Мои», перенос при конвертации, журнал смены, отказы 400/409, сортировку и фильтры обоих списков). vitest 12/12, tsc/eslint чисто, production-сборка ок.

### Процесс и документы
- Применено D21: полный текст инструкции деплоя дублируется агентом в чат владельцу (файл `RELEASE-INSTRUCTIONS-v0.2.4.md` остаётся частью релиза).

## [0.2.2] — Фаза 1: статусная модель и даты (24.10.2026)

### Статусная модель (P1-05)
- `src/lib/status-machine.ts` — единая матрица разрешённых переходов лида и заявки (чистый модуль: его используют роуты, unit-тесты и будущий UI). Заявка: Расчёт → Согласование → В работе → Завершена (перепрыгнуть «Согласование» можно), «Отменена» — из любого не-терминального. Лид: Новый → Рассчитан → Выигран/Отказ; «Выигран» — строго терминальный. (P1-05)
- Завершение заявки: все обязательные этапы (по актуальному каталогу) должны быть «Завершён», иначе 409 со списком незавершённых. Мастер может перекрыть: `override=true` + обязательный `overrideComment` — попадает в журнал заявки. (P1-05)
- Возврат из терминальных статусов («Завершена», «Отменена» у заявки; «Отказ» у лида) — только мастеру, с обязательной причиной; причина и причина отказа сохраняются в журнале. (P1-05)
- Лид: ручной перевод в «Рассчитан» без вариантов расчёта запрещён (409) — закрыта находка аудита №7; переход `calculated → new` закрыт. Повторная установка того же статуса заявки — 400 (контракт лида В2). (P1-05)
- GET карточки заявки отдаёт `allowedTransitions` (код + подпись) — UI показывает только допустимые переходы. (P1-05)

## Фаза 0: безопасность и гигиена (23.10.2026)

### Безопасность
- Удалены из репозитория файлы с паролем мастера (`check-master-pass.js`) и шесть файлов cookie-сессий (`cmv*`); пароль вычищен из журнала. `scripts/check-master-pass.mjs` принимает кандидатов только аргументами. Сид больше не печатает пароль в лог. **Требуются действия владельца — см. `docs/SECURITY-ACTIONS.md`.** (E0-01)
- Rate-limit входа: IP берётся только из доверенного источника (Vercel / `TRUSTED_PROXY=true`), подмена `X-Forwarded-For` не даёт новых попыток. Лимит по логину с любых IP больше не блокирует вход, а замедляет ответ (до 5 с) — злоумышленник не может запереть владельца. Жёсткая блокировка — по IP и по паре «логин + IP». (E0-05)
- Загрузка документов: проверка сигнатуры файла (magic bytes) — HTML/скрипт под видом PDF отклоняется; DOCX/XLSX без MIME от браузера определяются по содержимому. Скачивание: повторная проверка сигнатуры (в том числе для старых файлов), несовпадение → `attachment` + `application/octet-stream`; картинки — с `CSP: sandbox`. (E0-07)
- Security-заголовки на все ответы: CSP, HSTS, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy; убран `X-Powered-By`. `robots.txt` и `X-Robots-Tag: noindex` для кабинетов и API. (E0-04)
- CSRF: изменяющие запросы к `/api/*` с чужим `Origin` отклоняются (403), `src/proxy.ts`. (E0-09)

### База данных
