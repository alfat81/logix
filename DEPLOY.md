# Logix — локальный запуск и деплой

Этот файл описывает **реальный** процесс — git push в GitHub → Vercel
собирает и деплоит автоматически. В APEX Moto на каком-то этапе
`DEPLOY.md` разошёлся с реальностью (описывал несуществующий
self-hosted Windows-процесс, пока прод давно уехал на Vercel) — здесь
правило простое: если процесс деплоя меняется, этот файл правится в том
же коммите, не откладывается.

---

> **С 23.10.2026 схема управляется миграциями (Prisma Migrate), `db:push` на рабочие базы запрещён.**
>
> - Новая база: `bun run db:deploy` (применяет `prisma/migrations`).
> - **Существующая база, созданная через `db:push`** (в том числе текущий прод в Neon) — один раз пометить базовую миграцию как применённую, ничего не меняя в данных:
>   ```bash
>   DATABASE_URL="<direct-строка>" bun run db:baseline
>   DATABASE_URL="<direct-строка>" bun run db:deploy   # должно ответить «No pending migrations»
>   ```
>   Перед этим проверьте, что прод-схема совпадает с репозиторием:
>   `bunx prisma migrate diff --from-url "<direct-строка>" --to-schema-datamodel prisma/schema.prisma` — вывод должен быть пустым.
> - Изменение схемы: разработчик делает `bun run db:migrate --name <задача>` и коммитит папку миграции. На прод: Neon branch (снимок) → `db:deploy` → проверка.
> - Упоминания `db:push` ниже читать как `db:deploy`.

## 1. Что нужно завести один раз, до первого запуска

1. **Аккаунт на [Neon](https://neon.tech)** — бесплатного тарифа
   достаточно для старта. Создать проект, регион — **Frankfurt (eu-central-1)**
   (важно для скорости — см. раздел 4).
2. **Аккаунт на [Vercel](https://vercel.com)**, привязанный к тому же
   GitHub-аккаунту, где будет репозиторий.
3. **Репозиторий на GitHub** — создать пустой, запушить в него каркас
   проекта (см. раздел 2).
4. **Node.js 20+ и [bun](https://bun.sh)** локально (`curl -fsSL
   https://bun.sh/install | bash`).

## 2. Первая заливка кода в GitHub


запушить, не нужно коммитить заново.)

```bash
bun install
```

Открыть `.env`, вставить строку подключения из Neon (Neon Console
→ ваш проект → Connection string → **Pooled connection**, не Direct —
пул соединений важен, serverless-функции Vercel открывают много
коротких соединений, без пулинга Neon быстро упрётся в лимит).
Важно: именно `.env`, не `.env.local` — Prisma CLI (`db:deploy`, `db:migrate`)
читает только `.env`/`prisma/.env`, а не Next-овские `.env.local`.

```bash
bun run db:deploy  # применяет миграции prisma/migrations (создаёт все таблицы)
bun run seed        # мастер-учётка + каталог этапов + юрлицо-образец (один раз)
bun run dev         # http://localhost:3000, вход: /admin/login
```

**Файлы документов (Е) хранятся в базе** (`DocumentVersion.fileData`,
BLOB/bytea), не в файловой системе: переживают эпизодический диск
Vercel и путешествуют с базой между песочницами. Скачивание — только
через авторизующий роут `/api/document-versions/[id]/file` (проверка
кук сотрудника/клиента/брокера), публичных ссылок у файлов нет. Лимит
загрузки — 4 МБ на файл (вписывается в предел тела запроса
serverless-функций Vercel ~4,5 МБ); форматы — PDF, PNG, JPEG, WebP,
DOC/DOCX, XLS/XLSX, ZIP. Обслуживание базы с документами — обычное:
`db:push` при обновлениях (новые таблицы Е не разрушающие), бэкапы
Neon захватывают файлы вместе с данными.

(Нюанс для `db:push` и сида: им надёжнее давать **Direct**-строку —
одноразово, прямо в команде: `DATABASE_URL="<direct>" bun run
db:push`; переменная в команде перекрывает `.env`, поэтому
pooled-строка остаётся в `.env` для `bun run dev`. Пул в Neon
работает в transaction-режиме, для DDL не гарантирован —
подробно в разделе 4.1.)

Вход после сида: `+79000000000` / `logix-master`. Значения по умолчанию
работают ТОЛЬКО в локальном режиме (SQLite в `DATABASE_URL` или флаг
`--dev`). Против не-локальной базы (PostgreSQL/Neon) сид откажется
работать, пока в окружении не заданы ОБА значения — `MASTER_PHONE` и
`MASTER_PASSWORD` (З1: отказ до записи в БД, пароль по умолчанию
в бою недопустим — прямой аналог admin123).

Если меняли `prisma/schema.prisma` локально — всегда `bun run
db:push`, потом перезапуск `bun run dev` (Prisma Client генерируется из
схемы, живёт в `node_modules`, устаревает молча, если забыть
перегенерировать).

### 3.1. Обновление версии из zip-поставки (каждый новый logix-bN.zip)

Zip приносит новую схему и новый код, но НЕ трогает вашу базу и не
перегенерирует Prisma Client. Поэтому после распаковки поверх старой
копии — всегда три шага, даже если всё «и так работает»:

```bash
bun install          # свежие зависимости (если добавились)
bun run db:deploy    # применяет новые миграции к базе
bun run db:generate  # перегенерирует Prisma Client из новой схемы
# перезапустить dev-сервер: Ctrl+C → bun run dev
```

Дев-сервер НЕ подхватывает перегенерированный Prisma Client на лету —
без перезапуска он продолжает работать со старым (симптом: необъяснимые
500 на ровном месте). Типичный сценарий промаха: обновились с версии
Б-эры на В-эру без `db:push` → заявки открываются, а «Лиды» падают 500
(в Neon нет таблиц `Lead`/`QuoteOption` — API теперь честно напишет об
этом в тексте ошибки).

## 4. Подключение к Vercel (один раз)

1. Vercel Dashboard → **Add New → Project** → выбрать репозиторий
   `logix` из GitHub.
2. Framework Preset определится автоматически как Next.js — ничего не
   менять.
3. **Environment Variables** — добавить `DATABASE_URL` (та же строка,
   что в `.env`, но для прод-ветки Neon — если используете
   отдельную Neon-ветку/проект для прода, а не ту же базу, что для
   разработки — рекомендуется). Добавить для окружений **Production** и
   **Preview** отдельно, если прод и препрод должны смотреть в разные
   базы.
4. **Деплой** — Vercel соберёт и выложит сразу после подключения, без
   дополнительных действий.

`vercel.json` в репозитории уже задаёт `"regions": ["fra1"]`
(Франкфурт) — ближе и к Neon (если регион Neon-проекта тоже Frankfurt),
и к пользователям в России/Европе, чем регион по умолчанию (обычно
US). Это тот самый пункт, который в APEX Moto завели не сразу, а когда
уже заметили задержку — здесь сделано сразу, менять не нужно.

**Домен.** Пока своего нет — Vercel сразу выдаёт дефолтный
`<имя-проекта>.vercel.app`: приложение от домена не зависит (все
ссылки относительные), HTTPS есть и на дефолтном домене, вход
работает сразу. Свой домен подключается позже (Dashboard →
Settings → Domains) без правок в коде. Нюанс для РФ: у
`*.vercel.app` бывали волны массовых блокировок — если
пользуетесь из России, проверьте доступность дефолтного домена
из рабочих сетей и не затягивайте с личным доменом.

### 4.1. Первый боевой деплой: посев прод-базы

После подключения (раздел 4) Vercel соберёт и выложит приложение
автоматически, но прод-база Neon ещё пуста: таблиц нет, мастер-учётки
нет — логин-страница откроется, а вход и любой запрос к данным упадут
с ошибкой БД. Посев делается один раз, с локальной машины.

**Какую строку брать.** Для `db:push` и сида — **Direct**-строку
(Neon Console → проект → Connection string → Direct): пулер Neon
(Pooled) работает в transaction-режиме и для DDL/prepared statements
не гарантирован — pooled-строка остаётся для `DATABASE_URL` на
Vercel (раздел 4).

```bash
# 1. Таблицы в прод-базу:
DATABASE_URL="<direct-строка>" bun run db:deploy

# 2. Мастер-учётка: против не-локальной базы сид требует ОБА
#    значения (З1), пароль по умолчанию в бой не проходит:
DATABASE_URL="<direct-строка>" \
MASTER_PHONE="+79001234567" \
MASTER_PASSWORD="$(openssl rand -base64 24)" \
bun run seed
```

Переменная, указанная прямо в команде, перекрывает `.env` —
прод-строка не оседает в локальном файле.

Пароль генерируется один раз и сразу уходит в менеджер паролей:
сид печатает его в терминал открытым текстом («+ Мастер-учётка:
… / пароль: …») — лог посева не пересылать в чаты и не оставлять
на скриншотах. Повторный запуск сида безопасен: существующего
мастера пропустит, каталог этапов актуализирует, дублей не будет.

Смены мастер-пароля через UI пока нет (очередь задач), а сид
идемпотентен и существующего мастера НЕ обновляет — для смены
пароля есть скрипт:

```bash
DATABASE_URL="<direct-строка>" \
MASTER_PHONE="+79000000000" \
MASTER_PASSWORD="$(openssl rand -base64 24)" \
bun run set-master
```

`MASTER_PHONE` можно опустить — скрипт возьмёт единственного
мастера базы; если мастеров несколько, откажется и перечислит
телефоны. `MASTER_PASSWORD` обязателен всегда: значений по
умолчанию у скрипта нет ни в одном режиме. Подтверждение
печатается без самого пароля.

Отдельный случай — база, посеянная **до З1**, где мастер родился
с `logix-master`: сид это не лечит (существующего мастера не
трогает) — пароль меняется той же командой `set-master` выше.

**Проверка после посева:**

1. Открыть домен Vercel: `/admin/login` (сотрудники), `/contractor/login`
   (портал подрядчиков), `/client/login` (кабинет клиента) и
   `/broker/login` (портал брокеров) отвечают.
2. Войти телефоном из `MASTER_PHONE` и паролем из посева —
   открывается кабинет `/admin` со списком заявок.
3. `curl -I https://<домен>/admin` без сессии → `307` на логин —
   так и должно быть.

### 4.2. CI: автоматические проверки в GitHub

В репозитории живёт `.github/workflows/ci.yml` — после первого
`git push` GitHub сам запускает проверки на каждый пуш в `main` и
на каждый pull request:

1. `prisma validate` — схема согласована (провайдер postgres);
2. `tsc --noEmit` — типы (перед ним `prisma generate` — типы клиента
   Prisma генерируются в `node_modules`, без этого шага tsc падает
   на импортах из `@prisma/client`);
3. `eslint` — линт;
4. `next build` — сборка (те же шаги, что делает Vercel).

Настраивать ничего не нужно: workflow сам ставит bun и зависимости,
а `DATABASE_URL` внутри — фиктивный и публичный (никакие проверки в
базу не ходят, страницы за авторизацией динамические; значение нужно
только чтобы Prisma разобрал `env("DATABASE_URL")` из схемы).
Секретов в GitHub для CI не требуется.

Результат — вкладка **Actions** в репозитории: зелёная галочка на
коммите = проверки прошли; красный крестик → открыть прогон, там
виден упавший шаг и лог. Это ранний сигнал до деплоя: Vercel
сообщит письмом, а CI — сразу в интерфейсе GitHub, и pull request
со сломанным кодом не даст зелёную отметку «checks passed».

### 4.3. Планировщик уведомлений (DF-03, один раз)

Письма трёх режимов (D33) рассылает внешний вызов диспетчера — время рассылок
не зашито в код: эндпоинт сам решает по настройкам, что пора (окна 09:00/16:00
по Москве, повторы, «красные»). Источник вызовов — workflow GitHub Actions
`.github/workflows/scheduler.yml` (каждые 5 минут — минимум бесплатного
тарифа; окно считается выполненным, если вызов пришёл в течение 15 минут после
начала; задержки допустимы). Завести в GitHub: Settings → Secrets → Actions:

1. `CRON_SECRET` — тот же, что в Vercel (Bearer-токен диспетчера).
2. `APP_BASE_URL` — боевой адрес приложения (например, `https://logix.example.com`).

Подстраховка — суточный Vercel Cron (`vercel.json`, `crons`) на случай
недоступности Actions: окно 09:00 МСК выполняется вызовом либо из Actions,
либо из Cron — дедупликация (`dedupKey`) двойной отправки не допускает.

Боевая отправка (Resend) — отдельные шаги владельца в
`docs/releases/RELEASE-INSTRUCTIONS-v0.6.5.md`: подтвердить домен, добавить
DNS-записи SPF/DKIM/DMARC, выпустить ключ, положить `RESEND_API_KEY`/`EMAIL_FROM`
в Vercel, отправить проверочное письмо на gmail и mail.ru/yandex.

## 5. Обновление продакшена

Никаких ручных шагов — Vercel собирает и выкладывает **автоматически**
на каждый `git push` в `main`:

```bash
git add -A
git commit -m "описание изменения"
git push
```

Проверить статус сборки — Vercel Dashboard → Deployments, там же лог
сборки, если что-то упало.

**Если меняли `prisma/schema.prisma`** — миграцию создаёт разработчик (`bun run db:migrate`), а `bun run db:deploy` нужно
выполнить и против прод-базы тоже (обычно — локально, указав в
`DATABASE_URL` прод-строку на момент запуска команды, либо через Neon
SQL Editor вручную для сложных миграций). Vercel сам по себе схему в
базу не прокатывает — это отдельный шаг, не часть `next build`.

## 6. Частые проблемы

| Проблема | Причина | Решение |
|---|---|---|
| Build падает с `DATABASE_URL не задан` | Переменная не добавлена в Vercel или добавлена не в то окружение (Production/Preview) | Project Settings → Environment Variables — проверить, что есть в нужном окружении |
| Локально всё работает, на Vercel — ошибки Prisma про отсутствующие поля | Забыли `db:push` против прод-базы после изменения схемы | Выполнить `bun run db:push` с прод `DATABASE_URL` |
| Долгий отклик API | Регион функций не совпадает с регионом Neon | Проверить `vercel.json` (`regions`) и регион Neon-проекта — должны совпадать или быть соседними |
| `too many connections` от Neon под нагрузкой | Используется Direct-строка подключения вместо Pooled | В Neon Console переключиться на Pooled connection string |
| Страница открывается, а API отдаёт 500 (например, «Запросы») | Обновили код из zip, но не выполнили `db:push` — в базе нет таблиц новой дорожки (Д добавила таблицы брокеров: `Broker`, `BrokerSession`, `LeadBroker`, `OrderBroker`, `BrokerEstimate`) | `bun run db:push` + перезапустить `bun run dev` (раздел 3.1) |

## 7. Чек-лист перед первым реальным деплоем (не демо)

- [ ] `DATABASE_URL` в Vercel — это **не** та же база, что используется
      для локальной разработки (если данные уже не тестовые)
- [ ] Регион Neon и `vercel.json` согласованы
- [ ] Первый посев прод-базы — по разделу 4.1: `db:push` и сид с
      **Direct**-строкой, `MASTER_PASSWORD` из генератора
      (`openssl rand -base64 24`), сразу в менеджер паролей
- [ ] Вход мастером проверен на домене Vercel (не на localhost)
- [ ] Если база посеяна до З1 (мастер с `logix-master`) — пароль
      сменён через `bun run set-master` (раздел 4.1)
- [ ] `NODE_ENV` в проде — `production` (Vercel выставляет это сам,
      проверить не нужно, но держать в голове при любых кастомных
      скриптах здоровья/тестовых роутах, которые должны быть закрыты в
      проде — см. урок из APEX Moto про `/api/test/*`)
- [ ] Мониторинг: UptimeRobot (бесплатный план) → HTTP(s)-монитор на
      `https://<домен>/api/health`, интервал 5 минут, ключевое слово
      `"db":"ok"`. Ответ `503` — база недоступна.
